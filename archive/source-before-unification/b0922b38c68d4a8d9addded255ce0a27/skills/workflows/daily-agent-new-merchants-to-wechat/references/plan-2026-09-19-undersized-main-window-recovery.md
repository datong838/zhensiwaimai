# 桌面微信过小主窗口恢复方案

## 问题

生产预检在尚未创建 attempted、发送次数为零时，发现唯一标题为“微信”的窗口尺寸为 280×380。共享定位器先按 700×500 过滤主窗口，再尝试调整窗口，因而错误返回 `wechat-main-window-count-not-one`，阻断了已采集的新商家。

## 方案

1. 共享桌面定位器保留“恰好一个正常尺寸主窗口”的原有安全规则。
2. 当正常尺寸候选为零、但标题为“微信”的全部候选恰好一个时，代码仅将这一个已确认窗口恢复至既定安全尺寸，然后重新按原规则核验。
3. 多个正常尺寸窗口、多个过小同名窗口及任何其他辅助窗口仍失败关闭；不自动关闭窗口，不改变群、正文、发送次数、历史或游标。
4. 在激活、窗口边界和 OCR 定位共用该恢复逻辑，补充回归检查；维护入口仅在零发送收据后更新依赖摘要与验收态，再由总执行器复跑一次。
5. 商户维护入口把已由统一依赖清单登记的 `shared_desktop_locator` 纳入窄维护漂移白名单；维护前仍校验原封板验收，维护器再运行统一依赖维护、完整回归并原子切换验收态，不能直接封板。
6. 统一微信的原生输入激活器也先调用同一尺寸恢复入口，再读取 AX 主窗口；这样预检快路径、发送前聚焦和 OCR 路径不会因窗口过小采用不一致的门禁。

## 验收

- 单个过小同名窗口会被代码恢复后继续精确群定位。
- 多窗口歧义仍返回 `wechat-main-window-count-not-one`。
- 原有文字发送、复制回读、去重及游标提交规则不变。

## 2026-09-26 有界恢复尺寸修订

本轮机器收据显示微信唯一主窗仅 280×380，群预检失败且 `sendAttempts=0`。现场只读核对确认共享恢复逻辑会按屏幕可用区把窗口设到最多 1200×820；这对定位并非必要，且可能造成用户看到近似铺满屏幕的窗口。修订为共享几何计算统一设置上限 1000×700，同时保留最低可用尺寸门槛 900×560，并仍按当前屏幕可用区域裁切。激活和恢复必须调用同一纯函数；不最大化、不关闭窗口，不动群、草稿或账本。新增纯单测覆盖大屏上限、小屏裁切和低于最低尺寸拒绝。其余唯一主窗、未知副窗失败关闭及发送合同保持不变。

首次修订后一次授权复跑仍在预检 60 秒超时。只读 AX 再确认窗口仍为唯一“微信”主窗且尺寸 280×380；根因是共享恢复函数通过 AppleScript 在 `try` 中设置尺寸却吞掉 setter 错误，未验证写入结果。修订为仅对唯一标题主窗使用 AX 原生 position/size 属性设置并立即回读；失败时返回明确尺寸恢复错误，不做循环激活。已有合格尺寸时严格 no-op。恢复尺寸上限、屏幕边距与最低门槛不变，新增 AX setter 拒绝及回读不一致测试。

二次复跑在预检 90ms 失败，原因是共享包不存在 `running_app()`；按共享微信 bundle id 直接枚举 `NSWorkspace` 并校验唯一、未终止后创建 AX app element，加入进程身份的回归测试。

三次复跑在约 95ms 失败；只读 AX 能证明 `AXSize` 不可写、`AXPosition` 可写。恢复实现改为受控 System Events setter 并检查子进程返回码，随后对同一 AX 窗口核对 position/size 回读；不吞异常、不循环尝试。测试覆盖脚本唯一窗口选择和无 `try` 吞错，以及目标尺寸和读取校验。

第四次复跑触发 System Events 返回值拼装转换异常；删除无用的 AppleScript 尺寸字符串转换，只返回固定成功标记，实际接受仍由 AX 回读判断。
