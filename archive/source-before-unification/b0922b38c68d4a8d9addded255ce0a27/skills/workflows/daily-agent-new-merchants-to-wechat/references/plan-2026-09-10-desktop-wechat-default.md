# 新增商家流程桌面微信优先方案（2026-09-10）

## 目标

把已在 `daily-top10-to-wechat-group` 现场验证的桌面微信定位合同复用到本流程。未指定通道时固定使用桌面微信；桌面微信未运行、未登录、聊天主窗不唯一或目标群不能唯一确认时，在商家采集和任何发送之前失败关闭。只有调用者明确指定 `--wechat-channel mobile` 时才使用原手机执行器。

## 实现边界

1. 不复制桌面微信 OCR、窗口或点击算法；统一调用共享 `wechat-desktop-control`。
2. 总执行器在页面采集前执行 `open-group --exact`，要求完整群名搜索结果唯一且进入后顶部标题精确复核。
3. 共享控制器只操作唯一精确名为 `微信` 的聊天主窗；允许 `微信 (窗口)` 网页窗和 `图片和视频` 媒体查看窗存在但绝不控制，未知大副窗失败关闭。
4. 搜索候选不依赖“群聊”“最常使用”或任何可能变化的分区标题。搜索面板已经展开时，只要左侧结果区出现唯一完整群名候选，就必须直接点击，禁止先按 `Esc` 或再次点击搜索框把现成结果收起；搜索输入框本身不算候选。点击后仍须通过顶部完整群名唯一复核，不依赖固定坐标、近期会话截断名或聊天正文。
5. 桌面与手机继续共用成功历史、游标和 attempted 标识；任何通道出现未知发送结果，另一通道不得补发。
6. 默认改为桌面不改变生产群、测试群、消息内容、游标或授权边界。

## 验收

- 默认启动结果记录 `wechatChannel=desktop` 和桌面微信预检耗时。
- 桌面预检失败时，商家采集次数和发送次数均为 0。
- 无新增商家时仍完成桌面微信只读预检，但不建立发送账本。
- 显式 `mobile` 时不调用桌面预检，原手机流程保持不变。
- 正常节点 `runtimeModelDecisions=0`。

## 本轮无发送实操

- 首次适配器预检 2.5 秒失败、发送 0 次：微信同时存在名为 `图片和视频` 的媒体查看窗，共享门禁将其识别为未知大副窗。模型介入复盘后，将该窗口固化为“允许存在但禁止操作”的已知伴随窗；聊天主窗和截图目标仍必须唯一精确名为 `微信`。
- 修复后从本流程 `desktop_wechat_sender.preflight` 实际进入目标群，3.794 秒通过；回读顶部标题 `FEIBING NEO AI数字员工（18）`，发送 0 次。
- 22 项流程合同回归、Python 编译和 Skill 快速校验通过；正常运行的群定位节点不需要模型判断。
## 2026-09-10 文本输入稳定性补充

- 桌面微信默认发送文本前，必须通过 `pbcopy` 清空系统剪贴板，清除下载流程遗留的 Excel/图片等文件对象格式。
- 聚焦微信 `AXTextArea` 后直接写入文本框，不再使用剪贴板粘贴或快捷键；从同一文本框逐字回读完整正文，最多在 attempted 建立前重写三次。回读未通过不得创建 attempted、不得按发送键。
- 输入正文验证通过后剪贴板仍保持为空，再创建 attempted 并发送；本流程不读取或污染用户后续办公剪贴板。
- 发送后未知时保留两帧截图并稍后复核当前群底部。只有三份证据共同证明目标气泡未出现，才可隔离原 attempted 并仅重试一次，同时登记模型介入。

## 2026-09-11 桌面微信抢占等待与续跑方案

### 目标

其他进程或人工短时抢占桌面微信时，本轮任务不能因一次定位、聚焦或页面状态漂移而直接放弃。执行器必须先等待，再从同一安全节点恢复；每次等待的原因、次数和耗时写入运行收据，正常恢复不需要模型判断。

### 状态机

1. `desktop_wechat_preflight` 和每条消息的发送前阶段都允许恢复。失败收据明确 `sendAttempts=0`、未创建 attempted 文件时，判定为“尚未发送”，可等待后重新精确打开目标群。
2. 可恢复状态包括窗口/搜索/群标题/输入框/焦点瞬时不可用、输入框非空及发送前页面变化。执行器不清空来源不明的草稿，不点击当前聊天内容，只等待桌面微信恢复稳定。
3. `blocked-login`、授权缺失、输入载荷或本地合同错误、已有 attempted 锁不是抢占，立即进入对应安全门禁，不把它们伪装成等待。
4. 只要 `sendAttempts=1`、attempted 文件已经建立或发送结果未知，禁止自动重试发送；必须沿用既有只读 reconcile 合同，避免重复通知。
5. 单次等待默认最长 900 秒、每 5 秒重试一次；超时后本轮保持游标和成功历史不变，下一小时从同一排他游标续跑，不将任务标记为已完成。工作流互斥锁防止相邻小时重叠执行。

### 收据与验收

- `desktopWechatPreflight` 和 `desktopWechat` 收据增加 `contentionRetries`、`contentionWaitMs`、`contentionEvents`。
- `contentionWaitMs` 只累计实际退避等待，不包含正常群定位、截图或发送校验耗时；无抢占时必须为0。
- 每个事件至少包含阶段、尝试序号、失败原因和当次等待毫秒数；列表不写消息正文。
- 单元测试覆盖预检一次抢占后恢复、发送前一次抢占后恢复、登录门禁不重试、已发送/未知结果不重试。
- 运行时模型决策继续为 0；只有超时或未知发送结果的事后诊断才允许模型介入。

## 2026-09-11 长文本气泡确定性复核

真实整链中长地址在气泡内换行，截图 OCR 将“颍河路”识别为“颖河路”，旧共享发送器因此在已经单击发送、输入框两帧均为空后返回 `desktop-post-send-verification-unknown`。截图可见气泡正确，但模型看图不能作为后续自动运行的常规裁决。

首次尝试使用辅助功能树直接读气泡原文，但当聊天输入框保留焦点时，微信会把可见气泡临时移出 AX 树，产生 `messageCount=0`。因此最终采用现场验证通过的微信原生复制回读；OCR 只定位气泡和“复制”菜单，不裁决正文。边界如下：

1. 仅处理本技能 marker 已存在、状态为 `unknown`、群名和 payload SHA-256 与当前商家完全一致，且失败原因为 `desktop-post-send-verification-unknown` 的记录。
2. 目标群标题必须唯一，聊天输入框为空；用商家名称定位当前可见唯一出站气泡，连续两帧位置稳定后右键该气泡。全屏菜单中“复制”必须唯一，先写随机剪贴板标记，再点击“复制”，回读的完整四行正文必须逐字等于原消息。
3. 满足全部证据后只把原 attempted marker 改为 verified，并走既有“先历史、后游标”提交；不点击发送。任一证据缺失继续保持 unknown，禁止自动补发。
4. 共享发送器刚返回符合条件的 unknown 时立即在同一轮 reconcile；新运行在发送当前商家之前也检查同一 send identity 的 marker。复核成功后继续后续商家，避免等待下一小时、人工删除账本或重复发送。
5. 收据写明 `verificationMethod=desktop-bubble-copy-exact-two-frame`、两帧定位和输入框状态；正常复核 `runtimeModelDecisions=0`。

## 2026-09-11 已展开搜索面板直达方案

本轮真实运行已经把 `FEIBING NEO AI数字员工` 唯一完整结果显示在搜索面板，但旧控制器在识别候选之前先发送 `Esc`，随后又点击搜索框，导致已经可用的结果面板被关闭并连续返回 `exact-group-result-count:0`。这不是登录或群不存在。

修复合同：

1. 首帧先检查当前聊天顶部；顶部已是唯一完整群名时直接通过。
2. 顶部不是目标时，先在左侧搜索结果区寻找唯一完整群名；命中即点击，不读取或依赖其上方的分区标题。
3. 只有首帧既没有目标顶部、也没有唯一完整候选时，才关闭可能残留的无效面板并重新发起精确搜索。
4. 搜索框回显位于顶部输入带，不作为候选；聊天记录摘要必须整段文本完全等于群名才可能进入候选，多个完整同名结果一律失败关闭。
5. 点击候选后必须连续等待并确认顶部唯一完整群名；未确认时发送次数保持 0，不能建立 attempted。
6. 如果精确搜索词已写入顶部输入框但结果面板尚未展开，只允许单击该输入框一次以展开结果；随后重新识别唯一完整群名。候选已经可见时绝不执行这一步，避免把面板再次收起。
7. 微信搜索下拉是独立瞬态窗口，按聊天主窗窗口 ID 截图不会包含它。仅在“读取搜索候选”这一节点，先将微信置前，再按已核验的聊天主窗屏幕边界截取合成可见区域，从而包含下拉层；群标题、输入框、发送前后气泡等证据继续使用聊天主窗窗口 ID 截图。区域截图若被其他应用抢占会得到候选 0，由既有发送前等待重试处理，不得盲点。

## 2026-09-11 文本假成功收据修复方案

真实发送收据记录 `postSendInputCleared=[false,false]`，现场同时可见完整正文仍停留在输入框和绿色“发送”按钮；但旧文本分支仅以聊天区 OCR 探针生成 `signatures=[true,true]`，没有把 `input_cleared` 纳入 `ok`，因此错误写入 verified、历史和游标。触发动作使用 Return 键，又受当前微信“发送/换行快捷键”设置影响，未产生实际发送。

修复合同：

1. 发送动作不再使用 Return、Command+Return 或无效的 `AXPress`；只在唯一聊天主窗、目标群和载荷回读均通过后，从唯一可用且标题为“发送”的 `AXButton` 读取实时位置和尺寸，对其中心执行一次 CGEvent 物理点击，动作次数仍为1。禁止保存固定坐标。
2. 文本、图片、文件三类载荷的两帧发送后验证都必须包含 `input_cleared=true`；任一帧不为空不得生成 verified。
3. 文本 OCR 探针只读取聊天气泡区，明确排除底部输入区，不能把保留草稿识别成新气泡。
4. 当前错误记录不删除、不再次调用常规 sender。只有目标群标题唯一、当前输入框逐字等于原 marker payload、发送按钮唯一时，才允许读取该按钮实时边界并对中心执行一次 CGEvent 物理点击；随后必须用空输入框、两帧稳定气泡和微信原生复制全文一致修复收据。历史和游标已有同一身份记录时不重复追加，只补充恢复证据。禁止 `AXPress`、Return、Command+Return 和固定坐标。

## 2026-09-11 执行器代码封板门禁方案

### 目标

稳定流程不能依赖模型临场阅读 Markdown 后自行决定动作。Markdown 只描述合同；真正的运行许可由代码完成。任何关键执行器内容与真实验收版本不一致时，总流程必须在浏览器、微信和业务状态发生任何动作之前失败关闭。

### 代码合同

1. 新增 `scripts/executor_integrity.py` 和 `executor-lock.json`。锁文件固定本流程入口、采集器、桌面适配器、手机适配器，以及共享桌面微信定位器和发送器的绝对路径及 SHA-256。
2. `workflow_executor.py` 获取流程互斥锁后，第一节点必须调用完整性校验；校验通过后才允许桌面微信预检和浏览器采集。任一文件缺失、路径变化、摘要变化、锁文件结构变化或真实验收凭据不匹配，整轮停止，发送次数为0。
3. 封板凭据绑定本次真实非空发送的恢复收据：唯一“发送”按钮中心 CGEvent 点击1次、输入框连续两帧为空、微信原生复制正文逐字一致、消息 SHA-256 一致、`runtimeModelDecisions=0`。空跑、模拟测试、截图目测或 Markdown 复盘不能生成封板凭据。
4. 共享发送器的固定动作由摘要锁定：禁止键盘发送和 `AXPress`；文本、图片、文件均必须把输入框清空纳入成功条件。未来修改任何被锁代码后，旧锁立即失效；必须在明确解封、测试和新的真实非空验收完成后才可重新生成锁。
5. 完整性节点输出独立收据，记录锁文件摘要、关键文件数量和验收身份，不记录消息正文。每小时自动执行只读取并验证锁，不在运行中修改或重写锁。

### 验收

- 正常版本：完整性节点通过，随后才进入微信预检与采集。
- 任一关键脚本发生单字节变化：完整性节点失败，微信预检、浏览器采集、发送、历史和游标写入次数均为0。
- 锁文件绑定的真实验收收据缺失、被修改或不满足一次物理点击、两帧空输入框、复制回读一致：完整性节点失败。
- 自动化测试同时覆盖正常校验和篡改拒绝；Skill 快速校验通过。

## 2026-09-12 桌面微信窗口截图双通道预检方案

### 现场原因

桌面微信进程、唯一主窗口和 AXMinimized=false 均正常，但 macOS `screencapture -l <window-id>` 返回 `could not create image from window`。旧适配器收到非 JSON 异常后把目录名中的 `wechat-desktop-control` 误当业务原因，并按普通抢占每5秒重试；每次 `open-group` 又会激活微信，因此持续抢占用户桌面。对同一个窗口ID调用 Quartz `CGWindowListCreateImage` 虽可生成 2240×1276 PNG，但像素极差为0、标准差为0，是全黑图；原实现只校验文件和尺寸，误把黑图当成功，后续 OCR 才表现为搜索控件数0。由此确认登录、群名和窗口身份均不是根因，真正根因是截图通道失效且缺少内容有效性门禁。

### 代码合同

1. `screenshot_main_region` 仍先调用现有的窗口ID `screencapture -o -l`；失败时对同一已唯一确认的窗口ID调用 Quartz `CGWindowListCreateImage`。每个候选 PNG 都必须校验文件、宽高和像素变化，纯黑/纯色图不得进入 OCR。
2. Quartz 失败或产出黑图后立即返回明确 `wechat-window-capture-failed`。实机证明 `frontmost=true` 仍可能截到覆盖微信的 Codex，因此禁止使用任何主窗口屏幕区域截图作为发送点击证据。
3. 两种窗口截图都失败属于截图基础设施门禁，不属于人工/进程短时抢占。桌面适配器必须立即停止该轮，`sendAttempts=0`，不得进入5秒/900秒重试循环。
4. 抢占等待合同继续只处理目标群候选、焦点或输入区等短时页面状态；不得用反复激活应用修复底层截图能力。
5. 精确群预检优先读取 macOS AX UI 结构：唯一主窗口中，当前标题完整命中则直接通过；否则只允许定位左侧会话列表中唯一一个“首行完整群名”候选，由点击执行器在同一个原子动作内激活微信并点击，随后再次读取顶部标题复核。AX 候选为0时才进入原搜索流程，候选多于1或标题复核失败时立即失败。该路径不依赖截图、OCR 或大模型，且不得循环激活。
6. 点击执行器的原子激活必须使用 `NSApplicationActivateIgnoringOtherApps`；普通空选项激活不能保证当前工具窗口覆盖时点击仍归属微信。无论点击 API 返回什么，都以点击后的 AX 顶部标题为唯一成功判据。
7. 微信顶部标题会同时暴露父节点“群名(人数)”和同坐标子节点“群名”。标题计数必须先按规范化群名及同一 x/y/高度聚合；同坐标父子节点算一个标题，不同坐标的多个命中仍硬失败。
8. 封板清单必须同时绑定点击器 Swift 源码和实际执行的编译后二进制；只锁 Python 调用方而不锁二进制，不能证明实操使用的是已验收原子激活版本。

### 验收

- 故障注入：主截图命令失败且 Quartz 为黑图时立即失败，整个失败路径没有调用 `activate_wechat`、区域截图或点击。
- 遮挡门禁：禁止仅凭 `frontmost` 属性进行区域截图，不把其他应用画面交给 OCR。
- AX 直达：可见会话列表存在唯一完整群名时，点击一次并由顶部标题复核通过；截图调用次数为0，发送次数为0。
- 双失败：预检只调用一次群定位，返回 `desktop-wechat-window-capture-failed`，等待次数和等待耗时均为0。
- 真实预检：在当前已登录桌面微信上唯一进入并复核目标群，记录实际截图通道和耗时；不发送消息。
