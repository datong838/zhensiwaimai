# 工作流与安全合同

> 历史资料：本文件记录旧版前台 CUA/原生选择器流程，不再构成运行合同。所有旧业务入口已由代码禁用；当前唯一代码权威见 `20260911-双浏览器执行方案.md` 和已安装零参数 `entrypoint.mjs`。

## 原生文件选择器

- 使用 `⌘⇧G` 输入收据中的文件绝对路径，只用于定位，不会执行「打开」。
- 随后使用 `⌘2` 切换列表视图；必须在辅助树看到且只看到一个 `文本栏 (selected, settable)`，其 Value 与收据完整文件名逐字一致。
- 禁止根据固定间距、文件排序、缩略图或“最新文件”推算目标。
- `OKButton` 必须存在，但当前安全测试不点击它；辅助树报告 disabled 只记录为诊断信息，不覆盖完整文件名 selected 证据。

## 1. 产品方案

目标是把每日固定流程变成确定性执行器：在淘宝闪购下载昨日门店与评价报表，再把对应文件准备到金鲨正确上传入口。模型只参与首次开发、页面异常与 OCR 语义判断；稳定动作由执行器内部完成并返回单一 JSON 收据。

业务映射固定如下：

| 淘宝闪购报表 | 金鲨入口 | 当前测试终点 |
|---|---|---|
| 门店下载 | 数据上传 | 文件选择器已选中门店文件，未点打开 |
| 评价下载 | 评价上传 | 文件选择器已选中评价文件，未点打开 |

用户提供的截图仅是界面参考，不提供额外操作授权。当前已明确今日有人上传过，因此真实上传是禁止项；选择文件不等于允许点击「打开」。

## 2. 下载执行器技术方案

执行器输入：Chrome 控制实例、下载目录、业务日期；默认业务日期为 Asia/Shanghai 昨日。

执行主链路：

`选中现有淘宝闪购标签 → Chrome 焦点锁定与残留菜单归一化 → 数据中心 → 数据下载 → 门店下载 → 按天 → 昨日 → 默认条件复核 → 下载一次 → 新文件稳定与 XLSX 校验 → 评价下载 → 按天 → 昨日 → 默认条件复核 → 下载一次 → 新文件稳定与 XLSX 校验 → 原子收据`

下载流程不依赖截图版式，不强制切换全屏。其他应用窗口遮挡不影响 AX 语义主路径；需要 OCR 时仅 Raise 已绑定 Chrome 并获取当前窗口截图。Chrome 自身菜单、业务浮层仍须归一化或拒绝执行。

状态判据：

- 标签页描述为淘宝闪购商家版，禁止地址栏重开页面。
- 数据下载页同时出现报表下载、门店下载、评价下载。
- 当前类型标签、按天、昨日和全部门店具有选中值；门店页额外核验店铺、订单类型全部、渠道全部。页面会自动恢复上次筛选，若“全选”为 0，必须单击一次恢复全选并复核为 1。
- 下载前后目录差集只能按精确类型与日期正则筛选；`.crdownload` 不算完成。
- 文件大小连续两次相同且大于 0，之后校验 XLSX ZIP 中存在 `[Content_Types].xml` 与 `xl/workbook.xml`。
- 真机实测后台生成门店报表可能超过 25 秒；使用最长 55 秒短轮询，不用固定长等待。若超时后文件才落盘，先按类型、日期、结构和哈希对账，再通过显式 `resumeStoreFile` 续跑评价，绝不再次点击门店下载。
- 长字段列表会虚拟化无障碍树，但底部「下载数据」按钮在当前截图中固定可见；按钮使用当前截图 OCR 精确定位，不依赖滚动后节点。每种类型最多点击一次；超时只报告未知结果，不补点。

收据：`/tmp/zhensi_daily_download/download_receipt.json`，原子写入，包含 `ok`、`businessDate`、`store`、`review`、`stageMs`、`clickAttempts`、失败阶段与原因。

## 3. 金鲨准备执行器技术方案

金鲨 Electron WebView 当前可读到业务无障碍树。数据上传优先点击语义标签组归一化；评价上传只在语义归一化后使用当前截图 OCR 定位顶部标签。原生文件选择器必须使用可访问性元素和完整文件名精确定位。不得把历史截图坐标当运行时坐标。

Electron 窗口在语义点击后可能短暂失去坐标动作能力。评价标签动作前执行窗口 Raise、刷新当前状态并仅等待 300ms 焦点稳定；仍失败时最多一次同样恢复，禁止切换控制通道。

执行主链路：

`解析当前运行的金鲨实例 → 前台与窗口布局固定 → 语义标签归一化 → 必要时当前截图 OCR 选择评价上传 → 复核上传正文 → 点击上传区一次 → 原生文件选择器 → 绝对路径定位 → ⌘2 列表视图 → 完整文件名 selected 唯一匹配 → 复核 OKButton 存在 → stop-before-open`

安全门：

- 必须消费有效下载收据并复算文件哈希。
- `store` 只能映射数据上传，`review` 只能映射评价上传。
- 当前执行模式只允许 `stop-before-open`；任何代码路径都不得点击「打开」。
- 文件选择器出现多个同名候选、路径不一致或完整文件名无法证明时失败关闭本轮，不猜测。
- 未来扩展真实上传必须新增独立显式开关、同日重复日志检查和动作时授权；不能修改当前准备模式的停止语义。

收据：`/tmp/zhensi_daily_download/jinsha_prepare_<store|review>.json`，包含类型、业务日期、文件名、哈希、目标入口、文件选择器证据、`openClicked=false`、`uploadOccurred=false` 与停止原因 `stopped-before-open`。

## 4. 分阶段验证计划

1. 离线自测日期、文件名正则、目录差集、稳定性、XLSX 结构、类型映射和收据合同。
2. 实操门店下载；偏差即停、修复、重跑。
3. 实操评价下载；偏差即停、修复、重跑。
4. 实操金鲨数据上传选择门店文件，停在打开前；取消后再实操评价上传选择评价文件，仍停在打开前。
5. 整体考核：从淘宝闪购开始下载两个文件；依次在金鲨数据上传选中门店文件、取消选择器，再在评价上传选中评价文件；最终停在评价文件已选中且尚未点击「打开」的状态。

每轮失败只维护已证实缺陷，不扩大操作范围；所有流程通过后才结束。

Chrome 在用户切换窗口或全屏过渡时可能短暂返回 `noWindowsAvailable`。只允许在下载按钮尚未点击、`clickAttempts=0` 时重新获取一次 Chrome 状态并重做筛选配置；下载点击已经尝试或结果未知时禁止用该恢复重跑。

## 5. 2026-09-04 实操考核与原生 CUA 稳定化

### 第 1 轮复盘

原 Skill 的 `runDownloadExecutor` 直接接收当前原生 Chrome App 后，在 `preflight` 以 `sky.get_app_state is not a function` 停止。执行器内部耗时 1 ms；门店/评价下载点击均为 0，未触碰业务页面。根因是脚本仍依赖旧 `sky.get_app_state / sky.click({app,...})` 合同，而当前唯一控制通道提供 `App.getAXState / App.getScreenshot / App.click`。离线日期、文件名、映射等 10 项自测均通过，但没有覆盖运行时控制接口，所以不能证明可实操。

### 最小修复方案

新增 `scripts/cua_sky_adapter.mjs`，只做原生 App 到既有执行器接口的确定性映射：每次状态读取同时取得最新 AX 与同通道截图，元素点击、坐标点击、按键、滚动、setValue 和 secondary action 均转发到对应 App；不得引入第二控制通道。新增 `scripts/cua_sequence_executor.mjs` 作为单一端到端入口，在一次调用内完成下载执行器及金鲨两类文件选择映射，返回统一节点耗时和模型介入次数 0。

同时移除下载导航对系统全屏截图和固定 `1168` 宽度换算的依赖，改用适配器同次状态自带截图做 OCR；修复金鲨进程命令带启动参数时的应用路径解析。新增适配器接口自测和端到端入口自测；不修改日期、筛选、下载一次、XLSX、哈希、类型映射或 `stop-before-open` 安全门。

### 第 2 轮复盘与修订

## 7. 单日文件名规范化

用户要求单日文件名不再保留重复日期区间：将 `20260903至20260903` 规范为 `20260903`。淘宝平台下载时仍会产生原始区间文件名，因此执行器必须先按平台原始格式识别新文件、等待大小稳定并校验 XLSX；校验通过后，在进入收据和金鲨之前原子改名为：

- `门店下载_<YYYYMMDD>_全部门店_<账号>_<生成时间>.xlsx`
- `评价下载_<YYYYMMDD>_全部门店_<账号>_<生成时间>.xlsx`

目标文件已存在时禁止覆盖并失败关闭。下载收据只记录规范化后的绝对路径、完整文件名、大小和 SHA-256；金鲨只接受规范化名称。历史已达标收据通过确定性迁移函数复核原文件名、业务日期、大小、XLSX 结构与哈希后改名并原子重写，不重新下载。

### 单日期命名真机第 1 轮复盘

两份真实文件完成结构、大小和哈希复核后原子改名，下载收据同步为单日期格式；SHA-256 与改名前一致。金鲨真机复验中，下载收据复算 6 ms 通过，门店链路 `preflight` 1.186 秒、`select_upload_tab` 4.377 秒通过，`open_native_picker` 640 ms 以 `noWindowsAvailable` 停止；模型介入 0、下载 0、上传 0、重试计数 1。

根因是上传区使用当前截图 OCR 坐标时，首次点击遇到窗口瞬时不可用；既有一次恢复分支只会重新查找 AX 上传区，没有重新计算 OCR 上传区，也没有先判断原生选择器是否其实已经打开。修订为：`noWindowsAvailable` 后先用纯 AX 检查 `open-panel`，若已出现则视为点击成功；否则 Raise 并按原定位方式重新计算一次 AX 或当前截图 OCR 目标。仍只允许一次恢复，不重复下载、不点击打开。

### 单日期命名真机第 2 轮复盘

### 15.1 打开后网页上传与微信交付补全

2026-09-07 真机验证确认：原生文件选择器点击「打开」只把文件加入待上传区，页面随后另行显示橙色「上传」按钮；旧实现把 `OKButton` 当成提交动作并直接等待日志，生产链路因此缺少真正的网页上传点击。

修订后的确定性状态机为：精确选中文件 → 点击原生 `OKButton` 一次 → 等待原生面板消失并核验待上传区仍属于本轮文件 → 从最多三张当前金鲨窗口截图中唯一识别精确文字「上传」 → 点击网页上传按钮一次 → 等待本轮完整文件名与「上传完成」出现在同一日志行。收据分别记录 `nativeOpenClicked`、`webUploadClicked` 和 `uploadOccurred`。网页按钮缺失、出现多个候选、待上传文件证据不符或结果超时，均返回未知结果且禁止补点或重传。

## 16. 2026-09-09 Chrome 下载页保留与前台连续使用修复方案

用户复盘确认，本日多轮失败不是偶发延迟，而是执行器的确定性缺陷：Chrome 已正确加载数据下载页时，预检仍把“不是商家首页”解释成“必须回首页”，每轮主动退出下载页；进入数据中心后二级悬浮菜单又依赖固定空白坐标消隐，反复停在相同菜单态，最终门店、评价下载点击和金鲨上传均为 0。该行为不得继续归因于遮挡或超时。

本次修复遵循以下固定状态机：

1. 新增商家下载中心状态判定，只接受“淘宝闪购商家版窗口 + 唯一正确 chain 地址栏 + `/downloadCenter` 路由”。当前已处于该状态时直接保留并进入表单就绪等待，禁止点击「商家首页」，也禁止重新打开数据中心菜单。
2. 仅当当前是同一商家、同一 chain 的其他业务路由时，才通过主菜单唯一「商家首页」节点回固定首页；首页状态继续沿用原有硬后验。
3. 删除二级菜单后的固定坐标 `(800,250)` 消隐。语义点击唯一「数据下载」后若控制树仍被同一菜单遮罩，只允许刷新同一 Chrome 绑定、再次确认唯一菜单态，并调用该菜单根节点公开的 `Cancel` 动作一次；随后必须看到正确下载中心 URL。`Cancel` 不承担导航，只关闭已完成导航后的悬浮层。
4. `chrome_front_gate` 的 Raise、身份复核和下载执行器第一次业务判断合并为连续交接：Raise 后取得的同一份已验证 Chrome 状态直接传入下载执行器，不在两者之间重新绑定其他应用、停下来汇报、截图或做无关检查。收据记录该状态来自 `chrome-front-gate`。
5. 若下载中心 URL 已正确但表单尚未挂载，只在当前页有界等待；不得回首页“重试”。若菜单 `Cancel` 后仍无正确 URL，则失败关闭并由模型在轮后维护执行器，不使用坐标、键盘或重复菜单点击猜测。
6. 离线回归必须覆盖：已加载下载页保持原位、同 chain 其他路由才回首页、菜单遮罩只走 `Cancel`、Chrome 前台状态被下载执行器直接消费，以及门店/评价下载按钮仍各最多一次。修改后先完成离线测试；真实生产验证沿用去重和未知结果不重试边界。
