## 事故：误杀金鲨岗生产浏览器（监理操作越界）

**经过**：大同报"飞书里点开 Chrome 页面打不开"，我为清理诊断测试残留进程，写了
`pgrep -f "Google Chrome..." | while read p; do ps -p $p -o command= | grep -q "user-data-dir" || echo $p; done | kill`
**沙箱内 `ps -p <pid> -o command=` 对所有进程返回空** ⇒ 筛选逻辑失效 ⇒ 命中了**不带 user-data-dir 的第一个 PID = 1125**
= `AOS Background Chrome/jinsha-business`（金鲨岗 9232，已连续运行 1 天多）。

**影响**：9232 掉线；页面重开后落到登录页 `/#/login?redirect=%2FnegativeAnalyse`（登录态需确认）。

**止损**：已按原参数原样恢复 → PID 21260，9232 监听正常，CDP `/json/version` 通，跨命令存活复核 ✓。
**遗留**：金鲨岗页面停在登录页，需大同/车间确认是否需要补登录（我未代登录）。

**追加实证（同日）**：沙箱里 **`pgrep -f` 也会漏报存活进程** —— 我先前用 `pgrep` 判定"默认 profile
Chrome 未运行"，但 `lsof -p 21106` 显示它正握着 `Google/Chrome/Profile 3/` 的文件句柄，即
**用户默认 Chrome 其实一直在正常跑**。⇒ 结论从"用户 Chrome 起不来"翻转为"Chrome 完全正常"。
教训：**沙箱内判进程死活只用 `lsof` / `readlink SingletonLock` + `kill -0 <锁内PID>`，绝不用 ps/pgrep。**

**教训已写入 skill** `workbuddy-sandbox-env-quirks` 新增铁律 3b：
沙箱内 `ps` 是"瞎的"；**禁止用 ps/pgrep 筛选结果驱动 kill/stop/rm**；定位进程只用
`lsof -iTCP:<port>` / `readlink SingletonLock` 等可信来源；破坏性操作前先打印对象清单。
