## 0. 一句话定位

- **车间主任 = 调度 daemon（`careloop` / `runtime/run_all.py --daemon`）**：macOS launchd 常驻进程，按 `runtime/skills_manifest.json` 的时间计划**自主**拉起 20 条任务流（2026-10-18 口径，skills 共 23 = 20 enabled + 2 blocked + 1 共享库），持有真机/微信/浏览器会话不退出。它负责"把活干出来"。

**核心纪律**：车间主任调度，监理监理。两者职责正交，互不替班。

## 2. 车间主任（daemon）职责详解

### 2.1 它是什么、怎么跑
- 入口：`python3 runtime/run_all.py --daemon`（由 launchd `RunAtLoad + KeepAlive` 拉起，崩溃自动重启，等价 n8n `restart: unless-stopped`）。
- 会话常驻：持有 USB 真机 / 桌面微信 / 浏览器 GUI 会话不退出，根治"会话冷启动"类根因。
- 安装/重载：`bash runtime/install_daemon.sh`（生成并 `launchctl bootstrap` 加载 plist；**必须在大同自己的 Terminal.app 里跑**，WorkBuddy 沙箱内 `launchctl bootstrap` 会被拒，详见 §4）。
- plist：`runtime/com.zhensi.waimai.careloop.template.plist` → 注入后落到 `~/Library/LaunchAgents/com.zhensi.waimai.careloop.plist`，label = `com.zhensi.waimai.careloop`。

### 2.2 它做什么（正常职责）
1. 读 `runtime/skills_manifest.json`，按 `enabled` + `cadence_hours`/`earliest_hour`/`order` 统一编排。
2. 以命令行方式调用各 skill **现有入口脚本**（薄包裹层 `skill_runner.py`，零碰 skill 内部逻辑）。
3. 每轮产出 `runtime/state/last_cycle.json`（各 skill 状态/成功时间/是否全绿）。
4. 每轮写心跳 `runtime/state/daemon.json`（`pid / started_at / last_cycle_at / next_cycle_at / status`）。
5. 生成客户版台账 `work/YYYY-MM-DD臻肆工作台账.xlsx`（深蓝表头/绿"是"），**仅当当日 active 全绿**才把汇总发到员工群（老板看），有失败先处理不发群。
6. 周期性跑 `auth_watch` 扫描授权到期（只读告警，绝不代劳重封）。

### 2.3 它**绝不**做什么（铁律）
- 不感知/不绕过任何 skill 内部安全门（`EXTERNAL_EFFECT fail-closed` / 防重账本 / 逐字授权 / `policy sha256 fail-closed` / `UNSEALED_ACCEPTANCE`）。
- 不替自己排班（排班权在 manifest，归大同/监理配置，不归 daemon 运行时）。
- 不擅自改封印依赖文件（见 §6.5）。

## 3. 监理（WorkBuddy）职责详解

### 3.1 三看（日常看护主循环）
1. **盯每轮 `run_history` 结果并记录**：读 `runtime/state/last_cycle.json` 看 20 流绿/红；红的下钻 `runtime/run_history/YYYY-MM-DD/<skill>--<ts>--record.json` 看 reason/category。把结论简要记到 `docs/` 或自动化 memory。
2. **出错及时诊断 + 最小修复 + 重试收敛**：能在本机修的业务脚本（非封印文件）就最小改动修；修完用 `--resume`/手动重跑收敛；修不动（需登录态、需真机、需网络）就等冷却或升级。
3. **需授权的才上报大同**：只有"要动授权/要登录微信/要改封印/要重启 daemon"这类必须人工的情形，才 @大同。纯业务 bug 自己修，不留手。

### 3.2 还要盯 daemon 本身（心跳看护）
- 见 §4。daemon 挂了监理要在 1 小时内发现并喊人，不能再出现"死 25 小时无人知"。

### 3.2.1 每日环境复位（2026-10-03 大同新增，必做）
- **触发时机**：**每天发完当日工作台账之后**（此时当日流已收口）。
- **动作**：把**美团 IM 工作台页面关掉重新打开**——工位 9233 CDP：关闭 url 含 `/imworkbench/` 的页面 → `newPage()` → `goto` 同一 URL → 等渲染 15s → 只读校验页面文本含「未回复」或「待人工回复」。
- **为什么**：长驻 CDP 页面会话态会劣化，导致筛选区/元素不渲染，表现为 `filter-target-not-unique` 之类"元素找不到"。重开即恢复。
- **推广**：遇到**任何**"页面元素找不到 / 流程卡住"，**先做「关掉重开页面」这一步再定性**，不要归咎站点改版（2026-10-03 已误判两次：#12「活动页框架缺失」实为 iframe 竞态、#7「未回复筛选器消失」实为页面状态）。

### 3.3 监理**绝不**做什么
- 不替 daemon 排班（不改 manifest 的 cadence 去"替它调度"）。
- 不绕过安全门、不擅自改封印文件（见 §6.5）。
- 不在 WorkBuddy 沙箱里跑 `launchctl bootstrap`（会被拒，且可能污染）；恢复 daemon 一律让大同在自己 Terminal 跑 `install_daemon.sh`。
- 不 `rm` / 不手工改 `daemon.json`（心跳文件只读监控，异常由 launchd/安装脚本管）。

## 4. 心跳检测机制（两层，必读）

### 4.1 第一层：daemon 自身存活（车间主任自保）
- **launchd `KeepAlive` + `ThrottleInterval=30`**：进程崩溃/被杀，launchd 最多 30s 后自动拉起，会话由进程内保活。
- **心跳文件 `runtime/state/daemon.json`**：`run_all.py --daemon` 每跑完一轮就重写它。字段：
  - `pid` 当前进程号
  - `started_at` 本次启动时间
  - `last_cycle_at` 上一轮完成时间
  - `next_cycle_at` 下一轮预计时间（≈ last_cycle_at + cadence 聚合间隔，正常 ~30min）
  - `status` 通常 `running`
- 判定存活的最简方法：**`next_cycle_at` 距今没超太多 + `last_cycle_at` 在最近 1~2 个周期内** 即正常。

### 4.2 第二层：监理看门狗（WorkBuddy 自动化族群）

### 6.8 监理诊断经验（2026-09-30 work-refine 入库）
1. **「假断网」进程环境分裂诊断法**：daemon 侧报 `Errno 65 No route to host`，但监理侧 curl/ping/urllib（同栈）同时刻全通时，**不是网络问题，是进程环境分裂**（代理变量 / macOS「本地网络」TCC 授权 / 路由差异）。判据 = 同栈复测 + 同时刻对照实验；单侧探测不可信。修法按分裂方向排查，而非等"自愈"。
2. **daemon 心跳语义**：`daemon.json` 的 `last_cycle_at` 写在**周期开始**时；`next_cycle_at` 偏乐观不可信。真实唤醒时刻 = 上周期**全部跑完的时刻** + `cycle_interval_seconds`(1800)。等周期验证修复时按后者算，别按 next_cycle_at 空等。
3. **manifest 双字段语义**：`dev_state=active` ≠ 在派班；`enabled=False` = 人工暂停（如 #5 `daily-taobao-download-to-jinsha`）。判断「daemon 是否漏排」必须两个字段同看。
4. **白名单类 fail-safe 熔断跟进 SOP**：只读探针取证（CDP dump 遮罩文本 + 截图，**不点击**）→ 白名单加文案 + 关闭按钮唯一性闸门 → 手动单跑验证 → daemon 下轮自动转绿。全程不动 frozen core。

`create_connection((target,8731), timeout=8)` 建上游连接后，**该 8s 超时残留并作用于其后所有阻塞 IO**；
`pump()` 里 `dst.recv()` 在上游静默 8s 后抛 `socket.timeout`（`OSError` 子类），被 `except OSError: pass` **静默吞掉**
⇒ 响应泵线程死 ⇒ **任何 >8s 的上游响应永不返回**。症状 = 「快接口通、慢接口必挂」，会伪装成「发送被拒但消息已发出」。

3. 其余任何既有 marker（含本 case 的 `state=='attempted' / sendAttempts==null` / **无 `commonReceipt`**）⇒
