## 一、结论速览

1. **没有"单一模板"**：23 个 skill 的执行器是**异构**的——Python（venv / 特定 venv / python3）与 Node 混用，入口文件名各不相同（`workflow_executor.py` / `workflow.py` / `entrypoint.mjs` / `deliver_batch.mjs` / `business_workflow_executor.mjs` / `hybrid_inspection_executor.mjs` / `appeal_executor.mjs` / `ensure_unanswered_queue.mjs` / `daily_executor.mjs` / `*_daily.py` …）。不存在一处可改即覆盖全部 23 的 candidate 模板。
2. **真正被多 skill 复用的共享库只有 3 个**（其余都是各 skill 自带）：
   - `skills/wechat-messaging/scripts/`（**16 个 skill 依赖**，微信收发底座）

## 四、统一改造可行性（薄包裹层 + 适配）

**结论：可行，但需薄适配层，不能无脑包。** 设计 `runtime/skill_runner.py`：manifest（skill → 解释器 + cwd + 命令 + 参数 + 全局 timeout/看门狗）。

> ✅ **落地状态（2026-10-18 回填）**：`runtime/` 薄层（`skill_runner.py` + `skills_manifest.json` + `run_all.py`）已于 2026-09-30 建成，daemon（launchd `com.zhensi.waimai.careloop`）**自主调度 20 条值班流**。当年两条「需适配」都已解决：`daily-taobao-download-to-jinsha` 库式导出由 `node -e` 包裹 `runScheduled`（10-02 适配层落地）；`meituan-intelligent-customer-service` 已有 `ensure_unanswered_queue.mjs` CLI 入口（只读门禁），不再是「无 CLI」。

- **可直接包（干净 CLI）**：全部 20 条值班流均以 manifest `steps[].argv` 路由，不改内部逻辑。
- **需适配（小包装）**——均已适配：`daily-taobao-download-to-jinsha`（`node -e` 包裹 `runScheduled`；sha256 自锁钉 `entrypoint.mjs`，仍生效勿动）；`meituan-intelligent-customer-service`（CDP 注入已内聚为 CLI）。
- **前置硬约束**：
  1. `wechat-messaging/scripts` 是被 **16 个 skill** 隐式依赖的"共享前置"，调度器须保证其路径/依赖完整。
  2. 解释器混杂（部分 venv、部分 python3、部分 node 缓存路径），manifest 须**逐 skill 指定解释器与 venv**。
  3. 统一把 `.codex/skills/...` 硬编码改为 canonical 或注入 symlink（#6、#13 已发现分歧）。
  4. 在 `skill_runner` 层对每 skill 加**全局 timeout + 进程看门狗**，弥补内部无 timeout subprocess 风险。
