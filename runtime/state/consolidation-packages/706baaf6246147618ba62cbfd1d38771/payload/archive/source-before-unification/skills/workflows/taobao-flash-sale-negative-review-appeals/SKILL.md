# 淘宝闪购昨日差评申诉

## 2026-10-24生效规则（覆盖下文历史时点和自动申诉开启跳过规则）

每日13:00、15:00、17:00、18:30四档；前三档仅执行申诉，18:30查漏后汇总Excel及台账图。主条目仍是`taobao-flash-sale-negative-review-appeals`，调用原`taobao-shangou-negative-review-appeals`申诉器；旧11:20独立排班合并停用。车间主任调用`runtime/appeal_shift.mjs --platform taobao --execute`，入口拒绝上午及19点后执行。

用户确认：未申诉列表中有唯一“立即申诉”按钮的条目均受理，包括“自动申诉已开启”。不关闭自动申诉开关，不等待平台未来自动执行；仍须弹窗内容稳定、一次确认和权威回读。unknown/submitted_once不重复确认，原账本保留。

先完整阅读[流程方案](references/20260921-淘宝闪购昨日差评申诉流程方案.md)。本 Skill 中“发起申诉”和“发送微信群”均为外部写操作：每次实际执行前必须有用户对当次范围的明确授权；只复用已登录的浏览器与微信，不索取、复制或重新登录凭据。

## 范围与入口

- 页面路径：外卖 → 淘宝渠道 → 评价&负反馈 → 差评列表。
- 固定筛选：淘宝闪购、昨日、未申诉；日期以 `Asia/Shanghai` 的自然日为准。
- 仅处理卡片明确显示“自动申诉已关闭”且可见“立即申诉”的条目。自动申诉开启、申诉中、已申诉、已删除或状态不清的条目一律跳过。
- 不以卡片计数、截图或成功提示替代逐条页面状态核验；不对未知结果再次点击“确认申诉”。

## 逐条流程

1. 核验已登录账号、页面、淘宝闪购、昨日和未申诉筛选均已生效，并确认没有登录失效、验证码、风控或异常提示。
2. 对每个合格条目，在点击“立即申诉”前创建当天临时 Markdown：`/Users/ddt/work/projects/ai_agent/zhensi_waimai_back/records/taobao-flash-sale-negative-review-appeals/YYYY-MM-DD/<记录键>.md`。记录键由页面可见的门店、评价日期与稳定可见订单/评价标识构成；不可稳定确定时不处理。
3. 记录门店、评价日期、星级、评价原文（最小必要摘录）、页面状态、自动申诉状态、平台建议回复原文、拟用申诉理由、开始时间与初始状态 `prepared`。不写账号、Cookie、手机号或不必要的订单/顾客信息。
4. 点击“立即申诉”仅打开预览弹窗，不得立刻点击“确认申诉”。必须等待平台智能申诉生成完成，连续两次读取的弹窗文本一致后，才以该文本为准；不得把刚打开弹窗的短暂空白视为无内容。只有等待至页面明确完成或超时且文本框仍为空白时，才填“骑手送餐慢”。不要虚构、改写或扩展平台回复。
5. 将弹窗内实际文本、已选申诉类型和剩余次数写回该条临时 Markdown，状态更新为 `ready_for_confirmation`；再复核条目归属、文本和次数。一次只确认一条。确认后等待页面回到列表或显示权威状态。
6. 仅当同一条目在页面上可回读为“申诉中”或其他明确的已提交状态时，将临时记录更新为 `verified_submitted` 并写入核验时间与页面状态。若超时、页面跳转、弹窗消失但状态不明或出现异常，将其标为 `unknown`，停止当前批次，不重试提交。

## 18:30 昨日申诉闭环与日报

12:30、14:30、16:30 巡检昨天的差评申诉，处理新增的“自动申诉已关闭”未申诉候选并更新当天临时 Markdown。18:30 再汇总；若仍存在可自动完成的候选，先补齐申诉闭环，不得先发汇总。自动申诉开启的候选标记跳过。只有全部候选进入终态，且没有可自动恢复的未完成条目后，才汇总并发送日报。日报可晚于 18:30，但不能早于业务完成。

汇总时点不变，但 Excel 明细以金鲨“全部”页的分页回读为准：同一渠道、昨天、全部页的实际条数必须与 Excel 行数相等。每行写入门店、评价日期、星级、评价最小摘录，以及页面可见的申诉方式、申诉时间和申诉内容；本地 Markdown 只补充已处理条目的申诉类型与核验信息。严禁把 `prepared` 当作已申诉，也不因汇总失败重做申诉。

向完整群名“上海臻肆外卖运营-盯个盯-饭敢当 💰发财精英荟💰”（**运营群**；员工群“FEIBING NEO AI数字员工”不再接收本流结果表，大同 2026-10-22 指定）发送前，必须先使用 [统一微信收发 Skill](../../wechat-messaging/SKILL.md)，并完整阅读其 `references/contract.md` 与 `references/recovery.md`；一次汇总使用业务日期为唯一事件键。只有统一发送器返回 `verified` 或 `already_verified`，才能在当天汇总记录中记为已发送。`attempted` 或 `unknown` 只能对账，绝不补发。

Excel 返回 `verified` 后**必须再补发一张「汇总台账」截图**到同一运营群：先用 `runtime/appeals_summary_card.py --flow taobao --business-date <业务日> --run-key <运行日>` 渲染 PNG，再经 `--workflow-id taobao-flash-appeals-summary`（kind=image，独立 marker `taobao-flash-appeals-summary-<业务日>.json`）投递。两段投递互相独立：Excel 已 verified 而截图为空时只补图，绝不重发 Excel。截图上的数字只允许取 records 事实源与汇总表平台统计行，不得手填或估算。

如果当前已精确核验的群输入区只显示本事件冻结的唯一 Excel，且附件名称、大小、发送按钮均与本次载荷一致，直接点击“发送”一次并回读新文件消息；不将已准备附件误判为待清理草稿，也不重复上传。

## 停止与报告

遇到登录/CAPTCHA/风控、账号或群名无法唯一核验、条目识别不稳定、申诉次数不足、任一提交结果未知，立即停止相关写操作并记录原因。最终报告必须区分 `verified_submitted`、`skipped`、`blocked`、`unknown` 和微信群投递状态；不得根据操作过程或提示语推断完成。
