# 双平台数据接口可用性盘点与实施方案

> 盘点日期：2026-09-12。范围为淘宝闪购、美团外卖的巡店数据接入；全程只读，不申请资质、不创建应用、不生成密钥、不调用业务接口。

## 结论

当前应采用“后台定时导出 + 消费者端巡店补充”的混合方案，而不是立即 API 直连。

原因：金鲨已确认具备两平台的报表下载能力；官方 AppKey、平台开发者资质、具体接口产品权限及门店授权覆盖率尚未确认。先用已经可用的结构化报表覆盖经营指标，待最小授权闭环完成后再以 API 替换导出环节。

## 官方接入边界

### 淘宝闪购

- 淘宝闪购服务商平台公开说明其服务商接口覆盖店铺、商品、订单、配送等业务；接入属于服务商/企业服务场景，不应使用消费者账号或非官方抓包替代。

- 商家授权页面表明平台服务商在授权范围内可管理相应权限，因此必须在授权页逐项确认只读范围，拒绝订单、商品、优惠、卡券等写权限。

消费者端必须保留的补充项：搜索页可见名称与 POI、首屏图片与卖点、公开评价原文主题、分类视觉呈现。它们不应由经营 API 推断。

## 推荐实施路径

### 阶段 A：先落地报表混合方案

1. 由数据负责人在金鲨对每个平台建立固定下载方案：日经营、评价、商品/分类（若页面支持）。
2. 选 1 家已授权门店做只读试导出，确认文件列、日期粒度、平台、门店 ID 与店名映射；不在本阶段自动下载。
3. 建立本地标准化表：`store_snapshot`、`daily_metrics`、`review_metrics`、`menu_snapshot`、`authorization_health`。每行保留数据来源、导出批次、观察日期和字段口径。
4. 巡店执行器优先读取结构化快照；仅对视觉展示和公开评价主题使用消费者端页面。无法取得的检查点仍留空。

阶段 A 的通过门槛：两平台各 1 家店可稳定产生同日期、可映射门店 ID 的日经营与评价数据；导入不含重复店、跨平台混淆或未知日期。

### 阶段 B：最小 API 可行性验证

1. 平台负责人确认主体、已审核应用、AppKey 引用、接口产品和测试门店，不提供明文密钥给巡店执行器。
2. 仅申请 P0 的门店主数据、日经营汇总、评价汇总只读权限；不申请订单写入、商品编辑、优惠券、支付或营销写权限。
3. 用测试门店进行单次无副作用调用，验证签名、分页、日期边界、频控、授权到期与字段映射。
4. 将 API 响应与同日期金鲨报表对账；只有门店、日期、订单/评价数量及关键金额口径一致才扩大覆盖。

阶段 B 的通过门槛：至少各 1 个平台测试门店连续 7 天可读取；与报表对账差异有明确、可接受的口径说明；授权撤销、到期和接口失败均会被记录且不会重试写操作。

### 阶段 C：逐店扩大与降级

- 授权健康表每日检查，失败门店不进入“已完成巡店”结论。
- API 缺字段、过期或故障时自动降级到最近成功的已标注日期报表；不把旧值冒充当前值。
- 报表也不可用时，只做消费者端可见模块；经营后台字段留空。

## 禁止项

- 不使用消费者账号 Cookie、抓包私有接口、逆向参数、自动化绕过验证码或未授权第三方数据源。
- 不把联盟推广 API 当作商家经营 API。
- 不记录 AppSecret、Access Token、商家手机号、订单明细或精确顾客信息到 Skill、代码库或巡店 Excel。
- 不因单店授权成功推断全量门店已授权；授权状态必须按门店、平台和到期日分别记录。
