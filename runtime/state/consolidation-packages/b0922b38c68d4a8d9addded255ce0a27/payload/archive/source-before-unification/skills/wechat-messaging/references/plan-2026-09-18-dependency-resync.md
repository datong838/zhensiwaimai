# 2026-09-18 共享桌面依赖清单同步方案

## 2026-09-28 商户零发送失败后接管本轮自有文字草稿

### 现状与证据

商户总入口完成采集、审计和精确生产群预检后，首条通知返回
`desktop-text-input-write-failed`。商户机器回执明确为 `state=blocked`、
`sendAttempts=0`、`physicalSendAttempts=0`、`stage=prepare_payload`；本轮历史与游标
未变。用户随后提供的生产群截图显示输入框保留了内容。对本轮私有采集记录和零发送
回执做本地摘要核对，截图所示草稿属于首条待发对象且正文哈希一致。

静态追踪表明，`desktop_sender.set_focused_text()` 只要 `osascript` 返回非零就直接抛出
`desktop-text-input-write-failed`，失败分支没有原生回读正文，也没有保留 `osascript`
的退出码/错误输出。因此截图能证明这次错误报告与 UI 实际状态不一致，但现有机器证据
不能区分“AX 写入已生效、随后脚本报错”和“写入部分生效后失败”；根因应记为失败分支
缺少回读判定，不能臆断为单一环境故障。

### 最小恢复方案

- 仅扩展统一桌面适配器的预检恢复：商户主入口为唯一候选传入当前首条对象和原
  `send-attempts` 标记路径；统一适配器必须重新核验标记绑定生产群、对象、逐字正文、
  SHA-256、`blocked`、`prepare_payload`、物理/逻辑发送次数均为 0，且失败原因精确为
  `desktop-text-input-write-failed`。
- 适配器重新激活桌面微信并原生核验完整生产群标题；输入框逐字等于该唯一标记正文时，
  沿用这条草稿进入同一发送器的原文、双帧及原生全文复核并仅点击一次。若为不同的普通
  文字，仅在零发送回执完整绑定时才清空并复读两次；空输入不操作；附件占位符或不确定
  输入一律保留并失败关闭。
- 恢复不点击发送、不写账本、不推进游标。恢复后的真实发送仍且仅由商户
  `workflow_executor.py` 调用统一发送器一次完成，继承双帧、原生全文复核、历史和游标
  提交合同。`attempted`、`unknown`、非零或缺失发送次数不进入该分支。
- 增加离线回归：精确自有草稿清空并确认双空态；用户草稿、不同正文/哈希、群名不符、
  非精确失败原因、状态非 blocked、stage 不符、附件占位符、缺失计数以及清空后仍非空
  均不清空且不调用发送。保留已有媒体预览、常规空输入与防重行为。
- 随后按固定共享依赖维护器和商户维护入口完成全量测试及摘要/验收态原子维护，再由
  商户总入口唯一复跑；所有结果只采纳机器回执。

### 实施状态与权限边界

用户于 2026-09-28 明确授权为完成今日工作修改相关逻辑，并要求核实正确草稿后直接发送。
实施仅使用一个新建、精确绑定本次指令摘要及允许路径的代码维护授权，不扩展旧
`user-20260918-code-maintenance` 范围。此次授权覆盖统一桌面适配器、发送器回读逻辑、
商户桥接与对应测试；不能用于其他目录。运行时继续使用生产授权和唯一商户入口。

失败归因记账：`set_focused_text()` 将 `osascript` 非零直接报告为写入失败，没有逐字读取
控件值，也未保留退出码/错误摘要。截图证明这次 UI 中已有内容，但不能证明具体底层错误。
修复要求：非零后只有原生回读逐字等于请求文本时才可判定输入已写入；否则保留原错误，
并将退出码与限长错误摘要写入私有回执。不得将其他错误判断为写入成功。

实现路径更新：已由明确授权从“清空完全匹配草稿后重写”改为“精确匹配则复用该草稿并
通过发送器单次发送”；仅对回执绑定的零发送草稿执行这一优化。正文不同的普通文字只可
在群、marker、哈希均精确绑定后清理并验证双空态；附件占位符、来源不明、attempted、
unknown 或缺失计数一律拒绝清理/发送。

### 完成条件

旧标记与截图草稿匹配但未生成 attempted；维护测试全通过；本轮每个新商家仅有一次
`sendAttempts=1`、两帧与原生复制全文验证、逐条历史和游标提交；最终游标等于最后
verified 对象。任一状态不满足时保留草稿/证据并停止，不手工发送或推进游标。

## 2026-09-25 定时金鲨截图发送前依赖漂移

### 现状与证据

日报总入口已完成金鲨上传、截图和清理，但统一微信桥因
`dependency-drift:scripts/heartbeat_recovery.py` 在发送前失败。该运行收据的
`sendAttempts` 为 `null`，因此既有固定恢复器正确地拒绝恢复。桥接代码顺序为：
`prepare()` → `verify_dependencies()` → 创建发送账本目录/锁/marker → 桌面适配器、
`deliver()`。本次失败来自 `verify_dependencies()` 且发生在账本与桌面动作之前，
但通用异常包装丢失了这一阶段信息。

### 最小实现

- 在 `workflow_bridge.py` 仅对 `verify_dependencies()` 这一调用点捕获依赖完整性
  拒绝，并转换为专用 `PreDispatchDependencyFailure`。
- `main()` 仅对该专用异常返回结构化 `sendAttempts: 0`、空 `items`、阶段
  `dependency_integrity_preflight`；其他所有异常仍返回 `sendAttempts: null`。
- 回归测试验证专用失败回执的零尝试仅来自该前置异常，并验证 ledger/marker
  未创建、桌面 lookup/send 均为零；另验证一般异常仍不被归类为零。
- 不改发送、查群、发送锁、幂等账本、生产授权或发送重试行为。随后由已有
  `heartbeat_recovery.py` 和 `dependency_maintenance.py` 固定流程完成摘要维护、
  全量测试、完整性回读及唯一最终复跑。

### 完成条件

桥接测试通过；项目与已安装微信技能字节同步；只由维护器更新依赖摘要并回读
clean；日报安装入口 preflight 与离线回归通过；从同一日报总入口恢复后收到
代码生成的 verified 微信回执。任一结果为 attempted/unknown 或无法证明零发送，
不得重发，转只读对账。

## 2026-09-25 微信主窗 AX 候选不唯一

### 现状与证据

摘要维护后，日报总入口成功完成当日流程，上传决策均为
`skipped-existing-complete`；统一微信回执为 `state=blocked`、`sendAttempts=0`、
`items=[]`，失败阶段是 `preflight`，原因为 `wechat-main-window-count-not-one`。
当前 `desktop_input.py` 仅按 `AXTitle=微信` 和最小尺寸统计窗口，多个候选即
拒绝，因此未开始发送项目。

### 最小实现

- 抽取固定主窗口选择器：一个合格候选时沿用原路径；多个合格候选时，仅当其中
  恰有一个系统 AX `AXMain is True` 的候选，才绑定该窗口；AXMain 缺失、全假或
  多真均保持失败关闭。不得按列表顺序、几何位置或视觉猜测选窗。
- AX 应用代理初始化后即设置固定 3 秒 `AXUIElementSetMessagingTimeout`；AX
  查询超时不扩大窗口候选、不重试发送，按原有失败关闭处理，避免静默卡满业务
  截止时间。若系统 API 不可用或设置失败，不能声称 AX 查询已受限。
- `focus_chat_input()` 与 `activate_wechat()` 共用相同选择判据，避免焦点定位和
  激活绑定到不同窗口。后续仍必须通过固定群名/群类型与输入框空态校验；本变更
  不会关闭窗口、不切换账号/Profile、不放宽目标门禁。
- 离线测试覆盖单候选兼容、多个候选唯一 AXMain、AXMain 缺失/不唯一拒绝，并
  保持无障碍点击/发送不在选择器中发生；另断言 AX 通信超时设置固定且发生在
  读取窗口树之前。
- 只经统一微信依赖维护器同步 `desktop_input.py` 摘要、全量回归与完整性回读；
  再从日报已安装总入口重进。任何非唯一 AXMain 仍是安全阻断，不得猜选。

### 完成条件

上述测试与微信全量回归通过，依赖清单 clean，日报已安装入口 preflight 通过；
总入口回执满足当天业务完成合同与微信 verified 回读。若仍不能唯一绑定，保留
明确零发送收据，不执行第二条人工 UI 路径。

## 固化实现

### 2026-09-21 错误归因记录（已撤销，不实施）

#### 当时假设（非最终根因）

目标群的附件已被桌面客户端成功放入输入区，文件对象数为 1、发送按钮可用；但客户端将长文件名显示为“首段…尾段”。原发送器要求 OCR 命中完整的去扩展名文件名，因而把已就绪的预览错误判为未就绪，在写入发送标记之前停止。

#### 已撤销的临时方案

- 仅调整 `desktop_sender.py` 的**文件名可见性证据**：以不含省略号的固定首段和文件扩展名/日期尾段双锚点确认 UI 所示对象，不接受只命中其中一端的结果。
- 原有的目标群精确匹配、输入框初始为空、文件剪贴板 URL 类型回读、文件对象数、像素变化阈值、单次发送标记和发送后双帧回读保持不变。
- 补充单元测试：长文件名被省略时可通过首尾双锚点；相同首段或相同尾段的错误文件均被拒绝。
- 修改后只通过受控依赖维护器更新摘要、运行全量离线测试与入口完整性回读；然后对本次唯一附件重新登记策略、精确预检，并只允许一次发送。

#### 停止条件

全量测试与依赖回读通过，目标群预检再次确认空输入框；发送回执必须为 `verified` 且证据为完整文件名、大小、两帧位置稳定。任一环节失败均不发送或重发。

### 统一微信依赖维护器

本次授权只增加淘宝和美团各一个独立 correction-v1 事件身份及其严格来源校验，不修改既有标准事件、回执、发送结果或固定桌面发送实现。桥接器仍对路径和依赖摘要失败关闭；按统一依赖维护器更新当前代码摘要并保留维护收据。校正事件仅在标准事件已验证、原始发送至少一次、同群同文件名和固定文件路径、且正确文件哈希确有变化时进入现有发送链路；验证后重复调用复用校正回执，内容不同冲突，attempted/unknown 只对账不重发。禁止文件选择器与备用发送方式。

- 仅更新已登记依赖的当前摘要，并把维护器自身纳入清单；使用临时文件、`fsync` 和原子替换。

#### 已登记维护文件的封板基线兼容

维护器自身及统一依赖维护器可能已由早期封板写入运行文件清单。基线校验同时接受“这两个标签尚未登记”和“这两个标签已登记”两种形态；两种形态之外的新增、缺失或未知标签均拒绝。已登记时仍逐项校验绝对路径、文件存在性、摘要、原封板验收和共享文字验收，不能借此放宽任何其他漂移。

当本次已授权维护只修正维护器自身的门禁兼容缺口时，旧封板中 `maintenance_executor` 的摘要可由同一维护入口接纳并在完整回归后写入验收态。该窄例外不适用于任何发送器、采集器或共享桌面文件；它们仍须保持原摘要，或仅按已登记的统一微信依赖摘要处理。

### 封板门禁扩展

`executor_integrity.py` 将两个维护入口纳入 `RUNTIME_FILES`，并在验收态验证维护收据的路径、SHA-256、授权、状态、零外部发送和运行时模型决策为 0。真实非空生产发送成功后仍只由现有 `seal_from_nonempty_acceptance` 自动恢复 SEALED。
