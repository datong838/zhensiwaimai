# Top10 微信通道默认桌面化方案（2026-09-10）

## 目标

在浏览器后台采集保持不变的前提下，将发送通道固定为“桌面微信优先”：用户只说“开始”时使用已登录的 Mac 桌面微信；桌面微信未运行、未登录或目标群不能唯一确认时暂停等待人工登录，不自动降级到手机。只有用户明确要求“用手机微信”时才连接手机。

## 最小改动

1. `workflow_executor.py` 的 `--wechat-channel` 默认值由 `mobile` 改为 `desktop`。
2. 桌面通道在浏览器下载前先执行只读群定位，验证微信已运行、已登录且唯一目标群可达；失败立即结束，不生成新截图、不探测手机。
3. 桌面通道调用既有 `wechat-desktop-control/scripts/desktop_sender.py`，继续共用业务日期防重账本、唯一目标群、单图哈希、一次发送与发送后双帧复核。
4. 手机执行器及手机参数保持原样，只在显式 `--wechat-channel mobile --transport-file <私有文件>` 时调用。
5. 收据按实际通道写入 `desktopWechat` 或 `phone`，同时写通用 `delivery` 字段；失败原因使用 `desktop-wechat:` 或 `mobile-wechat:` 前缀。

## 停止与重试

- 桌面微信登录门禁失败：暂停等待用户登录，不启动手机、不自动重试发送。
- attempted 标记已存在或发送结果 unknown：任何通道都不得补发。
- 只有发送次数为 0 且账本无当日标记，才允许修复确定性前置问题后完整重跑。
- 正常路径 `runtimeModelDecisions=0`；模型只在失败复盘和代码优化阶段介入，并登记到考核记录。

## 验收

1. 不传 `--wechat-channel` 时收据显示 `wechatChannel=desktop`，且不需要手机连接文件。
2. 桌面微信未登录时在浏览器采集前停止。
3. 已登录时完成：后台首页 → 门店分析 → 昨日 Top10 → 原图 → 唯一群 → 单次发送 → 双帧复核。
4. 手机拔线不影响桌面路径；显式 mobile 时仍执行原手机门禁。

## 首轮真机复盘

- 首轮总入口返回 `ok=true`、`sendAttempts=1`，但人工复核 `before-send.png`、`prepared.png` 和两帧 `after-send` 后确认输入框始终为空、群内无新增图片。三张后续截图相对发送前仅有 1,348 个像素变化，变化来自光标/滚动条而非载荷。
- 根因一：文件 alias 列表写入系统剪贴板后，当前 Mac 微信版本没有生成图片预览；执行器在没有验证 prepared 状态的情况下继续写 attempted 并按回车。
- 根因二：发送后仅用整窗截图哈希不同作为图片成功条件，光标闪烁或滚动条变化即可造成假阳性。
- 修复：单张 PNG 改写为原生 PNG 剪贴板；写 attempted 之前，输入区域必须相对发送前出现大面积内容变化。发送后要求输入区预览消失，同时聊天区相对发送前出现大面积新增内容，并连续两帧满足；小范围光标/滚动条变化一律不算成功。
- 原首轮账本不删除，改记 `no-effect-confirmed` 并保留原 runId、图片哈希和证据路径；复跑使用独立授权标识，避免覆盖审计链。
- 第二轮在新 prepared 门禁前停止，`sendAttempts=0`；PNG 剪贴板已包含多种系统图片类型，但输入区只变化 136 像素。随后用普通文字做不发送探针，同样只变化 136 像素且可恢复为 0，证明失效点是 AppleScript `System Events` 键盘事件未送入微信，而非图片格式或输入框坐标。
- 输入事件最小修复：复用现有 CGEvent 点击层，增加同级 CGEvent 键盘执行器，固定支持粘贴、回车、全选和删除；桌面发送器不再使用返回成功但无实际效果的 AppleScript keystroke。先通过文字粘贴并清空探针，再进行图片 prepared 门禁。
- 几何复核进一步确认真正根因：旧桌面控制器强制窗口为 1200×820 点，而当前主屏幕可用区域仅 1168×686 点；窗口截图仍可包含屏幕外输入栏，但按该截图坐标点击会落到 Dock，因而所有粘贴通道都无效。窗口规范化改为读取 `NSScreen.visibleFrame`，四周留边并把尺寸限制在当前可用区域内，之后才允许计算输入栏和发送按钮坐标。
- 几何修复后不发送文字探针通过：窗口为 1120×638 点，输入文字带来 9,111 个像素变化；全选删除后相对空输入框仅余 78 个光标像素，证明点击与 CGEvent 键盘通道均已命中微信输入框。

## 固化后的定位收口

- 桌面微信群定位从“近期会话前缀 + 历史聊天区偶然文字”收口为：完整群名搜索、结果区唯一精确匹配、顶部标题二次精确匹配。
- 当前群已打开时只以顶部完整标题作为快路径，不再依赖“视频号/时间海/吃过/鱼杂”等历史业务内容判断聊天区就绪。
- 搜索框输入统一使用已验证的 CGEvent 键盘层，先全选再粘贴完整群名；AppleScript keystroke 不再作为执行通道。
- 只看到微信进程但聊天主窗不在当前可见列表时，不再反复截图；唯一精确名为 `微信` 的主窗取消最小化并 AXRaise，仍不可见则暂停。允许微信内网页形成名为 `微信 (窗口)` 的伴随窗，但绝不选择或截图它；其他未知大副窗仍失败关闭。
- 强制搜索实操发现第一次点击只进入搜索模式、搜索框仍为占位态；固化为两段动作：进入搜索模式后重新截图和重新定位，第二次点击聚焦，随后才允许全选与粘贴。
- 复核确认搜索态被普通截图函数的再次激活/AXRaise 破坏，而不是固定独立窗口。最终收口改为：点击唯一搜索入口后使用不激活的主窗口区域截图，区域内二次定位和输入；选择结果后才恢复主窗口验证。`Cmd+F` 不作为正式定位入口。
- 最终强制搜索验收通过：查询框显示完整群名；“群聊”分区唯一精确候选被选中；“聊天记录”中包含同名文字的内容未被当成候选；进入后顶部标题精确复核为 `FEIBING NEO AI数字员工（18）`。该轮无图片准备、无账本、无发送。
- 收口后复验暴露两项新边界并已固化：一是微信同时打开“今日头条”网页伴随窗时，按最大面积取窗会误选网页，现已改为 AX 与截图都只精确命中名为 `微信` 的聊天主窗；二是当前搜索结果位于“最常使用”分区且纵坐标小于旧阈值，现改为按“群聊/最常使用”到“聊天记录/搜索网络结果”的语义分区取唯一精确群名，不再依赖固定纵坐标。
- 最终默认总入口不发送验收：`ok=true`、`wechatChannel=desktop`、桌面微信预检 3.789 秒、`sendAttempts=0`；说明在手机拔线、微信网页伴随窗存在的状态下，执行器仍能稳定完成精确群定位且不会产生发送副作用。

## 2026-09-11 窄屏窗口回归与定位修正

- 实操时微信主窗口被确定性规范化为 `1200×820` 像素图，目标群已打开且顶部标题 OCR 为完整 `FEIBING NEO AI数字员工（18）`，但旧执行器仍要求标题中心横坐标大于固定值 `700`，导致正确标题被误判为不存在；本轮在发送前关闭，`sendAttempts=0`。
- 顶部群标题改为响应式内容区定位：先根据当前 OCR 结果的最右边界推导内容区左界（窗口宽度约 27%，且不小于 300 像素），再要求候选位于顶部 120 像素内并完整精确匹配群名。这样同时排除左侧搜索框/近期会话，又兼容不同屏幕缩放和窗口宽度。
- 该规则必须写入共享桌面微信执行器并由窄屏、宽屏、左侧同名结果排除测试覆盖；只更新文档不算完成。
- 打开群预检、发送前、载荷预览后和发送后复核必须复用同一个 `find_exact_headers` 定位器；发送器不得复制另一套固定坐标过滤条件，否则窗口变化会造成预检通过而发送复核失败。
- 发送后输入区证据不得从窗口高度 74% 开始，因为新发图片气泡可能延伸到该区域并被误判为“预览未消失”。按当前微信 4.x 布局将输入证据区收口为底部 18%，同时每帧回读唯一 `AXTextArea` 的值为空；图片发送成功要求聊天区显著新增、输入区变化低于预览阶段且 AX 输入为空，连续两帧同时成立。
- 发送键触发后微信可能把 AX 焦点短暂移出输入框；每帧回读前允许最多两次“重新聚焦唯一大尺寸 `AXTextArea` → 回读为空”的确定性尝试。若仍失败则保持 unknown，不得重发。任何发送后异常都必须把完整 unknown 收据原子写回 attempted 标记，禁止账本永久停留在缺少发送证据的初始 attempted 快照。
- 详细状态机、后置条件、超时和失败关闭规则固化于 [确定性执行器合同](deterministic-executor-contract.md)。
