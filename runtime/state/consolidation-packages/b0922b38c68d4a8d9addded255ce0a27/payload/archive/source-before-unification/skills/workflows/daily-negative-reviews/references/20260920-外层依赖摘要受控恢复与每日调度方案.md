# 外层依赖摘要受控恢复与每日调度方案

## 背景

2026-09-20 的昨日差评分析已对业务日期 `2026-09-19` 形成 `complete`、微信核验通过的收据，并自动封板。随后公共微信 `dependencies.json` 发生受控同步，公共依赖维护器的只读 `inspect` 结果为 `clean`，但差评工作流自己的 `dependencies.json` 仍登记旧的公共清单摘要。因此差评总执行器在任何浏览器、下载、报表或微信动作前以 `dependency-hash-mismatch` 失败关闭。

## 目标与边界

- 恢复每日昨日差评分析在下一业务日的可执行性，并在成功后由既有总执行器自动重新封板。
- 新增的维护路径只可更新差评工作流对已登记公共清单的外层摘要，以及将本工作流从 `SEALED` 切换为一次性的 `UNSEALED_ACCEPTANCE`。
- 维护路径不得打开浏览器、下载数据、生成报表、调用微信桥、写发送账本或触发发送；结果必须显式为 `sendAttempts=0`、`runtimeModelDecisions=0`。
- 不修改固定日期计算、三平台采集、1 至 3 星口径、Excel 字段、固定群、发送幂等标记、微信验证或未知结果规则。
- 不允许手工编辑 `dependencies.json` 或 `runtime-policy.json` 完成恢复；写入必须临时文件加原子替换，任一前置校验或回读失败均保持原文件不变。

## 实现

1. 新增 `scripts/maintenance_executor.mjs`。入口只允许 `prepare-unsealed-acceptance` 和固定维护授权；校验当前策略为 `SEALED`、旧封板摘要存在、差评工作流本地受保护文件未漂移、公共微信依赖维护器 `inspect` 返回 `ok=true` 与 `status=clean`。
2. 维护器只更新差评依赖清单中两个已登记的公共微信共享文件：`dependencies.json` 与 `workflow_bridge.py`。两者都必须已在公共微信自己的依赖清单中以当前 SHA-256 精确登记；除此之外的任何共享或本地漂移仍失败关闭。随后运行差评的全部离线测试与总执行器 `--self-test`，并回读摘要一致性。
3. 通过后原子写入 `UNSEALED_ACCEPTANCE` 策略，其中候选摘要优先绑定当前尚未完成的按 `Asia/Shanghai` 自动计算业务日期。若心跳已越过 09:00 才进入维护，仍必须补齐该当前业务日，不能错误绑定为明日。仅当当前业务日不存在运行状态、原验收态错误地指向未来业务日时，才允许零发送重新绑定；已存在运行状态、历史业务日或任意 `attempted/unknown` 都拒绝。维护收据记录前后摘要、测试、耗时和零发送证明。
4. 既有 `workflow_executor.mjs --execute` 保持唯一生产入口。它仅能在绑定业务日继续，完整真实运行成功后调用已有封板逻辑恢复 `SEALED`；出现 `attempted`、`unknown` 仍仅对账，禁止重发。
5. 调度只在维护成功且无副作用自检通过后建立：上海时区每日 09:00，提示只调用唯一总执行器；依赖摘要错误时按固定维护入口恢复并复跑，不能临场拆分阶段或构造发送参数。

## 验收与停止规则

- 新增单元测试覆盖：错误动作/授权/封板状态拒绝，公共清单不 clean 拒绝，未知本地漂移拒绝，09:00 后仍绑定当前待执行业务日，错误指向未来且无运行状态时才可重新绑定，成功仅进入验收态、摘要回读一致且 `sendAttempts=0`。
- 差评既有离线测试与 `--self-test` 必须全部通过；微信公共 `inspect` 必须保持 clean。
- 维护完成后不在当前已完成业务日重新执行发送；仅由下一次每日 09:00 的唯一总执行器处理新的昨日业务日。
- 若当前已绑定业务日仍为 `created/recoverable`，且已由代码证明没有下载点击、成品、发送收据、`attempted` 或 `unknown`，受控维护可登记本轮已方案化的采集器修复并从原状态恢复。该窄例外不适用于 `downloaded` 及以后阶段，也不适用于任何发送事实。
- 若登录、验证码、滑块或账号风险页出现，由总执行器记录阻断并等待用户处理；其他内部故障按既有受控恢复规则处理。

## 2026-09-30 新增「零发送 · 驱动拒绝」可恢复形态

### 背景与证据

- 昨日差评分析业务日 `2026-09-29` 的运行已完成采集、报表生成（`phase=report_built`），仅在 `wechat_send` 阶段被 Windows 驱动以业务拒绝方式挡回，状态 `blocked`。
- 发送收据 `/Users/ddt/work/projects/ai_agent/.local/runs/daily-negative-reviews/20260929/wechat-send/receipt.json` 明确：`ok=false`、`state=blocked`、`verified=false`、`sendAttempts=0`、`newSendAttempts=0`、`attempted` 缺省、`unknown` 缺省，`reason=windows-send-rejected:HTTP 500: {"ok": false, "error": "打开会话失败，当前标题='文件传输助手'，目标='上海臻肆外卖运营-盯个盯-饭敢当 💰发财精英荟💰'"}`。
- `windows_adapter.py` 的 `send_one` 对以 `HTTP ` 开头的**服务端业务拒绝**（即服务端已应答、什么都没发出）显式按「重试后仍失败则 `blocked, sendAttempts=0`」处理（见 `scripts/windows_adapter.py` 注释 “Deterministic server business error (HTTP status returned) -> blocked, sendAttempts 0”）。因此该形态与既有的 `No module named 'AppKit'` 运行时阻断同属**已证明零发送**。

### 缺口

- 受控维护器的验收态判定链只承认四种既有形态：无状态前置效应、`created` 前置效应、可复用下载、`exact-group-result-count:0` 预检阻断、`No module named 'AppKit'` 运行时阻断。
- 本形态（`report_built` + 驱动业务拒绝 + 零发送）不在其中，维护器以 `release-policy-not-maintainable` 拒绝，导致**外层依赖摘要无法通过受控路径刷新**，工作流被永久挡在 `dependency-hash-mismatch` 上。

### 方案（最小改动 + 测试先行）

1. 在 `scripts/maintenance_executor.mjs` 增加 `isZeroSendWechatDriverBlocked(state, receipt)`，判定条件与既有运行时阻断**逐项同强度**：`state.phase==='report_built'`、`state.status==='recoverable'`、`receipt.state==='blocked'`、`receipt.verified===false`、`receipt.sendAttempts===0`、`receipt.newSendAttempts===0`、`receipt.attempted!==true`、`receipt.unknown!==true`，且 `receipt.reason` 为字符串并以 `windows-send-rejected:` 开头。
2. 在验收态判定链末端追加该形态：前四级依次失败后，末级先试既有运行时阻断，再试本形态；仍失败才抛 `release-policy-not-maintainable`。
3. 该文件本已在 `CODE_REPAIRABLE_FILES` 内，`assertLocalIntegrity(..., {allowCodeRepair:true})` 允许其自身摘要随本次修复重绑，无需放宽任何其它安全门。
4. 新增单元测试覆盖：正例为真；`sendAttempts=1`、`attempted=true`、`state='unknown'`、`reason` 非 `windows-send-rejected:` 前缀四种反例均为假。
5. **不动**：固定日期计算、三平台采集、1–3 星口径、Excel 字段、固定群、发送幂等标记、微信验证、未知结果规则、`EXTERNAL_EFFECT` fail-closed 与防重账本。

### 放行条件

- 差评既有离线测试与 `--self-test` 全部通过；公共微信 `inspect` 保持 `clean`。
- 维护收据必须显式 `sendAttempts=0`、`runtimeModelDecisions=0`。
- 维护完成后仅复跑**同一业务日** `2026-09-29` 的总执行器；该次发送仍是首发改次真实发送（此前零发送），因此**允许且必须**完成一次真实投递；任何 `attempted`/`unknown` 仍只读对账、禁止重发。
