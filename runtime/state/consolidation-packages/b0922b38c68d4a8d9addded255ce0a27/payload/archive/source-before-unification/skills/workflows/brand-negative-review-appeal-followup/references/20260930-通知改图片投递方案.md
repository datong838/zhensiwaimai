## 1. 为什么是图片

Windows 驱动的发送路径是**逐字键盘注入**（`edit.SendKeys(text)`），`\n` 是控制字符敲不进去 → 群内消息被压成一长行（D16）。驱动源码只在 Windows 机、Mac 无写入口，所以走 Mac 侧改投递形态：

| 方案 | 换行 | 版式 | 可复制/可搜索 | 部署 |
|---|---|---|---|---|
| 现状（文本） | ❌ 丢 | ❌ | ✅ | — |
| 改 Windows 驱动 | ✅ | ✅ | ✅ | 需 Windows 侧改代码 |
| **改发图片（本方案）** | ✅ | ✅ | ❌ 群成员不能复制、微信搜不到 | **Mac 侧即可，零 Windows 依赖** |

图片版式的权威正文仍完整留在 `outputs/{业务日}差评申诉跟进.csv` 的「通知正文」列与冻结请求里，**系统台账不丢文本**。

## 4. 改动清单（Mac 侧，3 个文件 + 1 个新文件）

### 4.1 新增 `scripts/render_notice.py`（渲染器）
- `render(text) -> bytes`：纯函数，无时间/随机/环境依赖，字节确定。
- `NOTICE_STYLE`：把 §3 的常量集中一处，便于审阅与冻结。
- 字体按 **sha256 锁定**（渲染前校验字体字节摘要，不符即 fail-closed），避免系统升级换字体导致指纹无声漂移。

### 4.2 新增 `scripts/render_manifest.py`（身份台账）★ 关键设计
图片条目的「身份」不能再用正文 sha256（`normalize` 对非文本类型记的是**文件摘要**）。因此新增一份渲染台账：

```
.runtime/render/{业务日}/index.json
  { "记录键": {"path": "...png", "sha256": "...", "bytes": N,
               "styleSha256": "...", "fontSha256": "...", "renderedAtUtc": "..."} }
```

- `prepare_delivery` 冻结前生成（幂等：已存在且 sha256 一致则复用，不重渲染）。
- **为什么需要它**：校验时读台账拿原始摘要，而不是「现场重渲染」。否则一旦日后调整渲染样式，历史待核项会因摘要变化被误判成「载荷被篡改」，触发 `ledger-payload-digest-conflict` 假报警。
- 找不到台账条目时**回退现场重渲染**，仍拿不到则 fail-closed（不猜）。

### 4.3 改 `scripts/prepare_delivery.py`
- 冻结条目由 `{"type":"text","text":...}` 改为 `{"type":"image","path":"...png"}`；PNG 落在 `.runtime/render/{业务日}/{记录键}.png`（**文件名确定**，因为 `content_binding` 会把 `name` 计入指纹）。
- `delivery_state()` 的载荷校验：`expected_sha` 由「正文 sha256」改为「该行的图片摘要」（台账优先，缺失则重渲染）。**校验强度不变**——仍是字节级精确比对，只是比对对象从文本变成图片。
- `_load_human_audit()` 的可接受摘要集合改为 `{正文sha256, 图片sha256}` ⇒ **向后兼容** 2026-09-26 那条已存的文本审计，不需要重签。
- 逐品牌群映射、授权、deadline、事件 id 生成规则**全部不动**。

### 4.4 【建议同批】改 `skills/wechat-messaging/scripts/windows_adapter.py`：图片/文件回读加「尾部基线 diff」
**这是必说的一个风险**：非文本条目的回读锚点是 `[图片]` / `[文件]` 标记，而这类标记**不唯一**。现有规则只要求「标记处于尾部且其后只有时间戳」——如果群里**本来就有一条图片是最后一条**，那即使这次其实没发出去，也会被判 `verified`（**误报已送达**，是 fail-open 方向的问题）。

修法（小、局部）：`send_one` 在**发送前**记一次当前会话的尾部快照；`_verify_sent` 要求标记位置**越过**基线（即确实多出一条），把「标记在尾部」升级为「标记**新增**在尾部」。

- 收益：⑦⑥⑨ 及所有文件/图片投递一起加固。
- 代价：`windows_adapter.py` 又要走一次受控再封印（今天已走两次，流程熟）。
- 若不接受，则本方案降级为「以 `reconcile` 的字节绑定为权威证据」——`reconcile` 已经强绑定 `payloads[0].sha256 == item.sha256`，但发送当次仍可能误报 `verified`。
