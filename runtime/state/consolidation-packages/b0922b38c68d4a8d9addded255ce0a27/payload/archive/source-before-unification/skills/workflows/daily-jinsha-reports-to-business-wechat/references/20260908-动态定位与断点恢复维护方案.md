# 动态定位与断点恢复维护方案

## 背景

2026-09-08 真实业务群日报实操中，金鲨窗口尺寸与前一轮校准不同。淘宝方案已经正确加载为 34 项，但执行器继续使用旧的绝对像素坐标，未能完成 `34 → 35 → 36`，导致首轮在淘宝指标节点停止。手机阶段随后暴露两个独立问题：业务群 OCR 中 `AI` 被识别为 `Al` 时，稳定定位器仍调用未归一化的通用匹配器；定位失败后的断点再次执行时，搜索页被归类为未知遮挡页，不能自行回到安全的定位动作。

## 目标

在不修改隐藏内部底座 `.daily-jinsha-reports-core` 封板文件的前提下，为真实业务群包装层补充：

1. 不接受调用者传入的淘宝指标绝对坐标。
2. 每次运行从金鲨实时截图读取坐标系尺寸，用经过验证的归一化锚点计算本次点击位置。
3. 只在淘宝平台、精确方案、昨日日期及 `已选择 (34)` 同时成立时生成指标点击目标；每次点击后仍由封板执行器验证 `35` 和 `36`。
4. 截图尺寸、宽高比或目标落点超出已验证范围时失败关闭，不尝试猜点。
5. 业务群定位器独立执行空格与 `Al数字员工 → AI数字员工` 归一化，要求唯一结果连续两帧稳定且页面不再显示“加载中”。
6. 上一次在群定位阶段零发送失败后，若当前仍为微信搜索页且精确业务群唯一，则将页面路由回安全的 `locate` 动作；不放宽任何已发送或发送结果未知场景。

## 实现

### 金鲨

- 新增 `scripts/business_jinsha_cua_exam.mjs`，动态加载内部封板 `runJinshaCuaExam`。
- 预检读取 `getAXState()` 与 `getScreenshot()`；JPEG 尺寸直接从截图字节解析，不读取旧窗口配置。
- 以 2026-09-08 CUA 实测的 1168×686 窗口截图坐标系为参考，保存无量纲锚点比例而非绝对像素。
- 截图前后分别读取页面状态；任一帧不是精确下载页，说明用户或页面在预检中发生切换，立即停止。
- 计算结果必须位于方案指标区域的安全范围；业务配置若仍提供 `metrics` 字段则拒绝，防止旧裸坐标悄然回流。
- 动态定位只负责计算目标，下载次数、日期、方案、计数变化和失败关闭继续由封板执行器负责。

### 微信

- 稳定定位器不再调用通用 `helpers.exact_group_title`，改用业务群精确归一化匹配。
- OCR 坐标已实证为文字框中心点，点击仍使用最新帧中心；只有无“加载中”的连续两帧才允许点击。
- 业务发送包装器识别 `FTSMainUI` 中的唯一精确群结果，并将无发送记录的失败断点恢复为 `home → locate`。已有 `in-flight` 或 `confirmed` 状态仍沿用封板逻辑，禁止重新发送。

## 验收

1. 1168×686 实际窗口截图计算出本轮已验证目标 `(638,386)`、`(808,386)`，但调用配置中不再出现这两组裸坐标。
2. 至少两个不同尺寸的模拟截图均按比例得到不同像素目标；非法尺寸、错误页面、非 34 项状态均失败关闭。
3. `FEIBING NEO Al数字员工（18）` 可精确归一化匹配；相似群名、临时群、缺字群均不匹配。
4. 微信搜索页仅在目标群唯一且无发送状态时路由回定位；不能改变未知发送结果的只读复验规则。
5. 原封板哈希保持不变；业务 Skill 快速校验通过。
6. 旧流程目录迁入隐藏内部底座，唯一可发现入口为 `daily-jinsha-reports-to-business-wechat`。

## 后续考核

本次维护只做无副作用测试。下一次完整真机考核必须重新从金鲨下载开始，以节点耗时、下载次数、发送次数和最终只读复验作为验收证据。
