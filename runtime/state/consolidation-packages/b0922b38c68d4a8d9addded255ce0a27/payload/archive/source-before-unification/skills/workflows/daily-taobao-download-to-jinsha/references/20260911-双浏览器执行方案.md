# 淘宝昨日数据上传金鲨：双浏览器执行方案

## 总原则：门禁必须被解决，任务必须被完成

本流程的第一结果是每天完成下载、去重上传、证据生成和微信交付。门禁、代码漂移和环境异常是需要被诊断并修复的问题，不是数字员工可以据此结束工作的完成态。只要代码证据证明尚未产生外部效果，就必须按“方案补充 → 最小修复 → 离线回归 → 固定入口预检 → 同一总入口继续”的闭环推进，直到完成合同通过。

“必须完成”不授权绕过安全边界：若上传或发送已经进入 `attempted`/`unknown`，必须先通过代码化只读对账确认结果，绝不盲目重复外部动作；不得临时猜测页面定位、切换 Profile/通道或直接调用下层发送器。已经验证的关键定位、恢复逻辑和稳定流程必须写入执行器及测试，MD 只说明原则，运行许可仍由代码决定。

- 不创建/关闭页面，不切换 Profile/端口/通道，不读取或注入凭据，不改变下载、上传、去重、截图、微信、防重或完成合同。

  `unmatched`，提示先查方案/历史成功回执、形成新方案并增加自测，不提供猜测性
  恢复动作。
- `runScheduled()` 在 workflow、sender 或总入口失败结果中附上原样输入摘要对应的
  `experienceReview`，让每次维护从已验证案例开始，而不是先由模型自由推断。
  该字段不改变既有 `controlDecision`、防重或重试权限。
- `preflight()` 必须逐字节核对项目与安装版 `entrypoint.mjs`，并执行经验案例
  索引自测。入口不同步、案例自测未覆盖、经验案例重复/模糊时，在任何业务动作
  之前拒绝运行。
- 每条新增经验必须有真实历史依据或明确标记为“候选未验证”、正反测试和代码
  哈希；不得将一次成功结果反推成未观察到的恢复分支成功。用户要求的历史先查
  因此落为代码产出的第一项诊断结果，而非只写成 MD 提示。

## 持久执行与可验证复盘

- 单节点超时只结束该节点，不等于放弃每日流程。执行器必须先写失败收据；模型只根据收据中的阶段、页面诊断、点击次数和恢复次数分析。确认尚未发生未知外部动作后，才能修改并自测固定执行器，再从安全节点续跑；上传结果未知禁止重试。
- 淘宝两份下载已经明确成功而金鲨尚未发生上传点击时，后续零参数生产调用必须优先按上述安全失败收据续跑，不得再次点击淘宝下载。续跑前对两份文件和原收据做全量复算；不满足即拒绝续跑并重新走普通入口，不把未验证文件带入金鲨。
- 收据必须包含逐节点 `stageMs`、总耗时、恢复次数、`pitfalls`、失败页 URL/框架摘要、点击次数与 `cleanupStatus`。清理标签和连接也有固定硬超时；先写 `cleanupStatus=pending` 收据，再清理并覆写最终状态，避免清理挂起导致无收据。
- 执行器在最终写收据前必须由代码生成 `runReview`：`stageMs` 中每一项恰好对应一行，包含固定中文节点名、耗时、状态和该节点踩坑列表；清理警告也必须归入清理节点。`reviewSummary` 记录总耗时、节点数、踩坑数和策略版本。漏项、重复项、负耗时、未归属踩坑或策略版本不一致时，复盘合同失败，收据不得标记成功。
- 自动化和模型只能逐行展示 `runReview` 及收据字段，不能新增、删除、合并节点，不能把文档文字解释成继续许可。页面是否允许继续、恢复还是停止，只认执行器代码返回的阶段与门禁结果。
- 无人值守任务的“生产成功后才发送微信”条件也由 `runScheduled()` 强制编排：生产收据未通过完成合同则不加载发送动作；通过后只调用固定长期授权发送入口一次，并把 `runReview`、`sendReview` 和两个原始收据一起返回。自动化不得自行串联 `run()` 与发送函数。
- 只有已验证的定位、恢复与顺序实际写入 `background_browser_executor.mjs`，并由自测或真实回执覆盖，才算固化；仅修改本方案或复盘文字不算完成。
- 微信使用独立防重账本。桌面微信发送器必须标记 `locate_group`、`verify_target_and_input`、`prepare_payload`、`claim_and_send`、`post_send_verify` 阶段。只有 `sendAttempts=0` 且仍处于前两个发送前阶段时，资源被其他任务占用才允许按固定退避等待并重试获取；进入 `prepare_payload` 后不得整轮重跑，一旦发送结果未知更不得补发。
- 微信发送器也必须由代码生成 `sendReview` 与 `reviewSummary`，逐项覆盖已进入的发送阶段、耗时、状态和失败原因；发送账本与最终收据写入同一复盘。模型只负责展示，不得自行判断发送是否成功或是否可补发。
- 发送器在 `verify_target_and_input` 读取输入框时，只能把全空白字符残留规范化为空串并立即回读；出现任意非空白字符或无法回读仍以 `desktop-chat-input-not-empty` 失败关闭，不覆盖用户草稿。

## 运行入口与安装同步

本方案生效后，项目 Skill、安装到 `~/.codex/skills` 的同名 Skill、安装入口和每日 15:00 定时任务必须共同指向 `scripts/background_browser_executor.mjs`，不得继续把 `cua_sequence_executor.mjs` 描述或调用为生产入口。

- 安装入口只做依赖、哈希、自测和固定函数分派，然后动态导入项目内后台执行器；生产与两种验收模式均没有运行参数。
- 安装入口在任何业务动作前比较项目 Skill 与已安装 Skill 的 SHA-256；不一致时以 `installed-skill-drift` 失败关闭，禁止按旧规则继续运行。
