## 2. 为什么这是结构性改动（不是改一行）

「恰好两张图」是写死在 4 个层面、互相咬合的不变量：

| 层 | 文件 | 硬约束 |
|---|---|---|
| 发送器 | `daily-taobao-download-to-jinsha/scripts/desktop_wechat_evidence_sender.mjs` | `images.length !== 2` 即抛错；文件名/顺序固定；**授权挑战 = 双图名+双 sha 拼串**；marker 键 = sha(群名\n业务日\nsha_store\nsha_review) |
| 桥（封印内） | `wechat-messaging/scripts/workflow_bridge.py` REGISTRY | `'taobao-evidence'` 期望 payload 数 = **2**，发 1 张会被拒 |
| 恢复门 | `daily-taobao-download-to-jinsha/scripts/scheduled_evidence_recovery.mjs` | IMAGE_NAMES 成对、marker.payloads=2、manifest.images=2、verified 收据 items=2、blocked items=0 —— 五处 |
| 回归测试 | `test_scheduled_evidence_recovery.mjs`、`test_entrypoint_contract.mjs` | 断言全部按「成对」写 |

**关键事实**：每次重跑都重新截图 → sha 必变 → marker 键必变 → 系统内**不存在**「哪张已发过」的逐图状态。重复的根源不是发送逻辑，而是「逐图交付状态」这个概念在当前体系里不存在。
