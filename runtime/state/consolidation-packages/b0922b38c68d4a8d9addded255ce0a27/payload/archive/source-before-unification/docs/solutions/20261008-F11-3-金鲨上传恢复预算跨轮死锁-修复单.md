## 1. 现象

20:37 轮起，流程稳定失败于：

```
recovery-budget-exhausted:jinshaLogReload
```

关键旁证：`knownPopupCloseAttempts: 0` —— 全程**没有遇到任何弹窗**。
此前怀疑的「金鲨 V5.6 公告弹窗遮挡」方向被回执证伪，真正的阻塞在恢复预算。

失败时流程停在 `waitForCompletedLog`：金鲨上传日志当天为「暂无数据 共 0 条」（合法未上传态），
首读不到 → 申请 `jinshaLogReload` 恢复（budget=1）→ reload 后仍读不到 → 预算耗尽抛错，
**根本走不到 `input.setInputFiles` 上传那一步**。

## 2. 根因（跨轮 resume 的预算继承）

`background_browser_executor.mjs` 从上一轮失败回执 resume 时，构造本轮回执的恢复预算：

```js
recoveryAttempts: {
  ...resumeReceipt.recoveryAttempts,                              // ← 问题所在
  productionResume: resumeReceipt.recoveryAttempts?.productionResume || 0,
  ...
}
```

两个语义被混在了一起：

| 语义 | 载体 | 生命周期 |
|---|---|---|
| 单轮内恢复次数 | `currentAttemptRecovery` | **每轮归零** |
| 跨轮代数计数 | `productionResume` | 跨轮继承 |

后果链：

1. 上一轮把 `jinshaLogReload` 用到 1（budget=1，已耗尽）；
2. 本轮 resume 时 `...recoveryAttempts` 把 **1 整体继承回来**；
3. 而本轮守卫（`isSafeProductionResumeReceipt` 等）读的是**已归零**的 `currentAttemptRecovery`，于是放行；
4. 一放行，`claimRecovery('jinshaLogReload')` 立刻 `used(1) >= budget(1)` → 抛 `recovery-budget-exhausted`；
5. 当天每一轮都重复 2→4，**零产出、零自愈**。

## 3. 修复

只保留**跨轮代数** `productionResume` 的继承，其余恢复预算回归「单轮内」语义、与已归零的 `currentAttemptRecovery` 对齐：

```js
recoveryAttempts: {
  // 2026-10-08 F11-3：原此处有 `...resumeReceipt.recoveryAttempts`，会把上一轮**已耗尽**
  // 的恢复预算（如 jinshaLogReload:1，其 budget=1）整体继承回来，而本轮守卫读的是已归零的
  // currentAttemptRecovery ⇒ 放行后 claimRecovery 立刻 used>=budget 抛
  // recovery-budget-exhausted:jinshaLogReload，连上传都没走到，且当天每轮复现、零产出不可自愈。
  // 其余恢复预算本就是「单轮内」语义，应与已归零的 currentAttemptRecovery 对齐（不继承）。
  // 只保留跨轮代数计数 productionResume 的继承。
  productionResume: resumeReceipt.recoveryAttempts?.productionResume || 0,
  ...
}
```

- 改动位置：`skills/workflows/daily-taobao-download-to-jinsha/scripts/background_browser_executor.mjs`（L1298-1307）
- 改动量：**1 处**（全量 diff 仅此一处）
- 备份：`background_browser_executor.mjs.bak-20261008-2055`

## 7. 教训

- **★ 恢复预算要分清「单轮内」与「跨轮」两种语义**，混在一起就会产生「守卫放行、执行立刻耗尽」的死锁：看起来每轮都在重试，实际每轮都走不到业务动作。
- **★★ 改被摘要钉住的执行器前，先查有没有 hash/封印校验**（本次先改后撞 `executor-code-drift`，白跑一轮）。三处收口：执行器 + 摘要钉 + 已安装副本。
- **★★ 定性以现场工件为准**：`knownPopupCloseAttempts: 0` 直接否掉了弹窗方向；不要沿用上一轮的假设。
