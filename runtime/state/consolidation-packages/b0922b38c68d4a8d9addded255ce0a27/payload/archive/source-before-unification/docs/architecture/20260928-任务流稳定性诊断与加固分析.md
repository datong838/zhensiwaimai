# zhensi_waimai 任务流稳定性诊断与加固分析（只读）

> 分析时间：2026-09-28　|　方式：只读核查（未改任何代码）
> 目的：回答"为什么 skill 任务流工作很久了、执行还是不稳定、各种事情中断"，并给出如何让它顺畅跑起来的方向。
> 参照经验：近期在 MediaCrawler / Easel / 副业盯盘 Windows 迁移中踩过的"长任务断流 / 资源争用 / 临时态脆弱 / 授权过期"等坑。

---

## 一句话结论

项目**不是被 bug 拖垮，而是被"以 cron 心态跑长任务 + 共享 Mac/单手机 + 把瞬时 UI 抖动当永久失败反复重试"这三件事拖垮**。安全边界（fail-closed、ActionResult 收据、EXTERNAL_EFFECT 授权）设计得很好，要保留；出问题的是**调度形态、失败分类、资源独占、授权续期、会话保活**这五处工程化缺口。

## 二、为什么会"各种事情中断"——六类根因（按杠杆排序）

### 根因 1：被当 cron 跑的长任务，会话一断就废（最致命）
任务需要**长时间持有**真机 ADB 会话、桌面微信 AX 会话、浏览器 CUA 会话。但触发方式是一个"每小时外部 heartbeat"派生**全新进程**去跑，每次都是冷启动重新建会话。会话在两次触发之间或中途被杀，UI 一抖就废。
> 同我踩的坑：ollama 拉模型是服务端发起、**客户端断开即停**；必须有一个"持有客户端的后台进程"常驻。这里缺的正是这个"持有会话的常驻守护"。

### 根因 2：瞬时抖动被当永久失败 → 无限续跑（thrashing）
AppleScript 激活/AX 读取用了**无超时的 `subprocess.run`**，窗口尺寸、截图、激活任何一个瞬时失败，状态机就复跑；同一 UI 态反复复跑 4 次仍失败（plan-2026-09-19 记录），**无收敛**。
> `preflight` 跑满 60022ms 超时（deadline-expired）、`wechat-window-capture-failed`、窗口恢复连续卡 4 次——都是"抖动被当失败"的连锁。

### 根因 3：单 Mac + 单手机 + 多技能 资源争用
桌面微信、浏览器 CUA、OCR 全挤在一台 Mac；微信锁 `contentionRetries=63`、等待 313894ms（≈5 分钟）仍拿不到锁。同一台手机还要被多个业务抢。
> 同我踩的坑：副业盯盘因 Mac 内存紧、把整套运行时迁到**专用 Windows 机**（正交分工、各司其职）。这里缺的是"执行槽位串行化 / 机器独占"。

### 根因 4：Mac 睡眠 / ADB 掉线 / 无超时调用 级联
Mac 睡眠会掐断 ADB 与桌面微信会话；`subprocess.run` 无超时让控制调用挂起后级联超时。这跟"caffeinate 防睡"那课直接相关。

### 根因 5：授权/封板过期单点
`runtime-policy.json.expiresAt` 与 `executor-lock.json` 的 `UNSEALED_ACCEPTANCE` 任一过期 → 整条发送链 fail-closed，需**人工重新盖章续期**。几天一次，正好对应"工作很久、时不时中断"。
> 同我踩的坑：automation 的 `validUntil` 过期会静默让任务停摆；必须显式续期或提前告警，不能靠"记得"。

### 根因 6：恢复机制覆盖面窄
`heartbeat_recovery.py` 的 `RECOVERABLE_CODE_FAILURE` **只匹配代码类**（依赖漂移/ImportError…），对窗口尺寸、截图、激活、锁争用等**环境故障根本不真修复**，只是 fail-closed 反复复跑——等于把环境抖动全甩给人工。

## 三、对照我近期踩的坑：可复用的通用规律

| 我踩过的坑（MediaCrawler/Easel/Windows迁移） | 在 zhensi_waimai 的对应表现 |
|---|---|
| ollama 客户端断开即停 → 需常驻进程持有会话 | 长任务被当 cron，会话冷启动+中途掉 |
| Mac 睡眠断流 → `caffeinate -is` 防睡 | 真机/桌面微信会话被睡眠/掉线掐断 |
| `/tmp` 临时脚本重启即丢 → 纳入版本管理 | `.runtime/*.lock`、acceptance receipt 可能残留/过期 |
| 内存紧逼出 swap → 专用机器正交分工 | 单 Mac 跑微信+浏览器+OCR 争用，锁等 5 分钟 |
| `validUntil` 静默过期 → 显式续期+告警 | `runtime-policy.json.expiresAt` 过期整链停 |
| "假设成功"翻车 → 以真实验收证据为准 | 已有 ActionResult 收据（好），但状态机未按"瞬态/永久"分类 |

## 四、加固建议（按杠杆排序，均不改现有安全设计）

### ★ 最高杠杆：把"触发-冷启动"改成"常驻守护 + 请求"
- 用一个 **launchd KeepAlive 守护进程**（类比 Easel gateway）持有真机/桌面微信/浏览器会话常驻；每小时 heartbeat 只向守护**发一个执行请求**，守护在已有会话上续跑，而不是每次新建进程。
- 直接消除根因 1、4 的大部分。

### ★ 失败分类器 + 抖动预算（治 thrashing）
- 把失败明确分成 **瞬态**（窗口尺寸/截图/激活/锁等待/网络抖动，带超时）与 **永久**（包名错、授权过期、资源缺失）。
- 瞬态失败给**有限重试预算 + 冷却（如连错 3 次或 5 分钟内不再派生新 run）**；永久失败直接 fail-closed 报警，不要派生续跑 run。
- 把 `subprocess.run` 全加上**显式超时**（09-27 方案已提，未全落地）——这是根因 2 的直接解。

### ★ 执行槽位串行化 / 机器独占（治争用）
- 桌面微信、浏览器 CUA、OCR 不要同 Mac 并发；用**单一会话调度器**保证同一时刻只有一个人拿 `wechat-ui-interaction.lock`。
- 长期：参考副业项目，把重负载（浏览器 CUA/OCR）挪到专用机，手机控制与微信控制留在 Mac，按"正交分工"不重叠。

### ★ 授权/封板自动化续期 + 到期告警
- `runtime-policy.json.expiresAt` 与 `executor-lock.json` 的 `UNSEALED_ACCEPTANCE` 加**到期前 N 小时告警**；能自动续的自动续，不能的提前提示人工盖章，别等过期停摆才被发现。

### ★ Preflight 硬门 + 短回路
- 已有 preflight 很好，但要做成**硬门**：preflight 不通过就**立即短路返回**（不进 60s 的发送流程再 skip），减少无效 run。

### ★ 步骤级 checkpoint（而非整 run 级）
- 已有 `resume_flow.py`，需确认它是**步骤粒度**回放（断在发第 3 条就从第 3 条续）而非整 run 重跑；否则掉一次线前功尽弃。

### ★ 静默告警看板（治"堆积 146 run"）
- 与其堆 146 个 run，不如做**每技能"上次成功时间"看板 + 静默告警**（N 小时无成功即报）。类比监控看门狗：关注"没成功"而非"又跑了一次"。

### ★ 保留并强化（不要动）
- `EXTERNAL_EFFECT` fail-closed、`ActionResult` 收据、发送前明确授权——**这些是项目最值钱的部分，保留**。加固只在"让它更稳定地走到发送那一跳"上做文章。

---

## 五、建议的第一步（最小改动、最大收益）

1. 先给所有 AppleScript/AX/adb/browser 外部调用**加显式超时**（纯防御，不直接改业务逻辑）——消除挂起级联。
2. 再上一道**瞬态/永久分类 + 重试预算 + 冷却**，让每次 UI 抖动**不再派生新 run**——直接止住 runs 堆积与人力消耗。
3. 这两条都不动安全门，却能把"各种事情中断"的频率砍掉一大半；之后再做常驻守护与机器独占，才是根治。
