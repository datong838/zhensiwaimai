# 无新增零微信触达与真实非空自动重封方案

## 背景与问题

当前总入口在采集前执行桌面微信预检。即使最终没有待发商家，也会抢占微信并运行群定位；这既影响线上人工使用，也让已经由统一微信 Skill 解决的窗口分类、搜索弹窗和 OCR 后备问题进入无新增轮次。

执行器处于 `UNSEALED_ACCEPTANCE` 时，普通每小时入口会在完整性门禁立即停止，无法等待下一家真实新增商家完成本版本非空验收。人工空跑不能替代真实验收，也不能重新封板。

## 目标

1. 先完成采集与业务审计；只有确有待发商家时才触达桌面微信。
2. 无新增轮次由代码明确跳过微信预检和发送，仍复核游标并生成完整复盘。
3. 同一固定入口在 `SEALED` 时执行正常生产；在有效的 `UNSEALED_ACCEPTANCE` 授权下执行候选版本验收。
4. 只有本轮至少一条真实新发送通过统一微信 Skill、原生全文复制、双帧、历史及游标复核后，代码才原子更新锁为 `SEALED`。
5. `review.json` 的实际新增发送数从逐条阶段证据计算，不直接相信适配器汇总字段。

## 代码改动

- `scripts/workflow_executor.py`
  - 顺序调整为完整性、策略、自测、采集、审计、按需微信预检、通知、最终复核。
  - 无待发时不调用微信预检。
  - 统一调用可识别 `SEALED` / `UNSEALED_ACCEPTANCE` 的代码门禁。
  - 非空验收成功后调用确定性重封函数；重封失败则整轮失败，已发送事实保留且禁止重发。
- `scripts/executor_integrity.py`
  - 增加按锁状态选择验证的入口。
  - 增加从本轮真实非空收据重封的函数：验证运行结果、发送次数、最终游标、逐字复制证据、运行文件摘要，然后以临时文件同步并原子替换锁文件。
  - 商家工作流只要求统一微信的文字验收；图片/文件验收不再作为商家文字发送的运行门禁。仍锁定统一 Skill 的依赖清单，且统一执行器会校验当前全部依赖摘要；本改动不改变图片/文件实现或其验收状态。
- `scripts/runtime_contract.py`
  - 复盘阶段顺序与新执行顺序一致。
  - 从逐商家代码证据计算 `verifiedNewSends`、`verifiedExisting`、`unresolvedItems`，并把 `sent` 固定为 `verifiedNewSends`。
  - 增加“无待发跳过微信预检”的明确状态，不把未执行误报为失败或耗时 0。
- `tests/test_runtime_contract.py`、`tests/test_executor_integrity.py`
  - 验证无新增时微信预检调用次数为 0。
  - 验证有新增时预检先于发送且只运行一次。
  - 验证已有 attempt 的只读复核不计作新发送。
  - 验证空跑、复核既有记录、缺少复制证据或游标复核不能重封。
- `SKILL.md`、`references/workflow-contract.md`
  - 仅记录上述代码行为和验收边界，不作为运行许可。

统一微信 Skill 的文字、图片、文件实现不做修改。本工作流只调用其注册桥；合法搜索弹窗与 `wechat-unexpected-secondary-window` 的分类继续由统一 Skill 及其依赖摘要负责，避免商家工作流局部修复影响媒体发送。

## 验收与上线

1. 运行商家工作流离线测试、统一微信 Skill 回归和 Skill 结构校验。
2. 更新 `UNSEALED_ACCEPTANCE` 锁中的候选文件摘要；状态保持未封板。
3. 立即运行一次候选版本：当前无新增时应完成采集、审计、游标复核，微信预检为代码跳过，发送为 0，锁仍未封板。
4. 下一家真实新增商家出现时，同一入口完成真实发送；仅当本轮 `verifiedNewSends > 0` 且最终审计通过时自动重封。
5. 重封后同一入口自动走普通 `SEALED` 校验；历史、游标、attempted 和统一微信账本均不重置。

## 风险与停止条件

- 发送已发生但重封失败：保留 attempted、历史和游标，整轮报告失败，不重发；只修复封板元数据。
- 统一微信返回 unknown：不提交业务游标、不重封，后续仅按统一 Skill 只读对账。
- 无新增或只复核既有 attempted：不得重封。
- 锁授权过期、文件摘要漂移、目标群不唯一、任一证据不完整：代码失败关闭。
