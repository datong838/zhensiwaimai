# 金鲨后台专用浏览器优先方案（2026-09-10）

## 目标

在保留已验证桌面金鲨下载路径的同时，为真实业务日报增加浏览器下载路径。未配置下载通道时固定优先使用 `control-background-dedicated-chrome`；只有显式配置 `jinshaChannel: "desktop"` 才使用原桌面金鲨。两条路径必须产生相同的昨日日期、平台、下载方案、36项指标、文件命名和下载收据，后续制表与微信交付不分叉。

## 固定资源与隔离

- Profile：`jinsha-business`
- CDP：`127.0.0.1:9232`
- 首页：`https://data.guoshuyufen.com/#/businessData/realTimeData`
- 强 URL 前缀：`https://data.guoshuyufen.com/`
- 浏览器控制器：`control-background-dedicated-chrome`
- `taobao-brand:9230`、`taobao-agent-service:9231`、日常 Chrome 与桌面金鲨进程均不属于本通道，禁止连接、复制登录数据或自动回退。

## 首次登录交接

1. `init` 创建独立持久 Profile。
2. `login --disable-background-mode` 只打开普通可见 Chrome；此阶段不得启用 CDP、Playwright、页面读取、截图或自动输入。该开关保证用户关闭最后一个专用窗口后进程自然退出，不由执行器 SIGTERM 代关。
3. 用户本人完成账号、密码、验证码和风控，并通过 Chrome 正常退出/关闭专用登录窗口后明确确认“已关闭”。自动化不得用 `stop`、SIGTERM 或强制退出代替用户正常关闭，否则站点会话可能尚未持久化。
4. 执行器才允许用同一 Profile 以 `start --restore-last-session` 在 `9232` 启动无头 Chrome，执行 `probe` 并进入业务任务。
5. 登录失效或出现 CAPTCHA/风险验证时停止，回到人工登录交接；禁止切换日常 Chrome。

## 浏览器下载合同

1. 每轮使用唯一 task-id 创建自有标签；从首页通过 DOM 文本确定性导航到报表下载页，不按标签顺序、模糊标题或绝对坐标猜测。
2. 每个平台依次执行：选择平台 → 选择多店数据/按日 → 起止日期均设为 Asia/Shanghai 昨日并回读 → 选择固定方案 → 验证已选36项 → 触发一次下载。
3. 美团方案固定为「最终美团最新日报」；淘宝方案固定为现有桌面合同使用的「饿了么日报数据📊6.18最新最新」，并验证「单均实付」「单均到手」均被选中。若淘宝初始为34项，只允许通过标签文本唯一定位并补选这两项；禁止像素坐标。
4. 下载必须由当前任务页的 Playwright `download` 事件唯一捕获，保存到本轮配置 `raw.meituan`、`raw.taobao` 指定的全新绝对路径；收据文件名必须与目标 basename 一致。每个平台点击次数严格为1。
5. 保存后验证文件非空、ZIP/XLSX结构完整、名称正确、SHA-256可读；收据分别记录 `downloadStartedAt`、`savedAt`、文件路径、大小和哈希。
6. 两个平台成功后写 `jinshaResourceReleased=true`，关闭本轮任务标签但保持 `jinsha-business:9232` 存活。从此制表和微信阶段不得再调用浏览器或桌面金鲨。
7. 若美团已完成且哈希验证通过、淘宝尚未点击，允许同一 `runId` 显式 `resumeDownload=true`，从淘宝继续；必须绑定原收据、日期、Profile、端口、路径、大小和哈希。其他点击组合或未知下载结果均拒绝恢复。

## 稳定定位与失败关闭

- 页面、frame、平台控件、日期输入、方案候选、指标标签和下载按钮均要求语义唯一；页面重渲染后重新定位，不复用旧句柄。
- 报表页可能延迟出现标题精确为「新功能上线」的 `.upload` 遮罩。进入报表页后在2.5秒窗口内轮询，并在平台/模式切换后再次做1.2秒检查；仅当遮罩、标题和其内部「关闭」精确文本均唯一时关闭并等待遮罩消失。网页视觉按钮没有 button 角色，不能把角色缺失误判为不可关闭；仍禁止页面全局匹配、强制点击或处理其他弹窗。
- 日期、方案、平台、指标数、下载事件或文件结构任一不符合合同立即失败，不点击下载。
- 下载已点击但结果未知时记录 unknown 并停止；不得切换桌面路径补点，也不得重复下载。
- task-id 非唯一、端口/profile不符、URL越界、URL进入 `#/login`、风险校验或页面结构未知时失败关闭；登录 URL 必须直接报告 `jinsha-login-required`，不得等待并误报为下载页定位失败。

## 首轮维护记录

- 首次可见登录完成后，自动化错误地用受管进程 `stop` 代替用户正常关闭窗口。后台启动后 URL 跳转 `#/login?redirect=...`，说明会话未持久化；该轮下载点击0次、文件0个。
- 整改后把“用户正常关闭可见登录窗口”提升为交接硬门，并把 `#/login` URL 作为登录失效的首要确定性信号。
- 即使用户勾选“记住账号”，若 Chrome 关窗后仍后台驻留并再被 SIGTERM，金鲨会话仍可能丢失。为该 Profile 固化登录时 `--disable-background-mode`、无头启动时 `--restore-last-session`，不扩大到其他专用 Profile。
- 登录恢复后第3轮已到达报表页，但「新功能上线」遮罩拦截日期输入。该轮下载点击0次；整改为上述唯一遮罩合同后再启新轮。
- 第4轮即时遮罩检查在10毫秒时尚未发现遮罩，随后日期点击仍被延迟出现的遮罩拦截；下载仍为0。整改为有界轮询并在平台切换后复核。
- 第5轮已稳定发现唯一遮罩，但其“关闭”控件没有 button 角色，角色合同失败；下载仍为0。整改为遮罩内部精确文本唯一定位。
- 第6轮美团已一次下载并通过XLSX与哈希检查；淘宝方案在页面显示为旧桌面执行器已验证的截断名，完整文本精确匹配为0。固化同一runId只续跑淘宝，并只接受完整名或精确截断格式。
- 只读诊断确认方案下拉是表格而非标准 option；目标行「饿了么...最新最新」为34项，另一项「淘宝金鲨」虽为36项但不是既定方案。方案选择固定在可见表格单元格中做全文白名单匹配，再补两项指标至36。
- DOM进一步确认方案名称的真实节点为唯一 `DIV.plan_li_one.plan_li_val`，而非HTML `td` 或 ARIA option；执行器固定在该容器内做白名单全文匹配。
- 淘宝两个补选指标不是原生 `input[type=checkbox]`：完整文本节点的唯一父容器为 `DIV.check_one.w16.w20`，状态图标为其子节点 `SPAN.checkSpan`。旧原生 checkbox 定位稳定返回0，属于确定性定位模型错误，不是登录或焦点问题。
- 指标补选改为完整文本唯一定位容器，点击前后必须通过状态样式与页面「已选择（N）」数量增量双重回读；仅允许34项时补选「单均实付」「单均到手」，最终严格为36项。任一多命中、状态缺失、数量不增加或最终数量异常均在下载前失败关闭。
- 桌面微信首轮发送门禁耗时8.285秒并以 `desktop-wechat-blocked-login` 失败，发送0份；截图证明搜索操作后微信曾瞬态进入账号安全重新登录页，保留为外部状态证据。后续复测已恢复登录，但首张带窗口阴影的截图坐标被错误用于点击，实际打开了会话行而非搜索框，导致 `search-focus-control-count:0`。依赖控制器必须统一使用无阴影主窗口区域截图做动作坐标，群名和发送确认合同不放宽。
- 无阴影截图修正后搜索框已被准确点击，但搜索下拉成为 macOS `front window`，旧边界读取随之改绑弹层，第二张图被裁成弹层并再次得到 `search-focus-control-count:0`。依赖控制器进一步固定所有边界读取到唯一名称为「微信」的主窗口；弹层只作为主窗口区域内视觉内容，不得改变坐标原点。
- 群定位通过后的首次发送动作建立了1次 attempted，但 prepared、after-send-1、after-send-2 和当前群底部 UI 树均证明没有附件预览、没有两份报表气泡，结果可确定为未发送。根因是发送器仍用带阴影截图宽高计算输入区坐标。保留该 unknown 证据并隔离 marker 后，只允许一次恢复重试；发送器改为全程无阴影主窗口截图，并在 attempted 前强制回读两个完整文件名和足够的输入区变化量。
- 首次恢复运行被新增预览门禁在发送前拦截：`preparedInputChangedPixels=136`、完整文件名回读=false、发送键0次、attempted未建立。剩余问题是比例坐标仍未可靠聚焦输入框；整改为按主窗口AX树唯一大尺寸 `AXTextArea` 聚焦并回读，不再靠比例点位。
- AX输入框聚焦实机回读成功后，附件仍未预览；剪贴板类型诊断确认旧AppleScript写法只产生两个 `list` 类型，而新版微信需要标准 `public.file-url`。文件剪贴板改由 NSPasteboard 写入NSURL列表并逐项回读类型，不满足时在粘贴前失败关闭。
- 标准文件URL生效后输入区变化量达到140167，两个XLSX预览卡片可见，AX值严格为两个对象占位符；完整文件名OCR失败是微信4.x视觉截断导致。整改为粘贴前空输入区硬门，粘贴后对象占位符数=文件数、变化量阈值和「美团外卖日报/淘宝闪购日报」稳定前缀三重校验；当前未发送附件草稿已清空并回读为空。
- 三重预览门通过后的内层桌面发送已成功：预览变化140191、对象数2、两个业务前缀通过、发送键1次、两帧复核通过、marker为verified。外层业务包装器随后因 `Path` 不能JSON序列化而报错；这是回执封装缺陷，禁止重发。外层统一把文件路径转为字符串，再由已确认账本完成幂等回读和最终收据。
- 外层修正后幂等 `--send` 在2.928秒命中两份confirmed哈希并完成最终收据，新增发送0；随后 `--verify-only` 在2.819秒通过，`businessCompleted=true`。`jinsha-business:9232` 与 `taobao-brand:9230` 均保持headless存活且各保留唯一业务首页，任务标签已清理。
- 干净run 07浏览器双平台下载一次通过24.439秒、制表7.305秒、累计76.788秒，运行时模型介入0；但相同业务内容的XLSX因关系ID随机而字节哈希不同。防重增加固定业务交付键：在同一目标群专属账本内，完整成品名（包含平台和业务日期）且历史记录同时为confirmed、fullNameVerified、groupTitleVerified并唯一时，视为已交付；原SHA校验继续保留。这样重建文件不会重复发，同名历史冲突则失败关闭。
- run 08浏览器下载14.406秒、制表7.259秒均一次通过；桌面预检在2.518秒失败且发送0。证据图实际为用户前台今日头条，证明屏幕区域截图在微信被遮挡/失焦时会串窗。共享控制器改为微信唯一窗口ID的 `screencapture -o -l`，实现被遮挡时仍捕获微信且无阴影，不要求用户让出Chrome前台。
- 首次后台窗口截图探测因旧窗口ID函数使用 `OnScreenOnly` 返回空；Quartz全部窗口中确认主窗为唯一名称「微信」、layer0、1120×638，另有280×380小窗。窗口ID规则改为OptionAll并以名称、层级、最小尺寸和唯一性四重绑定，排除小窗且支持完全遮挡。
- 正常路径 `runtimeModelDecisions=0`；大模型只在一轮结束后根据收据维护执行器，不参与运行时选点。

## 业务入口

- 配置新增 `jinshaChannel: "browser"|"desktop"`，缺省解析为 `browser`。
- `browser` 调用本 Skill 的后台浏览器执行器；`desktop` 保留 `business_jinsha_cua_exam.mjs`。
- 两者输出继续绑定同一 `runId`、`businessDate`、原始文件路径和 `downloadUiReceipt` schema；`business_exam_pipeline.mjs --prepare`、制表及桌面/手机微信发送逻辑保持不变。

1. 离线测试覆盖默认 browser、显式 desktop、非法通道拒绝、Profile/端口/URL硬绑定、昨日日期、文件命名、两平台一次下载和收据合同。
2. 登录阶段证明 `automationAttached=false`、`cdpEnabled=false`。
3. 后台阶段证明前台 App 未变化、无可见 Chrome 窗口新增、任务标签唯一、`runtimeModelDecisions=0`。
4. 真机实操完成浏览器双平台下载、XLSX结构与哈希验证、制表、桌面微信交付及最终只读复核；逐节点记录耗时、是否模型介入、通过状态和待优化项。
