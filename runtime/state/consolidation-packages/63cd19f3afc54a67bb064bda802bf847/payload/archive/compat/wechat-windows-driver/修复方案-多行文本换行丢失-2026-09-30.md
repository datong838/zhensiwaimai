# 修复方案：微信发送的多行文本「换行丢失」

- 日期：2026-09-30
- 提出方：Mac 侧（WorkBuddy 臻肆外卖工作流会话）
- 影响面：**所有经 Windows 驱动发送的文字类交付物**（当前主要是 `#9 品牌差评申诉进度通知`）
- 结论：**能解决**，需 Windows 侧改 `driver.py` 发送路径；Mac 侧同时备一个立即可用的降级方案

## 1. 现象

大同实测：`#9 品牌差评申诉跟进` 发到 `李老哈（品牌）💰臻肆外卖运营对接群` 的通知**数据是对的，但换行/格式全没了**，六行正文被压成一长行。

## 2. 取证（已定案）

| # | 证据 | 判读 |
|---|---|---|
| 1 | 冻结请求 `brand-negative-review-appeal-followup/.runtime/delivery-2026-09-29-all-outcomes-v1/request.json` 里 `items[0].text` = `'--- 2026-09-29 差评申诉进度通知 ---\n李老哈·东北农家小院(海上海店)\n【美团】\n评价时间: 2026-09-29\n...'` | **Mac 侧离开时换行是完整的**（真 `\n`，`repr` 可见），不是上游渲染丢了 |
| 2 | `skills/wechat-messaging/scripts/windows_adapter.py::send_one` 对文字分支直接 `self.client.send(search_key, item['text'])`，无任何换行处理 | Mac 侧**无**压缩换行的代码 |
| 3 | 该群只读回读（`read_messages`）读到的是**单行拼接串**：`--- 2026-09-29 差评申诉进度通知 ---李老哈·东北农家小院(海上海店)【美团】评价时间: ...` | 群内真实存储的这条消息**就是没有换行**（回读忠实反映） |
| 4 | `driver.py` 发送最后一步：`edit.SendKeys(text, waitTime=1.0)` → `edit.SendKeys("{Enter}")` | **根因所在** |
| 5 | 大同肉眼在群里看这条消息 = 一长行 | 排除「只是回读通道压平」的解释 |

## 3. 根因

驱动用 uiautomation 的 **`SendKeys` 逐字键盘注入**输入正文：

```python
edit.SendKeys(text, waitTime=1.0)
time.sleep(0.3)
edit.SendKeys("{Enter}")   # 回车发送
```

`SendKeys` 把字符当**键盘事件**打进去。`\n`（U+000A）是**控制字符，不是可敲出来的键**——微信输入框收到它等于什么都没收到，于是所有换行被**整体吞掉**，六行变成一行。

这同时解释了两件此前分开看的事：

- 群内消息**确实**没有换行（现象 3、5）；
- 所以「回读被判 unknown」不是回读通道的毛病，而是**被忠实读回来的事实**。Mac 侧已据此把回读校验对齐到驱动的真实表示（换行压平，见 §6），**这是正确的修法**，无需回退。

副作用（同一根因）：`SendKeys` 还把所有 `{}` 当**特殊键语法**。正文里一旦出现半角花括号（如 `{门店}`）会被吃掉甚至误触发按键。剪贴板方案一并消除这一隐患。

## 4. 修法 A（推荐·根治）：发送路径改「剪贴板粘贴」

把「输入正文」那一步从逐字敲改成 **写剪贴板 + Ctrl+V**。换行、emoji、花括号全部原样保真，长文本还快得多。

在 `driver.py` 里新增两个函数：

```python
def _set_clipboard(text):
    """写剪贴板（Unicode）。优先 uiautomation 自带，退化到 ctypes，再退化到 clip.exe。"""
    try:
        auto.SetClipboardText(text)          # uiautomation 自带，最省事
        return "uiautomation"
    except Exception:
        pass
    try:
        import ctypes
        CF_UNICODETEXT, GMEM_MOVEABLE = 13, 0x0002
        u = ctypes.windll.user32
        k = ctypes.windll.kernel32
        data = text.encode("utf-16-le") + b"\x00\x00"
        if not u.OpenClipboard(None):
            raise RuntimeError("OpenClipboard failed")
        try:
            u.EmptyClipboard()
            h = k.GlobalAlloc(GMEM_MOVEABLE, len(data))
            p = k.GlobalLock(h)
            ctypes.memmove(p, data, len(data))
            k.GlobalUnlock(h)
            u.SetClipboardData(CF_UNICODETEXT, h)
        finally:
            u.CloseClipboard()
        return "ctypes"
    except Exception:
        pass
    # 最后兜底：clip.exe 默认按 ANSI 读 stdin，必须切成 UTF-16LE
    import subprocess
    subprocess.run("clip", input=text.encode("utf-16-le"), check=True, shell=True)
    return "clip.exe"


def _type_body(edit, text):
    """把正文写进输入框。多行走剪贴板粘贴，保住换行；失败则退回逐行 Shift+Enter。"""
    if "\n" in text or "\r" in text:
        _set_clipboard(text)
        time.sleep(0.2)
        edit.SendKeys("{Ctrl}v", waitTime=0.5)
        time.sleep(0.4)
        return "paste"
    edit.SendKeys(text, waitTime=1.0)        # 单行仍走原路径，行为不变
    return "keys"
```

然后把 `send_message()` 里输入正文的两行替换掉：

```python
-    edit.SendKeys(text, waitTime=1.0)
+    _type_body(edit, text)
     time.sleep(0.3)
     edit.SendKeys("{Enter}")   # 回车发送
```

要点：

- **只在含换行时走粘贴**，单行文本维持原路径 → 零回归面。
- 粘贴进微信输入框的多行文本会**原样落成一条带换行的消息**，不会自动发出；仍由末尾那个 `{Enter}` 发送。
- 剪贴板会被占用（覆盖用户原剪贴板）。若在意，可在发送前 `auto.GetClipboardText()` 存一份、发送后还原。
- `auto_send` / 文件分支若与 `send_message` 共用同一段输入逻辑，**同一处替换即可**；若是各自实现，需各自替换。

## 5. 修法 B（备选·零新依赖）：逐行敲 + `Shift+Enter`

不想动剪贴板就用这个——微信群内换行本来就是 `Shift+Enter`：

```python
def _type_body(edit, text):
    lines = text.replace("\r\n", "\n").replace("\r", "\n").split("\n")
    for i, line in enumerate(lines):
        if i:
            edit.SendKeys("{Shift}{Enter}", waitTime=0.2)   # 换行不发送
        if line:
            edit.SendKeys(line, waitTime=0.3)
    return "shift-enter"
```

比 A 慢（长正文逐字敲），且**仍需处理 `{}` 转义**（正文里的 `{`/`}` 要写成 `{{`/`}}`），所以 A 更稳。

## 8. 定责与边界

- 本方案**只**改 Windows 驱动的「正文输入方式」，不动会话打开/搜索、不动发送判定、不动 Mac 侧业务渲染。
- 与 §B1（emoji 搜索键）是**两处独立缺陷**：B1 在「打开会话」段，本条在「输入正文」段。两者都指向同一建议：**驱动侧凡涉及文本输入，优先剪贴板而非逐字 SendKeys**。
