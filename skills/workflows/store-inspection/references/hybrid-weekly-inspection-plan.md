# 周巡店报表混合执行方案

更新：2026-09-14。适用每周约 1,000 家店的淘宝闪购、美团外卖只读巡店。目标是让后台结构化事实先覆盖 44 条模板中可直接核实的部分，再用消费者端补齐展示事实；不把后台配置、历史模板或旧日报当作当前消费者端展示。

## 容量结论

不要每天逐店下载约 100 份报表。已验证的淘宝闪购日报下载命名为“全部门店”，正确的下载粒度是：每个平台、每个业务日各生成一次门店报表和一次评价报表；本地按门店 ID/名称/城市拆分事实后，再分批巡店。

`100 家/日 × 7 日 = 700 家`，不能完成约 1,000 家的自然周目标。默认采用六个执行日，每日两批、每批最多 80 家，即每日 160 家；第七日只处理最多 40 家失败恢复、授权恢复或前后台不一致店。若业务只能稳定处理 100 家/日，则必须把周期明确延长至至少 10 个执行日，不能仍标为“本周完成”。

## 数据层与边界

| 层级 | 输入 | 作用 | 禁止推断 |
| --- | --- | --- | --- |
| A. 金鲨全量日报 | 每平台门店报表、评价报表，均须带业务日期、文件哈希和门店范围 | 营收/订单/流量/评分与好中差评/复购等聚合事实 | 商品视觉、消费者端首屏、即时配送展示、真实出餐或自动回复。 |
| B. 淘宝服务商后台 | 仅目标店在授权服务商账号内时，按门店 ID 读取门店分析、商品、门店资料、装修状态、活动、评价与推广页 | 补足单店经营、商品结构、门店资料、活动规则、评价回复、复购与推广事实 | 看见程序路由等同于账号可用；配送空白页等同于无配送配置；后台配置等同于前台已展示。 |
| C. 淘宝品牌商后台 | 仅目标店在授权品牌账号内时读取单店菜单、装修、资料、配送、活动与评价详情 | 补足淘宝闪购的菜单、门店资料、活动规则、配送配置和评价详情 | 总部模板等同于单店在售；后台配置等同于前台已展示。 |
| D. 美团商家后台 | 仅目标店通过“美团门店 ID＋完整店名＋城市＋完整地址”四项唯一定位后，读取该店的资料、实际菜单、经营、评价回复、活动、配送、推广与既有报表事实 | 优先覆盖下述一期 14 条；页面确有字段时再覆盖二期 10+1 条 | 全部门店汇总等同于单店；只有入口等同于字段可用；店铺分等评分等同于原始经营数值；后台配置等同于消费者端已展示。 |
| E. 消费者端 | 城市 + 完整店名 + 地址回退门禁后，读取搜索、商品、评价和商家资料 | 补足搜索身份、POI、首屏视觉、公开评价主题、消费者可见分类与即时配送 | 不可见字段和因页面失败未取到的字段。 |

每个 44 条模板行只能由实际已读取的 A/B/C/D 来源填入；无来源时 `finding` 与 `recommendation` 同时留空。结果 Excel 不展示截图文件名。金鲨、品牌商和服务商 Skill 只负责各自平台能力识别与稳定定位；44 条业务映射、主来源选择和巡店生成规则只固化在本 Skill。

## 固定日流程

1. **报表日准备**：确认业务日期与上次成功下载日期；每个平台只创建所需的全量门店、评价报表各一次。下载结果未知时先在下载管理中按日期、报表类型、文件名和哈希查找，绝不重复点击下载。
2. **本地入库**：登记文件路径、SHA-256、平台、业务日期、报表类型、全量/门店范围、表头与可映射门店数。缺业务日期、平台、门店标识或表头的文件不进入巡店。
3. **确定性分批**：按 `平台 + 城市 + 完整店名` 的稳定排序生成队列；每日两批各不超过 80 家。不因为重跑而改变已分配批次；授权失败、缺字段和地址未唯一命中的店单独进入补偿队列。
4. **单店合成**：先将 A/B/C 层已确认事实按“字段来源 + 观察日期 + 门店唯一键”装入该店的 `inspection.json`，再只访问 D 层仍需要的页面。不得为了填满 44 条而补猜。
5. **交付前验证**：继续使用模板指纹、44 行顺序、成对空值、无“证据：”行、公式错误扫描及全表渲染验证。试运行只写本地结果，不上传企业微信、不回写台账完成状态。

## 执行器合同

混合巡店必须通过 `scripts/hybrid_inspection_executor.mjs` 生成计划和完成事实集，禁止直接凭文字方案手工决定手机范围。执行器只编排、验证和合并已经读取的事实，不操作金鲨、商家后台、手机或下载目录。

### 代码强制的阶段状态机

阶段顺序按平台固定，不允许运行时猜测：淘宝闪购为 `reports → agent_service → brand_backend → mobile → assemble → validate`；美团外卖为 `reports → meituan_backend → mobile → assemble → validate`。

1. `plan` 必须收到当前平台规定的全部后台阶段收据，状态只允许 `complete / skipped / failed`，完成时间必须按阶段非递减；缺收据、混入另一平台阶段或乱序失败关闭。
2. 每阶段最多 2 次尝试，即首次执行加 1 次受控恢复；`attempts > 2` 失败关闭。`skipped / failed` 阶段不得夹带事实，但不会阻断后续独立阶段。
3. 事实来源必须与阶段一致，且通过已有模板行资格、门店身份、日期、来源号和成对内容校验；同一行由固定优先级只选择一个主来源。
4. 消费者端强制行固定为 `2、3、4、21、23、25、26、38、39、40、41、45`；这些行即使后台有线索，也必须以消费者端实际展示为最终事实。
5. 金鲨优先行固定为 `5、6、10、11、12、13、14、15、16、17、22、31、36、44`；淘宝服务商优先行固定为 `7、13、14、15、16、17、18、19、29、30、31、36、42、43`；美团商家后台资格行固定为上述一期与二期 25 条。若优先来源缺失，只在该行被声明为消费者端可读时加入手机补查，否则留空。
6. `plan` 只输出仍需手机的模板行，并按 `search → products → reviews → merchant` 聚合为模块。没有模板行的模块不打开。默认策略为 `standard`；显式选择 `backend-first` 且满足上文金鲨评论前置条件时，第 7 行转入留空并记录策略抑制原因，不打开评论模块。该策略只减少手机访问，不伪造后台事实。
   - 手机行映射按平台固定。美团在通用消费者行之外，额外允许此前真机已验证可见的 `11、12、20、32、33、37`，分别归入搜索、商品或商家模块；这只是允许补查，实际页面未取得时仍留空。
7. `finalize` 必须收到计划内每个手机模块的收据；消费者事实只能来自计划行和状态为 `complete` 的对应模块。跳过/失败模块保持空白，越界事实、重复行或缺模块收据失败关闭。
8. `finalize` 输出带 `workflowMode=hybrid` 和执行收据的 44 行结果；执行收据必须逐模块保留状态、尝试次数及实际形成事实的行号，来源覆盖表据此明确列出本次完成的搜索、商品、评价、商家信息模块和条数。
9. 结果再交给 Excel 生成/校验器；制表器对新混合结果强制校验该收据，未经过 `finalize` 的混合运行不得生成正式结果。历史非混合结果继续兼容。

### 门店与手机门禁

- 允许执行的历史验证样本只来自 `references/verified-store-routes.json` 当前登记的 4 个 `平台 + 上海市 + 完整台账店名` 组合；新店必须先独立验证并更新路由，不能用相似店代替。
- `plan` 校验台账店名、城市和 POI；`finalize` 再校验消费者端完整店名与地址锚点。允许的名称漂移只能来自路由文件的 `aliases`。
- `mobile_inspection_executor.py validate-mobile-module` 在进入每个手机模块前校验计划、门店和模块；模块不在计划中时拒绝进入。校验器接受历史淘宝计划 `policyVersion=1` 与当前跨平台计划 `policyVersion=2`，其他版本一律拒绝；不能因为策略升级让已生成的合法手机计划误阻断。验证码由用户手动关闭后，只恢复受影响模块；评价模块失败可以跳过，但商品和商家资料仍须继续并分别出收据。
- 美团手机阶段必须通过 `mobile_inspection_executor.py start-platform-app --platform 美团外卖` 启动；执行器把平台唯一映射到原生包 `com.sankuai.meituan` 并复核前台包名。微信美团小程序不属于可选回退通道，运行时不得临时改道。
- 对每个来源保留 `sourceType`、观察日期、门店唯一键与文件哈希/页面观察号，仅在本地过程 JSON 留存，Excel 不显示敏感路径或图片名。

报表下载、后台页面读取和消费者端巡店仍由各自已授权的执行通道完成。任何单一来源失败时，执行器只留下该来源对应的模板行为空并继续其他独立来源；不会切换到未授权通道或重试写操作。

### 首店来源汇报表

首店另生成一份独立 Excel，逐行列出模板行号、项目、检查点、本次来源、数据/观察日期、本次结果及与原结果的对比。来源只允许写成“金鲨数据下载”“淘宝服务商后台”“淘宝品牌商后台”“美团商家后台”“手机翻查”或“留空”；不得向业务使用者暴露本地路径、文件哈希、截图文件名或内部观察号。

- 同一检查点只列实际形成该行结论的主来源；后台事实和消费者端展示事实不得拼成一个无法追溯的混合结论。
- `finding` 为空时来源必须是“留空”，日期与本次结果同步留空；不写“未核验”。
- 对比只表示“内容一致 / 本次新增 / 本次未复核，未沿用旧值 / 观察结果变化”；不同日期的销量、评分、评价量和时效变化不能直接判定为异常。
- 汇报表顶部汇总各来源覆盖行数和总覆盖率，并明确本次实际走手机的模块；统计口径为 44 条模板检查点，不以截图张数计数。

## 上线门槛

- 淘宝闪购、美团外卖各至少一个全量门店和评价报表可稳定下载、可读取表头并映射店铺身份。
- 每个平台各一店完成报表字段与后台/消费者端同日或相邻日期的口径对账。
- 两次连续日运行中，队列分批、失败归类和断点恢复均不改变已完成店的历史结果。
- 上线前不自动创建大批下载任务；每次报表动作仍要求用户当日明确授权。
