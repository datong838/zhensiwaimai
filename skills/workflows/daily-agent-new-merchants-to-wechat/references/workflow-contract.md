# 工作流与状态合同

## 1. 产品方案

目标是把“从已验证游标补偿到今天的意向商家增量通知”固化为两个低自由度执行器。模型只参与首次页面建模、异常和缺字段语义判断；稳定动作由执行器完成。

日期闭区间从有效游标的推荐日期起，到 Asia/Shanghai 今天止。完整遍历区间全部分页后，按 `(推荐时间, 页面稳定行序, 商家ID)` 排序并精确定位历史游标；游标是排他边界，只发送其后状态为「待处理」的商家，已完成记录不通知。不得因跨日只筛今天而跳过中间日期。

消息模板固定为：

```text
<城市或（城市字段缺失）>
<联系人姓名，手机号或（商家联系人字段缺失）>
<商家名称或（商家名称字段缺失）>
<商家地址或（商家地址字段缺失）>
```

每个商家独立一条消息，不合并、不加序号。商家ID不发送，只用于幂等、回查与游标。

## 1.1 第一原则：必须完成任务

门禁失败、代码缺陷和运行环境问题都属于待解决的阻断，不是任务终点。执行方必须保留失败证据，定位根因，在授权范围内修复代码、维护流程或运行依赖，完成针对性回归，再回到唯一总入口继续，直到本轮达到完成判据或出现明确的外部授权/登录缺失。任何修复都不得绕过门禁、改变目标群、切换未授权通道、重发未知结果、手工推进游标或修改发送标记；是否继续、发送、复核、提交和封板仍只由代码和机器可读收据决定。

## 2. 当前页面采集技术方案

总流程取得互斥锁后，第一节点由 `scripts/executor_integrity.py` 校验 `executor-lock.json`。该代码门禁固定总入口、结构采集、桌面/手机适配器及共享桌面微信定位和发送代码的路径与 SHA-256，并绑定真实非空文字发送的验收收据；未通过时不得执行微信预检、浏览器采集或状态写入。有效 `UNSEALED_ACCEPTANCE` 只允许同一候选版本执行验收；空跑和已有 attempt 只读复核都不能重封。Markdown 只解释合同，不参与运行时动作选择。

当前默认结构采集、输入发送和恢复合同以 SKILL.md「当前默认执行器」及 `plan-2026-09-10-background-dedicated-chrome.md` 为准。唯一浏览器控制通道是 `taobao-agent-service:9231` 后台专用 Chrome；首次登录仅由用户在无 CDP 的独立可见窗口完成，之后通过 localhost CDP 操作带唯一 task-id 的自有标签。日历选择“游标日期至今天”并回读，列表稳定且所有推荐时间落入该闭区间后，按业务表头映射业务行并遍历全部页码直到下一页禁用。逐条详情必须等占位值完成加载并与列表 ID/名称一致，推荐时间稳定升序，同时间保留跨页原顺序。

平台当前不提供可读总条数；以每页实际计数、连续页码、`(商家ID, 推荐时间)` 复合身份不重叠和末页禁用证明遍历完整，收据 totalRows 是实际读出数量，不声称平台总数。采集日期中途跨日立即失败。

采集输出在调用者指定的独立运行目录 collection.json；schema 含 ok、executor、businessDate、createdAt、dateFilterVerified、pages、paginationComplete、ascending、detailsVerified、cursorSource、selectionAudit 和 messages。表格任一行列数异常、商家ID非法或表头重复均硬失败；selectionAudit逐行保存商家ID、推荐时间和状态，并证明游标及以前、游标以后非待处理、最终目标三类计数闭合。每条消息保留详情身份证据与四行文本SHA-256。运行时模型决策0，不读网络接口、浏览器内部状态或凭据。

`structured_merchant_collector.py`每次结束必须由代码生成同名`.review.json`与`.review.md`，覆盖浏览器预检、任务页、导航、日期、逐页采集、选择审计、详情和总耗时。失败后的阶段必须为SKIPPED和空耗时；只读入口也只接受生产群，模型不得根据原始日志自行改写结果。

历史 AX/OCR 清遮挡、窗口置前和全局点击路径只作历史兼容，不属于默认路径，且不能作为后台专用 Chrome 的自动失败回退。

## 3. 游标恢复与持久化

状态目录：`/Users/ddt/work/projects/ai_agent/zhensi_waimai_back/state/taobao-agent-new-merchants/`。

- `cursor.json`：生产群「电销+直播攻坚组」。
- `cursor.test.json`：测试群「FEIBING NEO AI数字员工」。
- `send-history.jsonl`：两个群共用追加历史，每条带 `groupName`、`mode` 和内容哈希。

游标结构：

```json
{
  "schemaVersion": 1,
  "groupName": "FEIBING NEO AI数字员工",
  "merchantName": "峡谷补给站·开黑能量餐",
  "merchantId": "545841902",
  "recommendTime": "2026-09-08 09:49:35",
  "tableOrder": 2,
  "messageSha256": "...",
  "cursorSource": "user-designated-live-verified",
  "verified": true
}
```

用户指定并经页面详情只读复核的初始化游标可以不带 `sentAt`，但必须写明 `cursorSource`，且不得追加到成功发送历史；执行器仍只把“群内新气泡全文复验成功”的记录写入 `send-history.jsonl`。

写入顺序：群内新气泡全文复验成功后，先以单行 JSON + 换行追加历史并同步落盘，再把新游标写临时文件、同步并原子重命名。任何失败不得更新游标。

本地游标缺失/损坏时，只读目标群近期窗口，识别最新有效四行消息；第三行是商家名称。优先用当前表格唯一名称回查ID和推荐时间；重名时结合城市、联系人、地址。仍不唯一时停止，不能凭名称猜测。

## 4. 微信发送技术方案

生产群顶部 OCR 可能把 `+` 识别为 `＋`，或将人数括号后的图标并入单个 `>`。公共顶部标题入口只在这些有限视觉差异下，要求唯一视觉候选并只读核对唯一主窗 AX 的原始完整群名；实际群名、业务身份、搜索、正文及历史不得做加号归一化。图标兼容仅限人数闭括号后的单个 `>`，其他后缀拒绝。AX 缺失、不匹配或多个标题均拒绝，发送前后和只读 reconcile 使用同一规则。

开发测试目标为「FEIBING NEO AI数字员工」，使用用户持续站立授权；生产运行必须把目标群切回「电销+直播攻坚组」，并使用独立生产授权和 `cursor.json`。默认且优先使用已登录桌面微信；桌面未登录或目标群不能唯一确认时暂停，不自动切换手机。只有显式指定 `mobile` 才使用已校准荣耀真机。原「臻肆测试群」成功历史不改写，且因 `groupName` 不同不会参与新群去重或游标恢复。

执行主链路由 workflow_executor.py 串联。微信阶段使用本技能私有 ADB截图适配，避免 uiautomator2 图像流异常；解码失败最多一次重截。群名本体唯一、两帧位置稳定后打开，顶部群名回读；出现明确短时系统通知只等待消失，不操作其他群。

桌面微信是默认通道：发送前清空剪贴板，聚焦唯一 `AXTextArea` 后直接设置控件文本，并从控件值逐字回读；禁止使用粘贴，避免剪贴板残留文件被微信解释为待发送附件。手机微信仅在显式指定 `mobile` 时使用白色编辑区长按全选复制，并要求随机剪贴板标记被原文替换后逐字比对。两条通道都必须核验编辑目标和UTF-16光标长度；发送前以群+商家ID+推荐时间创建排他 attempted 文件，发送动作仅执行一次。最新绿色气泡必须与发送前不同、两帧稳定、原文逐字一致，同时输入为空且群名正确，才追加成功历史并原子写游标。允许中点和全半角标点的视觉差异，不允许模糊汉字/数字匹配。

桌面微信被其他进程或人工短时抢占时，只有 `sendAttempts=0` 且 attempted 尚未建立的定位、聚焦、输入区和发送前页面漂移允许等待后重试；默认每5秒一次、最长900秒，不清空来源不明的草稿。每次等待写入私有 `contention.json`，包含阶段、原因、次数和耗时。登录缺失、授权/载荷/业务合同错误、目标群出现多个精确结果不按抢占处理。`sendAttempts=1`、已有 attempted 或发送结果未知时绝不重发，只能走只读 reconcile。

桌面 `desktop-post-send-verification-unknown` 的确定性 reconcile 只接受原 marker 状态为 unknown、群名和 payload SHA-256 完全一致的当前商家。目标群标题必须唯一，宽聊天输入框为空；按商家名称识别当前可见唯一出站气泡并要求两帧位置稳定，右键气泡后全屏菜单中的“复制”必须唯一，随机剪贴板标记必须被微信原生完整四行正文替换且逐字等于原文。随后只把原 marker 标记 verified 并按既有顺序提交历史/游标，`sendAttempts` 保持1。任何不一致继续保持 unknown，不得删除 marker 或调用发送。

旧版共享桥接的 Quartz 窗口截图异常可能在 `send:0` 留下 `sendAttempts=null` 的 unknown 完整回执。不得把 null 推断成0或1。只有顶层及嵌套回执都逐字绑定生产群、唯一正文和同一 SHA-256，顶层与内层状态均为 unknown，唯一失败阶段为 `send:0` 且失败原因精确为 `wechat-window-capture-failed:could not create image from window:quartz-window-capture-invalid` 时，允许该特定兼容分支进入桌面原生复制只读核验。它仍要求唯一气泡、双帧稳定、唯一复制菜单、空输入框及复制全文哈希一致；成功后保留 `sendAttempts=null`、`physicalSendAttempts=null`，标记 `reconciledWithoutSend=true` 并计为 `verifiedExisting`，不能记新发送。任何其他 null/unknown 回执拒绝复核或保持 unknown；所有现存非安全 blocked marker 都只能对账，禁止发送预检重走及重发。

成功历史用于去重；中途失败后新一轮只从已成功游标之后继续。未知 attempted 不得自动重发；reconcile_attempt 只读当前最新气泡并核对保留的发送前截图、商家身份和消息哈希，证据完整才提交。截图、阶段耗时和失败证据保留在私有运行目录。手机每消息60秒硬预算，workflow与sender分别互斥，结束恢复输入法。

Mac 桌面微信是 `workflow_executor.py` 的默认通道。代码先采集并审计；待发列表为空时跳过微信预检和发送。确有待发时，`desktop_wechat_sender.py` 调用统一 `wechat-messaging` 注册预检完成精确群定位；发送时每个商家继续使用同一 `send_identity` 作为 `send-attempts` 文件名，并在桌面气泡核验后调用同一 `append_history_then_cursor`。因此手机与桌面共享成功历史、排他游标和 attempted 锁；任何一端出现 unknown，另一端不得自动补发。只有显式 `--wechat-channel mobile` 才走原手机实现。

本地游标和成功历史均缺失时，自动群历史恢复暂未实现，应停止并按上节人工恢复规程核验；不得静默从全量开始。

- 总入口的运行许可、生产授权、通道、有限预算、每轮离线自测、采集恢复次数均由代码检查。生产群固定desktop与 `user-20260915-production-hourly`，测试群保持原隔离授权。
- 导航优先等待已验证的客户管理结构；代运营只接受左侧唯一实时DOM候选，父子完全重叠边界去重，多候选立即停止。已知导航瞬态错误最多在总计180秒内重新采集一次，外层不能追加整轮重试。
- 桌面未知错误、多候选（任意大于1）和发送子进程结果不明均硬停止。发送重试前再次检查attempted；存在则禁止执行子进程。发送后每条先通过原文/群/身份/单次发送/复制双帧证据门禁，再调用原历史与游标提交；最终检查每个身份成功历史唯一且匹配marker。
- workflow.json保存阶段结果，review.json为代码生成的逐项复盘，review.md是其确定性展示。每轮包括无新增和失败均展示复盘；父子耗时不可重复相加，未执行阶段不能写0秒通过，已恢复故障不得隐藏。review.json由代码分别输出 verifiedNewSends、verifiedExisting、unresolvedItems；execute-noop必须显示「无待发，未触发发送」，前置门禁未通过必须显示「未执行」和空耗时。
- MD只说明规则，不能补足未通过的代码门禁。新代码仍必须经明确解封、测试与真实非空验收后才重新SEALED，空跑不封板。
- 商家工作流只绑定统一微信的文字验收。图片/文件验收状态不决定商家文字入口是否运行；统一依赖清单及当前文件摘要仍必须匹配。本工作流不得修改统一微信的图片或文件发送代码。
- 真实非空验收重封由代码执行：必须有本轮新发送阶段、提交阶段、最终游标复核和当前版本原生复制收据；任何一项缺失都保持 `UNSEALED_ACCEPTANCE`。
- 共享依赖漂移与解封维护只允许 `scripts/maintenance_executor.py` 执行。它必须绑定固定维护授权、七日内有效期、原 SEALED 验收、允许漂移集合、统一微信依赖维护收据及两套完整测试；失败同时回滚依赖清单与生产锁。维护收据固定声明 `sendAttempts=0` 和 `runtimeModelDecisions=0`。普通模型命令或 Markdown 不得直接刷新摘要或切换锁状态。
