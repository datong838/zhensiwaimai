首次新群整链实操在群搜索阶段安全停止：搜索页唯一结果实际为「FEIBING NEO AI数字员工(18)」，Vision 将 `AI` 识别为 `Al`，旧逐字匹配得到0项，发送0、游标未推进。仅在本技能的群标题识别层增加严格视觉归一化：去空格并把拉丁上下文中的 `Al` 归一为 `AI`，之后仍须完整匹配目标群，尾部只允许括号成员数；搜索分区唯一、点击前同位置复核和进群顶部复核均继续执行。消息正文复制回读不采用该归一化，共享封板助手不修改。

下一轮在采集第1毫秒被 `chrome-ax-not-ready` 安全拦截，实测原因是系统同时运行用户长期登录 Chrome 与临时自动化 Chrome，旧初始化错误要求全机只能有一个 Chrome 主进程。改为遍历 Chrome 进程并只绑定“包含唯一标题为淘宝闪购服务商的标准窗口”的 AX 根；若0个或多于1个候选仍拒绝执行。不会关闭、重启或接管其他 Chrome，后续标签身份与 URL 守卫不变。

修复进程选择后，旧 `tabs()` 仍通过 AppleScript 查询系统默认 Chrome 实例，临时 Chrome 成为默认实例时返回 `service-tab-count:0`。将标签身份守卫统一到已绑定的同一 AX 根：每次动作前后递归读取唯一 `open.shop.ele.me` WebArea，并核验源站不变；不再跨进程调用默认 Chrome，也不切换或激活其他窗口。

同进程守卫生效后，详情抽屉标题先于字段节点完成渲染，旧逻辑只等待标题就读取，瞬时触发 `detail-label-not-unique:商家名称`；页面稳定后实测该标签唯一。详情读取改为要求全部固定字段标签及对应值连续两帧唯一、内容稳定后再解析，超时仍失败，不放宽身份交叉验证。

群名 `AI/Al` 归一化后首次真机定位报告顶部通过，但输入前截图仍是搜索结果页：搜索框自身包含完整群名，被旧顶部条件误判成群聊标题，随后清空编辑框报空对象。群聊页判据增加负向结构门禁：只要页面仍含「群聊」搜索分区或「创建新的群聊」就拒绝标题通过；必须点击唯一结果并离开搜索结构后，顶部唯一群名才有效。

持久会话复测显示微信当前搜索页不再提供旧版「搜索网络结果」分界，唯一目标群稳定位于「群聊」与「创建新的群聊」之间，旧候选函数因此返回0。搜索候选区改为必须从「群聊」开始，并以其后的「创建新的群聊 / 聊天记录 / 搜索网络结果」最早一项为结束边界；只在该窄区间接受唯一完整群名，聊天记录同名文本仍被排除。

群页与正文输入通过后，发送前复制校验的长按误中历史绿色气泡。证据表明随机剪贴板标记写入会改变输入法/布局，而旧逻辑继续使用写标记前的编辑框坐标。编辑器复制路径改为写入随机标记后重新截图并重新计算白色编辑区锚点，再执行全选与复制；气泡回读仍使用新气泡自身边界，不受此变更影响。

下一轮输入长度回读为102，而固定正文UTF-16长度为54，截图证实旧草稿未被 FastInput 一次清空广播完全移除后又追加正文。输入改为清空事务：首次清空后通过 `dumpsys input_method` 验证目标仍为微信且 selection 为0；否则仅在同一已聚焦编辑框有界发送退格并再次验证0，未清空绝不粘贴。正文粘贴后仍要求长度54和复制全文一致。

定时运行中已登录服务商窗口可被同一运行时读到，但执行器单次初始化偶发 `service-chrome-process-count:0`，属于 AX 窗口枚举瞬时竞态。进程选择改为最多4秒有界轮询，要求同一唯一服务商进程连续两帧稳定后绑定；0个、多于1个或不稳定超过预算仍拒绝执行，不把商家版窗口作为替代。

真实定时场景可能只保留已登录淘宝闪购商家版窗口而服务商标签被关闭。执行器在 Chrome 存在但连续观测不到服务商窗口时，只执行一次确定性恢复：在 Chrome 前窗口新建固定 `https://open.shop.ele.me/manager/base/home` 标签，随后仍要求服务商窗口连续两帧唯一及 `open.shop.ele.me` WebArea 守卫通过；不把 `melody.shop.ele.me` 内容当作新增商家数据源，也不关闭或覆盖原商家版标签。

服务商标签 URL 已正确但 AX 仅渲染平台标题、业务菜单为空时，旧路由立即按「代运营」导致0命中。新增一次性壳页恢复：激活已有 `open.shop.ele.me` 标签并重载固定服务商首页，等待「代运营 / 客户管理 / 意向商户管理」任一业务结构出现后才导航；超时仍失败，不盲点。

定时检查原先在采集前由外层强制要求手机在线，使“无新增”的纯浏览器 noop 也被数据线状态阻断。整链参数改为手机序列号可选：先完成采集与去重；消息数组为空时直接成功，不连接手机；仅当确有新增时，发送器才枚举并要求唯一已校准荣耀真机，否则停止且不推进游标。

多轮恢复可能保留多个同源服务商窗口，旧 snapshot 要求全进程只能有一个服务商 WebArea，触发 `service-webarea-not-unique`。改为在已绑定 Chrome 进程的窗口前后顺序中确定性选择最前服务商标准窗口，并只在该窗口内要求唯一 `open.shop.ele.me` WebArea；其他同源窗口不关闭、不操作。

## 循环与停止条件
准备阶段先做结构勘察，固化后再计时实操。每轮有独立run目录/日志与节点耗时。浏览器AX单通道，每动作前后守卫窗口和标签，禁止全局键鼠。采集总预算180秒、每状态6秒、最多50页；手机每消息60秒，只有导航和只读观测允许一次恢复，发送绝不自动补点。循环修复只针对有事实的问题，不同一失败无修改盲重跑。登录、锁屏、安全验证或设备物理断线需人工处理则如实说明，不绕过。

### 汉字OCR歧义的确定性恢复
不添加汉字替换或放宽全文标准。输入OCR不一致时，定位当前输入首行，长按→全选→复制，先将剪贴板置为随机校验标记，再回读微信实际复制文本与原消息逐字一致。复制后恢复光标到末尾，仍核验目标群和发送按钮。最新出站气泡OCR不一致时，以最新绿色气泡、发送前后不同及消息特征为边界，只长按本条气泡→复制，随机标记必须被完整消息替换；逐字一致后复核群名和空输入。该过程无再次发送，最多一次，纳入同一条60秒预算。

复制菜单实测包含黑底「剪切 复制 粘贴」，原OCR把它们合成一个文本框。新增本技能 scripts/ocr_control_label.swift，只用Vision识别候选文字的子串 boundingBox 精确定位「全选」「复制」，不按整块坐标比例猜菜单项。产物编译到本技能 .runtime，封板OCR不修改。

### 用户追加要求：OCR不能成为稳定性瓶颈
默认文字验收改为微信原文复制精确比较，OCR不再担任业务正文通过/失败的裁决。输入框通过已校准白色编辑区域几何定位，长按全选复制；发送后两帧最新绿色气泡位置/指纹稳定后直接复制全文，不再为OCR同字错误轮询8秒。OCR仅用于群名及全选/复制/发送等短控件定位。通知横幅起始位置实测可下移到y150，改为顶部350像素内的微信+刚刚联合证据，不能按y100硬界限漏判。
