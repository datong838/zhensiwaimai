## 1. 定位与拆分理由

R16（发优惠券）与 R01–R15（只读：截图 + 发文字）在五个维度本质不同，混在一条流里会互相阻塞：

| 维度 | 只读指标流 | 本流 |
|---|---|---|
| 副作用 | 无 | **真实发券、花门店资金；重跑 = 重复花钱** |
| 放行 | 参数齐全即可轮转 | **人工放行闸**：参数未确认禁止执行，首跑 dry-run |
| 耗时结构 | 单店单页截图 | 7 次表单 + 7 次创建 + 创建后验证 |
| 频率模型 | 20 天轮换、每日 1 指标/店 | 写操作不轮换，频率待 Q-R16b 拍板后单独建模 |
| 失败语义 | 重发即可 | **宁漏发不错发**；attempted 死锁先取证再选出口 |

**拆流收益**：只读指标流按 15 项继续推进采集器/灰度不受影响；本流等参数确认后独立启动，独立排期、独立放行、独立台账。

**「全部发完」的完成判据**（写操作必须有可核验的终态；01:23 置灰口径后修订）：入口先数**可点的发券按钮数 N**（置灰=已发过，天然跳过、不计入 N）⇒ N 个全部创建成功（营销记录 tab 新增 N 条 / 进行中 +N）才算整店完成；只要还有可点按钮没发成 ⇒ 缺一不进（缺的那条按 §5 死锁流程取证，不补发不重复创建）。**N 可能 < 7 甚至 = 0**——反馈与台账数量一律按实际创建数，禁写死「7 项」。另外：金额区间随机 ⇒ **每店每人群实际抽中金额必须落盘**（run 记录 + 台账），事后资金核对只认落盘值。

**0 可点门店**（7 个全置灰=都发过了）：不创建、不反馈（遵「0 条绝不外发」铁律——无新活动可截，截图反馈等于说谎），run 记录按 skipped_idempotent 处理。

## 4. 人工放行闸（资金操作红线，★★★★）

1. **参数未确认前禁止执行创建**——大同原话「等我确认后再」。这不是暂缓，是硬闸；`deliver/issue` 缺任一参数 ⇒ `blocked` 退出，绝不默认放行。**进度（01:30）**：Q-R16a 金额已暂定（1–3 随机/有门槛 2–3/无门槛 1–2）；余 Q-R16e（券类型）、Q-R16f（有效期/周期/时间是否全默认）⇒ 闸门仍关。
2. **首跑 dry-run**：只开到表单页、不点「立即创建」→ 截图人工过目 → 才放行。
3. **重复创建防护（Q-R16d，01:23 口径已被 E08 实测证伪，见 §5 第 4 条 + F7）**：大同 01:23 说「已发过⇒置灰」，但 02:0x 实测店已发 4 人群（进行中）而按钮仍全部可点 ⇒ **UI 置灰不可依赖**。现行纪律：创建前读营销记录 tab，该人群已有「进行中」活动 ⇒ 跳过（方案待大同拍板 F7，拍板前维持禁止创建）。可点按钮集合快照仍作为运行证据保留。
4. **一键制动**：沿用指标流 §3.13 的 `--disarm` 机制，异常可立即停。
5. **创建成功判据 = 页面状态，toast 不可信**：营销记录 tab 出现新活动 / 进行中活动数变化（Element UI toast 可能是假阴性）。
6. **整店完成判据 = 计划集合全发完（N/N，N≤7）**：入口数的可点按钮（减去 F7 防重跳过项）全部创建成功才进反馈（§3.4）；任一失败 ⇒ 该店整体标 blocked，不部分反馈（部分反馈会让门店误以为活动只该有这些）。按 E08 实测，置灰跳过占比应为 0——跳过一律以营销记录为准，不以按钮灰不灰为准。

## 5. 防重发与资金安全（★★★★，写流特有用）

沿用指标流 `deliver_metric.py` 的 marker 三态（verified / unknown / blocked），但**升级两条**：

- **attempted 死锁处理**（指标流 #87 铁律）：先取证「活动在不在」（营销记录页）——在 ⇒ `conclude` 结论化 verified，绝不重发；不在 ⇒ 双层 void + void-receipt + 重发。**发券场景下错发的代价是真金白银，取证一步不能省**。
- **同日重跑必冲突**：同店同人群同参数的活动 marker 已 verified ⇒ 重跑直接 `already_verified` exit 0，不进重复创建。
- **UI 置灰 = 第三道护栏（已被实测动摇，见下条）**（大同 01:23）：即便前两道都漏，置灰按钮也点不动——但护栏不能当判据用，仍以「创建前快照可点集合 + 创建后复核变灰」为运行证据。
- **★★★ 已发人群防重护栏（02:02 E08 实测发现，Q-R16d 补充条款）**：实测店 542633444 于 8-31 已对 4 个人群创建过满减券（无门槛减 2，**进行中**，有效期至 2027-08-30），但这 4 个人群的「发券」按钮**仍全部可点（disabled=false）**——「已发过⇒置灰」在该店被证伪（至少不随活动存续立即置灰）。⇒ **UI 置灰不可作为唯一防重依据**。待大同拍板（F7）：方案② 推荐=脚本自建防重名单——创建前读营销记录 tab，该人群存在「进行中」活动 ⇒ 跳过（run 记 skipped_idempotent）；在拍板前，任何创建动作维持禁止（§4 放行闸不受影响，闸门仍关）。

## 7. 排期（频率已定=每店每月一次；置灰解除条件实测后定稿）

**已定**：可点的全部发，不轮换不挑选（01:21 范围 + 01:23 置灰口径）⇒ 单店 ≤7 次创建（置灰跳过）。
**执行频率（Q-R16b，大同 01:28 已定）：每店一个月一次。**（仅为容量测算口径，不是排班表——见文首 01:34 明令）

已定的单店耗时结构：

- 切店 24.6s（切换器实测）+ 精准营销页加载（待实测，预期 2–3s）+ N × (开表单 + 抽金额 + 填参 + 创建 + 验证) + 反馈截图 1 次 + 发送 + 回复「全部发完优惠券」。
- 参照：只读流单店 3 指标 = 41s（切店 24.6s 占 60%）；本流 ≤7 次表单创建是纯增量，**即便每次只 15s，单店也 ≥2.5 分钟**，400 家全天跑不完 ⇒「每店每天」确实不成立（与 01:28 拍板的每月一次互相印证）。
- 与只读流的差别：只读流 400 家 × 3 指标 = 4.6h/天（实测可行）；本流单独建模，**不并入指标流 §4 的 15 指标口径**。

**频率模型（每店每月一次，01:28 定；仅为容量测算，不是排班表）**：
- 863 家营业中池 ÷ 30 天 ≈ **29 家/天**；单店 ≥2.5 分钟 ⇒ 采集+创建 ≈ 1.2h/天，加发送 29 家 ≈ **1.3h/天**，测算上宽裕（只读流同期 4.6h/天）。
- ★置灰问题已被 E08 实测改写（02:0x）：不存在「随活动置灰」——已发 4 人群（进行中）按钮仍全可点。原「第二个月 0 可点空转」担忧作废；真风险反转为**第二个月重复创建同人群券**（平台不阻止，高价值忠诚已并存 2 个活动）⇒ 防重方案挂 F7（脚本按营销记录跳过），频率模型不受影响。
