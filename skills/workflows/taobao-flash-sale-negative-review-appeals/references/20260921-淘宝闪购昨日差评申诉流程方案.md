# 淘宝闪购昨日差评申诉流程方案

## 目标与边界

在臻肆外卖运营后台的“评价&负反馈 → 差评列表”中，处理淘宝闪购渠道昨天仍为未申诉的差评。只提交页面明确标记“自动申诉已关闭”的条目；申诉内容优先采用平台在申诉弹窗中提供的回复，回复输入区域为空时才使用“骑手送餐慢”。

本方案不授权自动申诉开启条目、其他平台/日期、非差评列表页面、批量点击、未知状态重试或未授权的微信群消息。图片仅作为页面布局和字段含义的参考，不是页面当前状态或操作授权。

## 依据与口径

用户提供的截图显示：渠道可切换至“淘宝闪购”，时间可选“昨日”，状态可选“未申诉”；卡片底部显示“自动申诉已关闭”和“立即申诉”；申诉弹窗展示可编辑的“申诉内容”和平台的申诉类型选择。实际处理必须以本轮实时可见页面为准。

业务日期按 `Asia/Shanghai` 的昨天计算。一个待处理条目至少应有可稳定辨识的门店、评价日期和页面唯一标识。评价文本只作最小必要摘录写入本地临时记录，避免扩散顾客信息。

## 状态机与防重

```text
discovered → prepared → submitted_once → verified_submitted
                           └──────────→ unknown / blocked
discovered → skipped
```

`prepared` 表示临时 Markdown 已写入，不等于已提交。点击确认前状态记为 `submitted_once`；任何点击后页面未明确给出同条目的已提交状态，立即落为 `unknown`，不得再次提交。平台状态明确为“申诉中”或等价已提交状态才可记作 `verified_submitted`。

## 临时记录合同

路径固定为：

```text
/Users/ddt/work/projects/ai_agent/zhensi_waimai_back/records/taobao-flash-sale-negative-review-appeals/YYYY-MM-DD/<记录键>.md
```

每个文件包含：业务日期、记录键、门店、评价日期、星级、评价最小摘录、页面申诉状态、自动申诉状态、平台建议回复、最终申诉理由、状态、开始/提交/核验时间、页面核验结果和异常原因。不得保存登录信息、Cookie、手机号、完整顾客档案或不可脱敏的订单信息。

## 人工交互与验收

1. 进入目标页面后回读并核验渠道、日期、未申诉状态和登录可用性。
2. 对每个候选先建临时记录，再确认“自动申诉已关闭”。
3. 点击“立即申诉”后只打开弹窗，等待平台智能申诉完成；连续两次读取弹窗文本一致后，核验弹窗归属、实际文本和申诉类型。不得将弹窗刚打开时的短暂空白当作无内容；只有页面明确完成或等待超时且文本区域仍为空白时，才填“骑手送餐慢”。
4. 将弹窗的实际申诉内容、类型和剩余次数写回该条临时 Markdown 后，才一次确认一条；确认后回读列表的权威状态。
5. 结果明确则更新本条临时记录；结果不明停止批次，并留存 `unknown`，不再次确认申诉。

验收以每个 `verified_submitted` 文件中的同条目页面状态为准。当前未申诉列表中该目标门店移除，且未申诉总数同步减少，可作为同条目已进入平台申诉处理状态的组合证据；不以按钮变灰、弹窗关闭或 toast 单独判定成功。

## 批次交付

批次结束后，将当天临时 Markdown 记录汇总为一份 Excel：顶部保留已核验提交、跳过、阻断、未知的事实计数；明细只展示 `verified_submitted`、`blocked`、`unknown`，不展示 `skipped`。跳过条目仍仅保留在本地临时 Markdown 中，不计为人工申诉。Excel 经完整群名预检、防重和发送回读后交付至“FEIBING NEO AI数字员工”；流程说明保留在本地作为审计依据，不作为群附件。

### 微信接入实现

新增一个固定工作流标识 `taobao-flash-appeals`，只允许发送至“FEIBING NEO AI数字员工”，载荷固定为当天 `淘宝闪购差评申诉汇总-YYYY-MM-DD.xlsx`。桥接层校验完整群名、文件类型、数量、文件名、业务日期、绝对路径和独立账本；发送器只接收 `--execute` 或无副作用 `--self-test`，不接受群名、日期、端口或任意文件参数。任一已有 attempted/unknown 事件只允许对账，禁止再发。

### 已准备附件直发通道

若群标题已精确回读为“FEIBING NEO AI数字员工”，输入区仅显示本事件冻结的唯一 Excel 附件、附件名称和大小与冻结载荷一致、发送按钮可用，则该附件已完成准备，应直接点击“发送”一次并回读新文件消息。此状态不是草稿异常，不再重新上传、反复清空或重新搜索群。任一条件不满足才进入阻断和只读诊断。

## 18:30 昨日申诉闭环与日报

每天 12:30、14:30、16:30（`Asia/Shanghai`）执行昨天差评申诉巡检：处理新增的符合条件条目，并将平台智能申诉内容和页面核验写入当天临时 Markdown。18:30 是日报汇总时点，不是无条件发报时点。执行顺序固定为：

1. 读取昨天的临时记录与页面状态；若还有符合“自动申诉已关闭”的未申诉条目，继续完成逐条申诉、记录与页面核验。
2. 对自动申诉已开启条目记录跳过；对登录、验证码、风控等必须人工处理的异常记录阻断原因。
3. 仅当昨天全部候选均处于 `verified_submitted`、`skipped`、`blocked` 或 `unknown` 的终态，且不存在可自动恢复的未完成条目时，生成并发送日报。
4. 日报发送可晚于 18:30，但必须在申诉闭环完成后立即进行，并以业务日期绑定唯一发送事件；发送后回读文件消息或统一发送收据。

日报包含业务日期、已核验申诉数、跳过/阻断/未知数、每条最小必要标识与理由、发送结果。任何 `attempted`/`unknown` 投递仅允许对账，不补发。微信群发送异常不影响已核验的申诉事实。

## 风险与控制

| 风险 | 控制 |

## 2026-09-22 巡检执行器补强方案

### 现状与最小变更

巡检页面可能同时出现多条“自动申诉已关闭”候选。为避免依赖临时脚本或人工连续点击，新增固定执行器 `scripts/appeal_executor.mjs`，只覆盖本 Skill 已授权的逐条申诉与临时 Markdown 记录，不改变日报生成、微信发送或其他金鲨流程。

### 固定门禁

1. 浏览器只能连接 `http://127.0.0.1:9232`，且该端口必须只有一个 `https://data.guoshuyufen.com/` 页面；不启动、重启或切换浏览器。
2. 页面固定为 `#/negativeAnalyse`。进入差评页前必须先在首页回读并锁定左侧渠道上下文“淘宝”，再选择平台单选值淘宝闪购 `2`、上海时区昨天和“未申诉”。左侧上下文、平台、日期或状态任一回读不一致均在业务写操作前停止；不得仅切换顶部平台单选而沿用上次页面的左侧上下文。
3. 只接受同一卡片同时包含“自动申诉已关闭”和“立即申诉”；自动申诉已开启只生成或校验 `skipped` 记录，不打开弹窗。
4. 记录键沿用既有合同，由门店、评价日期与评价最小摘录生成稳定 SHA-256 摘要前 12 位。若同键已为 `verified_submitted`、`unknown` 或 `blocked`，禁止再次确认；`skipped` 仅在实时状态仍为自动申诉已开启时保持跳过。
5. 合格条目必须先原子写入 `prepared` 临时 Markdown，再点击“立即申诉”。弹窗内容需连续两次稳定读取；仅超时仍为空时写固定兜底“骑手送餐慢”。确认前再原子写入 `ready_for_confirmation`。
6. 每条最多点击一次确认。点击前先落 `submitted_once`；点击后只以同条目从未申诉列表移除且总数减少，或页面明确出现“申诉中”等权威状态为成功证据。结果不明确时写该条 `unknown`，禁止对该条重试；后续新一轮可在重新完成固定筛选回读后跳过该未知条目，继续处理其他尚未触碰且仍符合门禁的独立候选。
7. 每轮输出机器可读收据，分别统计 `verified_submitted`、`skipped`、`blocked`、`unknown`；执行器不生成日报、不调用微信能力。
8. 若已通过 `--inspect` 回读到候选，但 `--execute` 的页面准备阶段偶发返回空列表，不得将空列表当作“无待办”。在不进行任何点击前，执行器最多重新进入并回读同一固定筛选 3 次；只有连续 3 次均为空才按“本轮无候选”结束。任一非空回读立即按既有逐条门禁继续处理，既有 `verified_submitted`、`unknown`、`blocked` 仍禁止重发。
9. 差评列表可能分页懒加载：页面总数是全部筛选结果，DOM 卡片数可以是当前页子集。执行器允许“当前页卡片数小于等于总数”，但拒绝空页与卡片数超过总数；每个操作仍只使用当前页可见卡片，并在确认后核验目标卡片移除及全量未申诉总数递减。

### 自测与生产验收

- `--self-test` 覆盖稳定键、状态解析、自动申诉门禁、终态防重、空列表重试合同和 Markdown 必填字段，不连接浏览器。
- 真实运行先以 `--inspect` 完成非写入筛选与候选清单回读，再以 `--execute` 逐条处理；生产验收以临时 Markdown 回读和页面权威状态为准。
- 执行结束将页面恢复到金鲨首页；恢复失败只记录为清理告警，不改变已核验的申诉事实。

### 问题与边界

首版 `build_batch_excel.mjs`、`deliver_batch.mjs` 及统一微信 `taobao-flash-appeals` 注册项固定绑定 2026-09-20，只能复现首次验收数据，无法安全执行后续日常汇总。本次仅把业务日期、当天输出目录和记录读取改为上海时区动态计算；完整群名、单个 Excel、独立账本、事件键、`attempted/unknown` 禁止重发及统一发送器均保持不变。

### 最小实现

3. `deliver_batch.mjs` 与统一微信桥接共同绑定上海时区昨天、当天输出目录、完整文件名、单文件、固定群、固定账本和稳定自动化授权引用；不同日期使用不同 marker，路径或日期不匹配时在微信动作前失败关闭。

- 申诉执行器 `--self-test` 和 `--inspect` 通过，实时 `closedCandidates` 为空；本地所有候选均为四类终态。

## 2026-09-24 全量状态日报口径

在“全部”统计外，日报头部固定并列展示页面当前的“申诉成功”“申诉失败”“申诉中”“未申诉”条数。五个数字均从同一渠道、同一业务日期的差评列表页面直接读取；“全部”继续作为 Excel 明细行数的唯一强校验，其余四项仅反映页面状态计数，不用于重算或拼接明细，避免页面状态标签与全量明细之间的异步差异影响报表完整性。未申诉条目是否均为自动申诉已开启，必须逐条以页面卡片事实另行说明，不能仅由未申诉计数推断。

## 2026-09-25 空列表稳定性恢复方案

### 现象与根因

当页面在已完成“淘宝闪购 / 昨日 / 未申诉”固定筛选后暂时返回 `total=0`、`cards=0`，现有稳定性判定把空键集合视为永不稳定，提前抛出 `candidate-list-not-stable`。这绕过了既定的“空列表最多重新进入并回读 3 次”门禁，使可恢复的页面暂态被误报为执行失败。

### 最小修复与不变项

稳定性判定改为连续两次读取到相同集合（包括空集合）即可返回；返回空集合后，仍仅由既有 `shouldRetryEmptyList` 驱动最多 3 次重新进入与回读。非空候选的资格、稳定键、临时 Markdown、单次确认、提交后权威回读及 `unknown` 防重规则均不变。连续 3 次均为空才按无待办结束；任一回读非空继续原有逐条门禁。

### 验收

离线自测须保持通过；新增测试覆盖空集合在第二次相同读取时可交给三次重试门禁。实际运行仅在页面回读满足固定筛选且连续三次为空时报告无待办；否则不以空结果结束。

## 2026-09-28 折叠导航入口门禁顺序修复方案

### 现象与根因

金鲨首页在左侧导航折叠时，页面仍处于已登录的 `#/businessData/realTimeData`，但“外卖”“评价&负反馈”菜单文本不渲染在可见 DOM 中。现有执行器在展开导航前即要求这两个文案可见，因而在无登录、验证码或风控异常时误报 `jinsha-entry-or-login-gate`，无法进入既有的渠道上下文选择与固定筛选门禁。
