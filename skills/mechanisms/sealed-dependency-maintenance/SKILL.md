# 受控依赖维护

改动前复习产品/技术方案，完善本次方案文档并声明具体文件目录。先读取相关包现行维护器、release policy、授权和依赖清单，不照搬历史授权常量。

## 判定与执行

1. 以真实维护器inspect及实际SHA诊断漂移，枚举所有上游/下游消费者（JSON、MJS常量、安装入口、历史摘要绑定）。先确认文件是否受封印；普通文件不虚构再封印要求。
2. 有专用维护器就用专用受控通道；核对授权原文、范围、有效期、允许字节及本次差异。禁止为过门删校验、裸改封印、扩大范围或把旧授权当新授权。
3. SEALED、UNSEALED_ACCEPTANCE、allowedBusinessDate分别核对。维护动作零发送；测试GREEN或摘要一致不能冒充真实非空验收、重封印或业务完成。
4. 上游维护后逐个复验下游实际钉值与原校验器，不能只搜索旧摘要就宣称全链一致。至少覆盖共享微信依赖、商家executor-lock、Top10 runtime-policy及差评release policy的受影响部分。
5. 测试隔离目标群和业务身份，禁止真实传输与生产状态写入；测试不能绕过原安全边界。验证失败只回滚本次代码/配置，不回滚生产账本、游标、授权历史或未知发送。
6. 维护收据持久保存仓内，记录变更、测试、门禁及真实未完成项。真实业务验收由原主任按原排班/原control执行；attempted/unknown只读对账，不以维护为由重发。
