## 当前事实

### 路由覆盖

`registry-routing.json` 当前有14条：

- 9条由 `registered_ui_routes.WORKFLOWS` 做群、类型、数量和原账本事件路径校验；
- `merchants`、`meituan-customer-reply-daily` 由 `wecom_ui_queue.enabled` 的原专用合同校验；
- `negative-reviews-summary` 目前由 `ALLOWED` 仅按 workflowId 直接放行；
- 两条历史单件修复通道 `jinsha-reports-taobao-repair-20260917/20261023` 被明确拒绝，不扩成常规生产路由。

因此12条非修复登记流都有运输入口，但 `negative-reviews-summary` 的队列门弱于其原桥合同：错误群、空载荷或错误事件路径只要 workflowId 相同就会被 `ALLOWED` 放行。合法原桥仍会先校验，但队列本身是授权边界，不能依赖调用方永远正确。

`dependency_maintenance.py inspect` 当前返回 `clean`、`candidateFileCount=38`，仅说明已登记的38个文件未漂移。按 `executor → wecom_adapter → wecom_ui_queue → native_ui_post` 解析出的26个本地Python模块闭包和直接配置/脚本，以下10项是现役安全依赖但未被任何现行摘要绑定：

其中前9项属于执行/证据/拒绝门，后续应通过原依赖维护器纳入共享摘要；`registry-routing.json` 是2026-10-03明确外置的日常路由数据，旧设计要求“零封印”，应改为独立的严格schema、允许集合和变更审计，而不是直接混入代码封印。

## 本轮最小实现

1. 将 `negative-reviews-summary` 加入 `registered_ui_routes.WORKFLOWS`。
2. 删除 `wecom_ui_queue.ALLOWED` 的无条件放行分支，使该流与其他登记流共用原群、kind/count、独立账本路径校验。
3. 增加合法请求保持通过、错误群、空载荷、错误账本事件路径拒绝的测试；已有原桥、载荷、授权、防重和发送实现不变。
4. 落盘只读审计证据，记录路由分类、依赖闭包、当前摘要覆盖和后续受控维护范围。
