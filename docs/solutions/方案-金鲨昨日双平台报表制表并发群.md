# 金鲨昨日双平台报表制表并发群方案

> 现行规则（2026-09-04 用户更新）：180秒仅为效率目标，不是业务终止线。软故障恢复当前节点，保留本轮文件/哈希/原始起点，直到两份文件交付；超时与维护耗时如实计入，不用新轮替代未完成交付。身份、群、文件不符仍禁止发送。下文旧版“到期即中止”“结束失败轮次再新建”的考核记录仅作历史，不再执行。当前唯一业务入口为 `daily-jinsha-reports-to-business-wechat`；公共封板实现已收纳到隐藏内部底座。

## 产品目标

从已登录的金鲨后台分别导出美团外卖、淘宝闪购的 Asia/Shanghai 昨日报表；按客户表补齐「运营总监」「客户等级」，保持用户指定模板的列序、公式与格式，生成两个独立 Excel；最后仅发送到普通微信「臻肆测试群」并逐文件复验。

## 数据与字段合同

- 业务日期：执行日减一天，两个日期端点相同。
- 美团：保持参考图的默认平台、数据类型、汇总方式、日期、方案和指标选择。
- 淘宝闪购：保持默认选择，并额外确保「单均到手」「单均实付」均为选中。
- 关联键：美团 `店铺ID` → 客户表 `美团ID（完善）`；淘宝 `店铺ID` → 客户表 `饿了么ID（完善）`。
- 补充列：`运营总监`、`客户等级`。ID 统一按去空格后的文本匹配，禁止浮点化或科学计数法破坏标识。
- 模板只提供列序、公式、样式、宽高、冻结、筛选等格式；业务行全部来自本次实际下载。
- 条件格式硬门：店铺评分 `<4.3` 用红色字体；营收 `0–300` 用黄色填充；客户等级 `A`、`S` 用红色字体。
- 模板数据条继续继承：美团为月售销量、营收、曝光人数、进店率、下单率、有效订单、新客复购率；淘宝闪购为有效订单、营收、曝光人数、进店率、下单率、近30天复购率。其余列宽、行高、字体、边框、数字格式、冻结和筛选也按各自模板。
- 模板历史业务行中由旧值形成的静态红黄着色不能直接带入新数据；以模板首条正常业务行统一复制基础格式，再由本次值和条件格式重新计算显示。
- 两个平台成品都按「营收」数值降序；相同营收保持下载文件原始顺序。制表收据记录首尾营收并验证全列单调不升。
- 客户表重复 ID 采用首条匹配（VLOOKUP 语义），记录同值重复与冲突计数；下载表缺少 `店铺ID`、客户表缺少目标列、业务日期错误、必要指标缺失时停止制表，不猜测。

## 技术方案

### 桌面宿主确认（2026-09-03 用户纠正）

本流程金鲨是用户已登录的桌面 App，不是 Chrome 标签页。当前实测运行路径为 `~/Downloads/金鲨数据 2/金鲨数据.app`，进程为该包的 `Contents/MacOS/jinsha`，窗口为「臻肆外卖运营」。App 内部 HTML 出现 `data.guoshuyufen.com` 不改变桌面宿主身份；Chrome 同域名网页不能代替该 App，Chrome 的超时也不能证明当前桌面 App 不可用。

准备阶段先通过运行进程及窗口确认实际 App，使用 CUA `getApp` 的完整路径绑定；安装目录可能变化，历史 AppTranslocation 路径不得长期缓存。发现旧绑定失效时重新定位运行实例，不先打开浏览器，不擅自启动同名旧安装包。当前路径是本机校准记录，不是所有机器的通用路径。

### 1. 金鲨下载执行器

唯一桌面控制通道使用 CUA REPL，绑定用户已登录的金鲨桌面 App；不得使用旧 sky 下载器或 Chrome 同域名网页替代。

主链路：`前台/固定窗口 → 美团平台 → 多店数据 → 按日 → 昨日 → 方案与默认指标复核 → 下载一次 → 新文件稳定/XLSX校验 → 淘宝平台 → 多店数据 → 按日 → 昨日 → 默认指标复核 → 单均到手/单均实付复核 → 下载一次 → 新文件稳定/XLSX校验 → 原子收据`。

下载前记录目录基线；每个平台按钮最多点击一次。仅接受动作后新出现、大小连续稳定、可解析且包含 `店铺ID` 的 Excel。结果未知时不补点。

### 2. 制表执行器

使用工作区提供的 `@oai/artifact-tool` 导入实际下载、客户表、模板和成品参考。先读取并渲染模板/参考，再生成两个成品。

主链路：`结构审计 → 规范化ID → 首条匹配关联 → 写入运营总监/客户等级 → 营收稳定降序 → 按模板列序/公式/格式生成 → 关键范围检查 → 条件格式/公式错误扫描 → 全表渲染 → 导出 → 哈希收据`。

输出目录固定为 `../../../臻肆/报表/`，文件名分别为：

- `美团全部_<昨日>至<昨日>.xlsx`
- `淘宝闪购_<昨日>至<昨日>.xlsx`

不得覆盖既有同名文件；如已存在，先比对哈希和业务日期，只有确认是本次合法产物才复用，否则停止。

### 3. 微信文件发送执行器

复用已校准的荣耀真机、主微信选择、完整群名搜索和 OCR 复验。文件先推送到手机专用目录并刷新媒体/文件索引；通过聊天页「+」进入文件发送入口，以完整文件名选择，不按固定间距猜测。

主链路：`物理设备核验 → 主微信 → 搜索完整群名 → 顶部群名唯一复核 → 发送前打印两个成品绝对路径/大小/哈希 → 逐文件：推送、完整文件名选择、发送一次、新文件气泡文件名复验 → 最终双文件复验`。

本轮用户已明确授权普通微信「臻肆测试群」和上述两个成品文件，满足完全相同的群名、文件路径和哈希时不重复申请。群名不唯一、文件名不匹配或发送结果未知立即停止；已确认发送的文件不得重发。

## 迭代与完成判据

### 手机文件入口修复（2026-09-03 实证）

ADB 推送后先核验手机文件大小及 SHA-256。微信「选择文件」默认「聊天」不是手机目录；必须走「手机文件 → 选取 → 系统文件选择器 → 内部存储 → Download → zhensi_reports」。系统选择器能提供完整文件名的 UI 树，按精确文本选择，不凭截断的可视文件名猜测。微信加号面板动画必须等两帧稳定，文件入口在音乐左侧，不能混用滑动前后坐标。

文件页就绪必须同时证明 FileSelectorUI 和页面标签，不能把「非 LauncherUI」当作成功。每次外部发送前原子写入 in-flight 状态；不确定结果不自动重发。恢复后跳过已确认哈希，仅继续未发送文件。测试阶段允许从已校准的文件选择页面继续，不必重走下载和制表。

系统文件选择器点击内部存储后，要等待可滚动目录树就绪再滚动到 Download，不以点击返回当作页面完成。2026-09-03 用户核验：同一已发送美团文件在手机微信预览不显示条件格式，下载到电脑后显示正常；这不是未保存或发错文件。验收分层为文件哈希/完整文件名/大小、数据和保存后的格式规则、桌面实际打开效果；手机预览仅用于传输与内容核验，不能单凭不支持条件格式的预览触发重发。

目录滚动应绑定系统选择器的 `com.android.documentsui:id/dir_list`，同时校验「HLK-AL00上的文件」标题和两次稳定存在；泛化的 `scrollable=True` 可能先命中正在退出的抽屉列表，产生假就绪。

已复现根因：位于内部存储时，标题栏与侧栏同为 HLK-AL00。侧栏选择必须同时绑定 `android:id/title` 和完整文字，并等待 `roots_list` 消失；单独按文字会点到后方标题栏，导致抽屉未关闭。

制表保存后新增只读验证：重新导入实际磁盘文件，比对表头和全部业务行；检查 XLSX 中 7/6 条数据条及 3 条业务高亮规则确实存在。不能只检查导出前的内存预览。发送最终复验提供 `--verify-only`，不导航、不选文件、不点击发送；单元测试覆盖错群、错日期、错大小、重复标题及已发送/未知结果禁止重发。

双文件同屏复验发现：OCR 会把扩展名 `.xlsx` 中小写 l 误读为大写 I（`.xIsx`），而日期、平台、大小均正确。仅对这一扩展名已证实混淆做规范化，禁止模糊化群名、业务日期和平台名称；保留原始截图。该误判不触发重发。

每个执行器先离线自测，再真机/真实页面分段实操；发现偏差只修复已证实缺陷，然后重跑该阶段。分段通过后执行一次端到端考核。
