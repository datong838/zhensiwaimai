# F11-4 缺陷登记：closeKnownJinshaPopup 只认「新功能上线」文案，版本公告换文案即失效

> 提出：监理（2026-10-08 22:58） · 状态：**待车间/大同排期，未改码**
> 性质：**预防性缺陷**（今日未真实触发，非当日故障原因）
> 归属：金鲨岗（执行器 owner）

## 1. 缺陷描述

`background_browser_executor.mjs` 的 `closeKnownJinshaPopup()` 把「已知可关闭的金鲨公告弹窗」**硬编码为单一文案**：

```js
const popup = page.locator('.upload:visible').filter({ hasText: '新功能上线' });
if (await popup.count() === 0) return false;          // ← 文案不匹配 ⇒ 静默放过
if (await popup.count() > 1) throw new Error('jinsha-known-popup-not-unique');
const close = popup.getByText('关闭', { exact: true });
if (await close.count() !== 1) throw new Error('jinsha-known-popup-close-not-unique');
```

**两个问题：**

1. **识别面过窄**：只要站点把版本公告文案从「新功能上线」改成别的（例如 V5.6 的公告文案），
   `.upload:visible` 遮罩仍在，但本函数 `return false` 静默放过 ⇒ 上传/切 tab 全部被遮挡，
   报错会落在**毫不相关**的位置（如 `jinsha-tab-not-unique`、`jinsha-data-upload-menu-not-unique`、
   或超时），定性严重偏移。
2. **静默失败无信号**：与同函数内的 `jinsha-known-popup-not-unique` / `...-close-not-unique`
   不同，「未匹配到已知弹窗」既不计数也不记 `pitfalls`，**回执里查不出原因**。

## 3. 建议修法（待批，未实施）

三个改点，均在同一函数，建议一次做完：

| # | 改法 | 说明 |
|---|---|---|
| 1 | 把单点 `hasText` 换成**白名单正则**：`/新功能上线\|版本更新\|更新公告\|V\d+\.\d+.*上线/` | 判据必须可枚举、可审计，禁止写「包含 xx 即关」的模糊匹配 |
| 2 | 新增 **未识别兜底**：`.upload:visible` 存在但文案不在白名单 ⇒ **抛明确错** `jinsha-upload-overlay-unrecognized` 并写 `pitfalls`（含弹窗 innerText 前 200 字） | 今天正是因为「没单据」才花时间找错方向；要有可定性信号 |
| 3 | 无论走哪条分支都记 `receipt.knownPopupCloseAttempts` 与 `receipt.popupObserved`（文案） | 供下次回执直接分辨「没弹」vs「弹了没认出来」 |

**红线：** 关闭动作只能用于「已确认的非业务遮罩」，禁止对业务元素（如真正的上传弹窗）误关。
未知文案**必须 fail-closed 抛出**，不得默认关闭（对应 10-04 起「0 条/空表不外发」同族的保守原则）。
