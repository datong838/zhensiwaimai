# 每日新店工作流：识别与微信群通知阶段方案

本方案只覆盖当前已授权的「新店识别 → 当日记录 → 指定微信群通知」阶段。用户说明完整工作流还有后续阶段；后续内容需取得具体规则后另行设计，不以本阶段通过代替完整流程完成。

## 业务目标与来源

每天北京时间 10:30，从金鲨「外卖 → 数据中心 → 实时数据」检查美团、淘宝两个渠道。以各店铺「店铺头像」列实际显示的开业天数为准，仅把 0、1、2、3 天列为命中。美团先选「新店」再逐行核对；淘宝无「新店」，先切到 50 条/页并检查全部分页。「新店」筛选可能包含大于 3 天的店铺，不能直接当作结果。

当日记录固定在 `zhensi_waimai_back/records/new-store-identification/YYYY-MM-DD_新开店铺识别.md`。每条命中写渠道（仅「淘宝」或「美团」）、店铺名称、页面原样开业天数、来源页码与核验时间。没有命中须有完整页数和行数证明；页面或字段不确定时记为未完成，不写「无新店」。

用户指定群为普通微信群「FEIBING NEO AI数字员工」。有命中时发送一条纯文字消息，每店一行。自本日已发消息之后的新发送，格式固定为 `渠道  店铺名称  新店铺（开业X天）`，例如 `淘宝  伊戈塔可(雨花店)  新店铺（开业3天）`；不加标题、解释或截图。无命中不发送。2026-09-28 已发送的旧格式正文保留在当日记录，不能因格式修改重发同一业务日事件。

## 实现边界

- 新增独立 Skill `skills/daily-new-stores-opening-to-wechat/`。`SKILL.md` 说明入口和判据，浏览器采集与业务编排由固定代码执行。共享微信技能的定位、输入、发送、回读、防重保持原实现，不新增手工微信分支。
- 浏览器只连接用户指定的 `127.0.0.1:9232` / `jinsha-business`，不启动或重配 Chrome；复用现存唯一可识别的金鲨标签。若其停留在其他金鲨菜单，通过页面「数据中心 → 实时数据」导航；不反复打开链接、不刷新或关闭该标签。若有多个候选则阻断并报告歧义，不猜测或切换其他任务标签。页面如出现「新功能上线」遮罩，仅在目标标签点「关闭」后继续；不触碰上传、数据修改或其他标签。执行中校验站点、渠道、筛选、每页条数、总数和末页。
- **页面契约变更（2026-09-30 金鲨前端改版）**：渠道切换 tab 由实时数据页筛选行移入侧边栏容器（`sidebar-container > cut > .cutli`），现有「美团 / 淘宝 / 京东」三个 tab（京东为新增，不在采集范围）；**侧边栏收起时 `.cutli` 整体不在 DOM**。触发条件实测为窗口宽度 < 992px 时应用切到移动抽屉模式、侧边栏默认收起。采集器在采集前增加 `ensureChannelTabsVisible`：仅在 `.cutli` 缺失时点击侧边栏汉堡按钮的**可点击 `svg.hamburger`**（外层 `.hamburger-container` 为 0 尺寸容器、点击无效，故不绑父级、按全局唯一匹配），展开侧边栏后 `.cutli` 出现；展开后仍走原有 `count!==1` 唯一性闸门；其余判据、筛选、分页与双轮对账契约不变。
- 采集器写完收据后结束自身连接进程，避免残留 CDP 会话；不调用关闭共享 Chrome 或原标签的操作。
- 采集器逐页按可见表格单元格提取店名与开业天数。每页校验页码、条数、字段非空和筛选状态。淘宝至少做两次完整扫描，最多三次；仅相邻两次总数与命中集合一致才给出结果，持续不一致时保留阻断收据，不宣称全量结论。美团筛选后仍逐店核对，且不得误选「简版」。
- 运行入口持有本工作流独占锁，防止定时任务与手动复跑同时翻动同一标签；锁被占用时直接阻断。目标金鲨标签不得被其他任务同时操作；若页面状态在扫描中变动，按校验失败处理。
- 成功机器收据包含渠道、总数、页数、逐页行数、命中候选与耗时；失败收据记录阻断原因和耗时。Markdown 只由经过校验的完整收据生成，不能用截图或模型推断填补缺失行。
- 群发送走统一 `wechat-messaging` 的 **Windows 网关 HTTP** 通道（`windows_adapter.WindowsAdapter`，Mac → HTTP 8731 → Windows 10 微信驱动），与 jinsha / negative-reviews / top10 / taobao-appeals / ⑪ 共用同一条出站通道；**不触碰任何封印文件**（本技能 `workflow.py` 不在封印清单，直接复用已封印的 `windows_adapter`）。事件身份固定为业务日期加目标群，正文摘要由当日命中集合产生；落盘 `verified` 收据（含服务端回读锚点 `windows-readback-text-anchor`）才把当日记录改为已发送。幂等依靠本技能 `.runtime/new-stores-send-ledger`：发送前检查同一业务日的所有记录，同载荷 `verified` 跳过，有尝试或结果不明则只读对账，不同载荷则冲突阻断。手机主微信通道保留、当前入口不调用；Mac 桌面微信停用。
- 群名、正文、渠道和天数必须在发送前后逐字核对。只对 0–3 天命中发送，不把前一次人工记录或其他群的历史状态当作本轮发送证据。

## 验证与停止条件

1. 离线测试覆盖边界 0/3/4 天、渠道映射、缺失字段、分页总数和末页、复核中集合变化、新消息行格式及同日事件防重；验证无命中不构造发送请求。
2. 真实只读采集回执须覆盖美团筛选后所有页、淘宝 50 条/页所有页；将候选行与页面二次回读一致性核对。侧栏汉堡控件点击目标为全局唯一的 `svg.hamburger`（外层 `.hamburger-container` 为 0 尺寸容器、点击无效，故不依赖 `.navbar` 父级）；渠道 tab 展开后仍需唯一匹配。
3. 微信入口能力或依赖校验未通过时，保留当日记录和零发送事实，不降级为模型手工点击发送。Windows 网关发送前核对健康状态及目标群；发送后核对当前群标题与末尾原文。登录、验证码、滑块、账户风险或目标群不唯一需用户处理。
4. 2026-10-01 用户明确要求恢复自动执行；Codex 任务 `10-2` 调整为每天北京时间 10:30，本机 careloop 不再并行调度本技能。

### 发送后只读对账修复

本轮原事件已发生一次物理发送：传输收据 `sendAttempts=1`，发送后双帧及群会话截图可见正文 `淘宝  伊戈塔可(雨花店)  3天`。账本仍为 `unknown`，原因是 OCR 将半角括号识别为全角括号，定位逻辑要求逐字相等，导致不能找到气泡；后续只读对账也因相同原因失败。**不得再次点击发送**。

最小修复只在气泡 OCR 定位时做 Unicode NFKC 归一化（含中英括号）与原有空白归一化；这一步仅产生坐标候选，最终仍必须通过精确群标题、两帧稳定位置和微信原生「复制」全文与请求原文逐字相等验证。统一执行器中 `reconcile` 的 `sendAttempts=0` 表示本次对账新增发送 0 次，原事件物理发送次数仍保留在 `transport.sendAttempts=1`；本工作流汇总必须分别呈现，不把对账的 0 次误写为原事件未发送。增加对应离线回归；更新共享依赖摘要时继续使用本次固定维护授权与完整测试。仅对同一事件运行 `reconcile`，收到机器 `verified` 才将当日记录标为已发送。

本轮新增的共享实现路径仅为 `scripts/desktop_text_readback.py`，须把它的当前精确摘要加入本次维护授权；其余共享路径仍受原精确摘要约束。对账尚未通过前不修改发送账本状态。
