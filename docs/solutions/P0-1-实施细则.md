> **日期**：2026-10-03（v2，替代同日的 v1「P0-1b 实施草案」思路）

## 0. 结论速览（与上一版的关键差异）

| 项 | v1 结论（**错**） | v2 实测结论（**对**） |
|---|---|---|
| P0-1 可读化的 UNKNOWN | 仅 **94/434 = 22%**（只认顶层 `stage`） | **433/434 = 99.8%**（认 `stage` **或** `reason`，含嵌套/文本兜底） |
| 是否需要 P0-1b（skill 侧补吐 stage） | 需要，覆盖 322 条 | **不需要**（残留 1 条空日志，属调度侧边缘） |
| 能否达成 `UNKNOWN <30%` | 不能（顶多 83%→~65%） | **能，且远超**（83% → ~0.2%） |

**v1 错因（务必记牢）**：v1 只在每条日志尾部 8000 字节内、按「整行以 `{` 开头」找 JSON，且**只认 `stage` 键**。两个缺陷叠加：
1. **截断**：`daily-taobao-download-to-jinsha` 的收据是**超长单行 JSON**（>8000B），被尾部截断切成半截 ⇒ 误判「无 stage」。
2. **字段窄**：8 条非发射者其实**都吐了结构化收据**，只是失败原因写在 **`reason`**（或嵌套 `send.reason`）而非 `stage` ⇒ 被误判「不吐收据」。

## 1. 「顶层收据」的精确定义（解析器必须按这个找）

> **顶层收据 = 日志全文中，最后一个「满足：`line.strip()` 以 `{` 开头、以 `}` 结尾、且可被 `json.loads` 解析为 dict」的整行。**

**三个「不要」**（都是踩过的坑）：
- ❌ 不要只扫 `data[-8000:]`——超长单行 JSON 会被切断（jinsha 即如此）。
- ❌ 不要用「从文件末尾往前找第一个 `{`」——会命中**嵌套子对象**（jinsha 会抓到 `reviewSummary.wechat`，键是 `totalElapsedMs/itemCount/...`，丢掉真正的 `stage`）。
- ❌ 不要把「全文件 grep `stage` 命中数」当判据——会把内部提及（如 `executor_integrity`）也算进去，产生"吐收据"的假象。

## 2. 字段优先级（在方案 §4 P0-1「字段优先级」专块基础上**扩展**）

解析器按下表次序取值，**命中即停**：

| 优先 | 取值位置 | 说明 | 用途 |
|---|---|---|---|
| 1 | 顶层 `stage` | 技能自报的失败阶段 | 分类 + 写 `detail` |
| 2 | 顶层 `ok` | 技能整体成败 | 判 FAILED（**外层 `ok` 优先于内层 `workflowReceipt.ok`**） |
| 3 | 顶层 `reason` | **新增别名**：失败原因码（`ok:false` 时普遍存在） | 分类 + 写 `detail` |
| 4 | 嵌套 `reason` / 嵌套 `stage`+`status:failed` | 如 `send.reason`、`review[].stage` | 分类（标注为"嵌套"来源） |
| 5 | **文本兜底**：`Error:\s*<code>`（取**最后一个**匹配，优先含 `-` 的 code） | Node 崩溃栈（如 `Error: channel-context-readback-mismatch`） | 分类 + 写 `detail` |
| 6 | 兜底 | 真的什么都没有 | 保持 `UNKNOWN` |

> **`stage` 与 `reason` 的语义关系**：`stage` = 「卡在哪一步」，`reason` = 「为什么」。**两者都可作分类键**；若同时存在，`stage` 定阶段、`reason` 写细节，`detail` 里两个都带上。

## 5. 二级提取（可选增强，用于「文本兜底」的 50 条）

`Error: Command failed` 太笼统（45 条），它下面还有真正的 stderr。建议文本兜底**取最后一个 `Error: <code>`**，并要求 code 形如 `[a-z][a-z0-9-]+`（含连字符），以跳过 `Command failed` / `the following arguments...` 这类噪声。**这一条不阻塞 W1**，可作 W1 内的增强项。

## 6. 自测用例（`--selftest` 必须新增，四种形态 + 两个负例）

| # | 形态 | 输入（日志尾部） | 期望 |
|---|---|---|---|
| 1 | 顶层 stage | `{"ok":false,"stage":"wechat-send-failed","workflowReceipt":{"ok":true}}` | FAILED，`stage=wechat-send-failed` |
| 2 | 顶层 reason | `{"ok":false,"reason":"daily-record-key-duplicate"}` | FAILED，`reason=daily-record-key-duplicate` |
| 3 | 嵌套 reason | `{"day":"...","status":"blocked","send":{"status":"blocked","reason":"dependency-drift:<p>"}}` | FAILED，`reason=dependency-drift`（来源=嵌套） |
| 4 | 文本兜底 | `...\nError: channel-context-readback-mismatch\n    at ...` | FAILED，`reason=channel-context-readback-mismatch` |
| **负例 A** | **嵌套收据反转** | 外层 `ok:false`/`stage:"wechat-send-failed"`，内层 `workflowReceipt.ok:true` | **必须判 FAILED**，**不得**因内层 `ok:true` 判 SUCCESS |
| **负例 B** | **超长单行** | 收据为单行 >8000B 的 JSON | **必须**完整解析出 `stage`（证明未用尾部截断） |

## 7. 风险与铁律

- **低风险**：纯调度层（`runtime/skill_runner.py`）**只读增强**——在既有 `classify()` 前面插一层「顶层收据解析」，解析失败**自动回退**原文本正则；**不改变** `classify()` 既有返回值语义。
- **不碰封印/安全门**：W1 无需授权（见方案 §8）。
- **不新增依赖**。
