# 原队列自动接续与原子实操验收

## 原因与目标

现有exchange写task后仅轮询response，需要模型岗位另行调用native_ui_post，导致等待、多轮调度和重复预检。沿原入口原账本，在owner-process任务写盘后由exchange同步调用相同dispatch，不新增发送通道或轮询守护。生产默认配置切换前先离线验证；同一时刻仅此消费者，不并行手工领取。

具体文件：skills/wechat-messaging/scripts/wecom_ui_queue.py、scripts/native_ui_post.py（确需修改时）、config/ui-execution-policy.json、tests/test_native_queue_dispatch.py。共享依赖清单尚未登记queue/native模块，不修改既有受管文件来绕过摘要；后续应独立核对完整性覆盖。

## 约束与异常

原adapter持有物理通道锁；原task/binding/owner及一次intent规则不变。新配置nativeDispatch=true才对原QUEUE、owner-process任务自动派发，不消费自定义队列/历史遗留。preflight完成搜群，send在同一adapter会话内连续选择/输入和发送，无模型往返；send仍核对当前真实目标及内容。调用异常如已有response复用，否则有intent则unknown不重发，无intent则blocked0；不伪造成功，不回退共享/注入，不重新领取同任务。

用户授权唯一测试群：临时测试群请忽略 💰发财精英荟💰。准备唯一标识合成文字、Excel、图片，不含客户数据；使用独立事件与账本，原适配器及相同队列，不更改生产路由。实际验收从其他会话/台前调度左侧收起状态开始，记录搜群→三类送达、呈现类型、耗时、原回执和重复调用零重发。离线测试不能替代真机验收。图片不可读时如实标待核验，不用空框或尺寸假写内容核验。

测试入口runtime/native_ui_acceptance.py仅接受runtime/state/native-ui-acceptance-20261025/manifest.json中完全相同的已冻结request及本日测试群；使用原WeComAdapter/executor而不是独立发送。测试前持原通道锁确认无其他消费者，随后启用nativeDispatch配置。生产不改投测试群。测试资料不进入Git。

首轮真机发现：选取文件可能直接发送而不出现“使用原文件”预览；固定要求预览会在真实文件已送达后误报unknown。修复需优先只读判断本次新增文件卡完整名称/大小/正确群/空框，再决定是否仍需操作真实预览按钮；已有卡绝不再点击或Return。旧未知不重发，仅独立只读对账。

后续只读证据纠正上述首轮猜测：实际composer为U+FFFC且有唯一附件子节点，说明本次Excel仍为未发送草稿，并非已直接发送；完整测试群保持正确，原代码没有执行最终Return。现需支持三种真实状态：新增文件卡已送达→只读核验；“使用原文件”预览→点真实按钮一次；专用文件选择器选择精确冻结文件后产生U+FFFC附件草稿→核群/owner后Return一次。不能仅因预览不见判成功。旧测试任务保持原未知，不延长旧owner；仅清理已知测试附件草稿后使用不同标识新测试载荷验收。

第三批文字实际出现z前缀，原因未证实，不归咎风控/输入法或用户。原正文核对正确拦截，blocked0且未执行Return。补充取得composer焦点后、粘贴前只读核对正确群及空框；任何已有内容不覆盖。只清理本次测试群已知“z+完整测试正文”草稿，保存零发送证据后沿同一事件重入，原executor对blocked0可重试、新task仍走原队列；不改旧回执、不清账本、不重发此前已提交图片。
