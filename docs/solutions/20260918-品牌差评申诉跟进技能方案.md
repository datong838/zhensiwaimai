# 品牌差评申诉跟进技能方案

## 目标与范围

新增独立 Skill `brand-negative-review-appeal-followup`，每天按上海时区的“昨日”从金鲨“评价&负反馈 → 差评列表”读取品牌维度的中差评申诉进度，并输出 `YYYY-MM-DD差评申诉跟进.csv`。

本方案仅覆盖“美团外卖”和“淘宝闪购”两个平台，评分范围为 1–3 星。每个品牌单独查询并保留品牌列，避免多品牌时无法辨别门店归属。当前品牌表仅包含“李老哈”。

该 Skill 与既有 `daily-negative-reviews`（固定运营群、单个 Excel 文件）隔离；不得修改其代码、策略、账本或目标群。

## 输入与输出

### 输入

- `inputs/品牌表.csv`：UTF-8 CSV，无表头；每行一个非空品牌名称。
- 运行日：按 `Asia/Shanghai` 自动计算昨日；不接受手工日期覆盖。
- 金鲨已登录且可读取的业务页面。

### 输出

- `outputs/YYYY-MM-DD差评申诉跟进.csv`：UTF-8 CSV，固定字段为：
  `记录键、品牌、平台、门店、评价时间、评价等级、申诉结果、评价内容、通知正文、群检索结果、发送状态、备注`。
- 每条记录的 `通知正文` 固定为逐条可发送格式；不把同一品牌的多条评价拼接成一条消息。
- 通知标题按星级固定：3 星为 `--- YYYY-MM-DD 中评申诉进度通知 ---`；1–2 星为 `--- YYYY-MM-DD 差评申诉进度通知 ---`。
- 普通微信群文本不支持局部颜色或字体加粗；申诉结果固定写为 `申诉结果：---未申诉---`、`申诉结果：---申诉中---`、`申诉结果：---申诉成功---` 或 `申诉结果：---差评免责---`，以三横线增强辨识度。“差评免责”只能由页面明确的“已拦截评分／免责，不计入评分”触发，不得推断。
- `发送状态` 初始为“未发送”；只有微信发送一次且逐字回读验证为 `verified` 后才改为“已发送”。

## 只读生成流程

1. 读取品牌表，逐行去除空白；相同品牌在同一轮只处理一次。
2. 对每个品牌，依次选择“美团外卖”“淘宝闪购”，选择“昨日”，在品牌搜索框输入该品牌并执行查询。
3. 回读平台、昨日日期范围、品牌搜索值与状态计数；任一项不一致则该品牌/平台记录为阻断，不生成推测数据。
4. 读取全部分页的 1–3 星评价卡片，提取门店、评价日期、星级、评价内容和申诉状态。状态可为：`未申诉`、`申诉中`、`申诉成功`、`差评免责`；页面明确免责时如实报告“差评免责”。其他失败、已删除或未识别值原样写入备注，不得映射为成功。
5. 用 `品牌 + 平台 + 门店 + 评价时间 + 星级 + 评价正文` 生成稳定记录键。重复调用复用既有记录，不重复生成通知草稿。
6. 写入 CSV 后重新读取校验列顺序、记录键唯一性和通知正文与字段一致性。

## 微信发送门禁

默认模式为 `dry-run`，禁止触碰微信。发送模式需要用户在当次明确授权，且授权对象必须包含业务日期、品牌、每条通知正文摘要和目标群。

发送前优先核验当前微信会话；仅当前会话不等于目标群时，对每个品牌执行一次群检索：

1. 当前会话的原生完整群标题、群类型和空输入框均与目标匹配时，直接复用当前群，禁止再次搜索或打开群。
2. 仅未命中当前群时，搜索核心品牌名，例如“李老哈”。
3. 仅把经过原生标题与群类型核验的群聊计入候选；联系人、聊天记录命中和网络搜索结果不计入候选。
4. 恰好一个候选群时，回读其完整群名并绑定该品牌；零个或多个候选群均跳过该品牌，CSV 写入“跳过：群不唯一”或“跳过：未找到群”。
5. 同一品牌的多条消息在首次群核验后复用当前群；每一条发送前仍需核验原生完整群标题、群类型和空输入框。
6. 按 CSV 的稳定顺序逐条发送，每次只允许一次发送键。使用统一 `wechat-messaging` 的防重账本、文本逐字回读和双帧新气泡验证。
7. 仅收到 `verified` 或 `already_verified` 回执时，将对应一行更新为“已发送”。`attempted`、`unknown`、`blocked`、`partial` 均不得改写为已发送，也不得自动重发；只允许只读 reconcile。

## 停止与恢复

- 采集阶段同一品牌/平台连续两次失败即停止该阶段，保留其他品牌的只读结果。
- 发送阶段一条消息出现未知或回读失败，立即停止整个批次，不再发送后续消息。
- 群不唯一不是可重试错误；跳过当前品牌，继续品牌表的下一行。
- 任意页面登录、验证码、风控、日期/品牌/平台回读不一致时失败关闭；不得切换浏览器、账号或通道绕过。

## 本轮演示边界

本轮创建 Skill、品牌表和基于已核对的 2026-09-17“李老哈｜美团外卖、淘宝闪购”数据生成的首版 CSV。不会搜索微信群、不会创建发送授权、不会发送或更新任何“已发送”状态。

## 执行器沉淀与每日运行（2026-09-18 增补）

本节是每日定时执行前的代码级门禁，不以 Markdown 提示代替执行器约束。

1. **批次会话复用**：同一品牌批次在首条定位成功后，后续条目只能走“当前会话原生完整标题 + 群人数标题 + 空输入框”预检。该预检成功时，执行器不得调用搜索或打开会话函数；当前会话丢失、标题变更或输入框非空则失败关闭。
2. **唯一群判定**：搜索结果采用 AX 列表的结构化行与点击后的原生群标题联合证明。不得把“最常使用”“聊天记录”“群聊”等任一展示分区文案作为正确性的前提；同名聊天记录摘要、联系人或网络结果均不得计为候选群。只有一个可点击本地会话行且点击后标题精确匹配，才能继续。
3. **批次防重与恢复**：`attempted`、`unknown` 和超时只能进入只读 `reconcile`；不能再次发送。每项仍保持一次发送键上限，只有 `verified` 或 `already_verified` 才更新业务 CSV 为“已发送”。
4. **可审计复盘**：统一执行器必须在回执 `review` 中实际记录授权、冻结、群预检、每条发送或只读对账阶段的 `elapsedMs`、状态和踩坑字段。未执行的阶段不得生成虚假耗时；业务层汇总该结构输出本次复盘表。
5. **每日定时入口**：定时任务按当前配置时间先调用 `daily_executor.mjs`，再且仅调用 `delivery_executor.py`；运行日按上海时区取昨日，读取品牌表后生成当日 CSV。它不得绕过统一执行器的请求摘要、当日授权、唯一群、账本、原文回读和离线策略。任何群不唯一、页面不一致、未知回执或策略不满足均停止或跳过，不靠模型临场决定重试。

### 验收用例

- 当前目标群已打开时，模拟后续两条消息：断言搜索函数未被调用，且每条均重新通过标题、群类型、空输入框预检。
- 搜索弹窗中同名条目分别出现在任意展示分区和聊天记录摘要：仅接受唯一可点击会话行；不依赖分区名称；点击后标题不匹配即拒绝。
- 已有 `attempted`/`unknown` 账本时，断言执行入口没有调用发送函数，只允许 `reconcile`。
- 断言复盘条目包含实际耗时、失败原因和最终状态；重复运行已验证事件不产生 UI 调用或新发送。

## 心跳内受控恢复（2026-09-19 增补）

定时任务不得把“发送代码或依赖加载失败”误当作本轮业务终点。新增固定恢复编排器，业务发送始终且只能委托统一 `wechat-messaging/scripts/executor.py`；恢复编排器不直接操作微信、不构造消息、不改写发送账本、不提升运行策略。

### 同一心跳流程

1. 先调用一次统一总执行器。
2. 只有同时满足以下条件才可进入恢复：批次回执及全部项目都**显式**证明 `sendAttempts=0`（缺失次数按未知处理）；错误属于依赖摘要漂移或 Python 模块加载/语法类发送代码错误；不存在 `attempted`、`unknown`、`partial`、业务页面校验或群定位异常。
3. 通过既有 `dependency_maintenance.py prepare` 执行受控维护。该入口必须完成全量离线回归、原子更新、依赖回读与总执行器完整性检查；恢复编排器本身也被纳入依赖摘要。任一步失败自动回滚。
4. 维护成功后，仅调用统一总执行器**一次**最终复跑。最终复跑不可再进入恢复循环。
5. 任何出现实际发送尝试、未知状态、群不唯一、登录/页面/日期/品牌校验失败、维护失败或最终复跑失败，均不重发。保留完整复盘，在同一心跳内尽可能完成只读对账；仅在无法安全恢复时通知。

## 每日策略登记（2026-09-20 增补）

每日消息正文、请求摘要和到期时间都不同，不能复用过期的 `runtime-policy.json`，也不能靠人工编辑该文件恢复运行。固定入口 `wechat-messaging/scripts/policy_registration.py` 只做以下零发送动作：校验请求、授权摘要、群名、账号、通道和短时有效期完全一致；原子登记唯一请求摘要；写入回执。它不导入桌面控制、不搜索群、不发送消息、不改写账本。

登记成功后，业务动作仍只能由 `heartbeat_recovery.py → executor.py` 完成。若策略登记失败，整个批次 `sendAttempts=0` 并可在同一心跳受控维护后复跑；若任一项已 `attempted` 或 `unknown`，只允许 reconcile，不能重新登记为新的发送许可。

### 代码验收

- 可恢复的 `dependency-drift` 且零发送尝试：断言维护一次、全量回归一次、总执行器最终复跑一次。
- 任一条 `sendAttempts > 0`、`attempted`、`unknown` 或业务门禁错误：断言不调用维护且不复跑。
- 维护失败：断言不执行最终复跑，保留维护复盘与失败原因。
- 最终复跑失败：断言总执行器调用次数恰为两次，不发生第三次尝试。

## 固定每日入口补齐（2026-09-21）

`brand-negative-review-appeal-followup/scripts/daily_executor.mjs` 是该业务的唯一每日编排入口，补齐此前仅有规则和历史 CSV、没有可执行采集入口的缺口。

1. 入口自行按上海时区计算昨日，并仅读取同目录的品牌表；调用方不能传日期、端口、群名、通道或输出目录。
2. 金鲨只连接 `127.0.0.1:9232` 的唯一 `data.guoshuyufen.com` 页面；依次回读淘宝外卖主题、差评路由、品牌输入、昨日双日期和平台选中值。任一不符均不生成推测评价。
   首页与差评路由跳转同样必须连续两次回读 URL、页面标题、登录门禁和必要菜单一致后才算就绪；不得以固定延时后的单次路由状态判定失败。
3. 对每个品牌仅采集美团外卖和淘宝闪购 1--3 星卡片，分页切到 200 条并由页面总数与卡片数双次稳定确认；输出固定列 CSV，并以字段重新计算通知正文和稳定记录键。
   平台或品牌筛选写入后，必须等待“品牌、平台、昨日双日期、评价总数、星级计数和评价卡片数”连续两次回读一致，才可判断该平台无评价或开始提取；不得使用固定延时后的单次空结果。
4. 采集结果属于四种明确状态（未申诉、申诉中、申诉成功、差评免责）时，后续发送编排才可生成冻结请求与短时授权，并先执行统一微信策略登记；策略登记、恢复器和统一执行器的每一步均保存代码生成的阶段耗时、状态和踩坑。采集入口本身不实现微信搜索、定位、发送或回读。
5. 遇到 `attempted`、`unknown`、群不唯一或任一金鲨回读不一致，入口只保留收据或进入统一只读 reconcile，绝不产生新的相同载荷发送。
6. 已通过真实发送验收的路径为唯一固定路径。运行时不得基于窗口、超时、授权或其他现场状态新增事件类型、续发分支或替代策略；仅在执行器自身存在可复现缺陷时，按最小修复、回归验证后维护代码。业务批次仍以完成为最高目标，但不得以扩大运行策略换取完成。

若用户明确逐条审阅并确认某条 `unknown` 已送达，可由续发准备器记录该人工审核引用；它仍不得重发该条，只能把此前未尝试的后续条目创建为新的稳定续发事件并继续交给统一微信执行器。
既有续发准备器必须以原事件最新回执逐项判定：仅选择回执中不存在、且从未写入发送键的条目；任何已 `verified`、`already_verified`、`attempted`、`unknown` 或 `partial` 的条目均不得再次纳入续发请求。不得以 CSV 固定行号推断剩余条目。

金鲨入口校验不得依赖会随业务平台变更的 `theme-mode` 或旧版“智能斗金”文案；代码改为核验已登录业务页、外卖入口、评价&负反馈菜单、固定差评路由、品牌搜索、昨日双日期和每个平台单选值。这样美团与淘宝入口均可在同一专用会话中被逐项回读，不把正常平台切换误报为登录失效。

## 2026-09-25 多段发送恢复与结果闭环加固方案

### 问题证据

- 2026-09-24 批次共 4 条。群内四条消息均可见；续发批次的江浦路、奉贤宝龙、宝山三条最终由统一执行器原文回读为 `verified`。成山路原批次曾 `sendAttempts=1` 且即时核验 unknown，之后群内可见，但旧请求对账被 `acceptance-scope-mismatch` 阻断。
- 三条续发均经历 `desktop-post-send-verification-unknown`，后续只读 reconcile 能以原生复制文本 SHA-256 精确核验为 `verified`。发送后的即时结果与后续对账结果因此可能短暂不同。
- 一次执行器预检报 `current-group-composer-not-empty`，而当前微信窗口显示目标群输入框为空；刷新相同窗口后预检通过。必须维持严格空输入门禁，不得以视觉印象直接放行发送。
- 续发结束后日报仍将三条 verified 项记为“未发送”；业务方案要求业务层只对 verified 项更新，但当前可执行入口没有完整的回执到 CSV 投影闭环。
- 续发准备器当前依据初始事件的最新回执和固定输出目录，只能覆盖单段续发；它没有可靠表达“unknown 已经 reconcile 为 verified、原请求已授权范围变化、再为从未尝试项创建下一个唯一事件”的状态链。

### 最小实现范围

保持金鲨采集、已验证的微信群复用/定位、消息格式、账号、通道、授权门禁、统一执行器发送函数和一次发送键限制不变。仅补齐既有方案已经要求但未完整实现的恢复闭环：

1. **确定性投递编排入口**：增加品牌差评业务层投递编排器，仅调用 `policy_registration.py`、`heartbeat_recovery.py` 和其内部统一 `executor.py`。编排器不操作微信 UI、不调用发送 API、不编辑运行策略、不生成或更改正文。
2. **逐项回执归并与续发选择**：以稳定 `itemId` 汇总当日初始及全部续发事件的只读回执/底层账本。`verified`/`already_verified` 永久排除；`attempted`/`unknown`/`partial` 只能 reconcile，不能进入任何新发送请求；只有明确从未写入 attempt 账本且 `sendAttempts=0` 的项目才可进入新的续发事件。缺回执、次数缺失、摘要/授权/群不匹配时失败关闭，不靠行号推断。
3. **唯一续发事件**：每次续发事件 ID 由业务日、父事件/已核验回执身份及有序未尝试 `itemId` 确定；相同续发再次运行复用同一请求，禁止覆盖或重复创建。前一 unknown 经只读 reconcile 变为 verified 后，下一事件只含其余未尝试项目。不得创建旁路发送分支。
4. **授权范围**：每个新请求仍必须调用现有 `policy_registration.py prepare` 原子登记精确请求摘要；不手工修改 `runtime-policy.json`。旧事件只能按原授权证据 reconcile，不把新请求策略用于旧请求、不扩大授权。
5. **日报状态投影**：增加纯本地、零微信副作用的回执投影步骤，从实际总执行器回执更新 CSV：仅 verified/already_verified 写“已发送”；unknown/attempted 保持“核验未知”；blocked 或从未尝试保持“未发送”。按记录键/itemId 匹配并原子写入、回读校验；正文、采集数据和排序不变。人工确认仅可帮助排除已送达项、防止重发；没有机器 verified 回执时不伪造机器核验等级。
