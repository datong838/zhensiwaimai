# 2026-10-29 旧机接管与 Windows 网关恢复方案

## 最新授权与目标

用户明确“由旧机重新接管”，要求监理恢复并使用 Windows 网关，同时“企业微信通道保留不变”。本次旧机成为监理执行端；不主动启动新机、不恢复源机历史暂停定时。旧 Goal 中的日期和已完成事实作为历史保留，不追补旧日生产。

## 分阶段执行

1. 回读本机主任、真实进程和锁、当日班表与状态。保留原账本、游标、原事件和全部 attempted/unknown；不复制或清空新旧机账本。
2. 通过既有 Windows 客户端只读核验 health、会话身份和实际暴露能力；不输出连接凭据，不用业务发送探针。
3. 使用原 runtime/install_daemon.sh 恢复原主任；回读 launchctl、真实 PID、当日心跳和在途步骤。已有通道暂保持原配置，独立业务按原班表推进；启动不等同于 Windows 切换完成。
4. 企业微信 scripts/wecom_adapter.py、原生 UI 实现、配置和队列保持原样。Windows 切换必须覆盖桥接路由以及直接绑定 WeComAdapter 的消费者，不能只改14条外置路由便宣称完成。
5. Windows 投递必须保留完整群、空输入框、一次发送与原载荷回执核验。现有旧适配器存在通用媒体占位匹配和 HTTP 错误自动重试，不满足当前证据合同；未核对现役驱动实际能力并修复前，不启用该发送路径。
6. 如需代码改动，先取得现役 Windows driver/server 真身，列出具体实现文件和差异，离线自测并经共享依赖与消费者原维护入口同步；不以本仓4-action骨架覆盖线上多action驱动。

## 当前拟操作文件和验证

用户进一步明确授权：商家预检、Top10、活动、装修等直接绑定入口改走 Windows，企业微信登录后再切回；维护后立即投入今天工作。实现使用 `skills/wechat-messaging/config/active-transport.json` 单一显式开关，`scripts/transport_selection.py` 统一构造适配器，桥接和所有本机直接调用者共用。缺失、损坏、未知通道失败关闭，不能静默回退。

具体代码目录：`skills/wechat-messaging/scripts/{transport_selection.py,workflow_bridge_windows.py,workflow_preflight.py}`；`skills/workflows/` 下商家、双Top10、日报、新店、活动、装修、未养活、完成度、基础诊断、排名、商品整改、品牌申诉的发送/预检入口。另一电脑经营指标/发券/巡店代码不修改。企业微信原生实现、选择器、队列和历史回执不修改。

Windows 使用严格包装层：前检必须从实际当前会话返回完整目标和显式空框证据；只有标题、会话列表或ready不放行。现役API若未暴露空框则明确零发送阻断。Windows历史unknown不采用旧占位符匹配结论化；传输不能仅因HTTP错误判零发送并自动重试。当前现役驱动缺失能力属于真实部署缺口，路由完成不等于已发送。

测试覆盖配置错误、双向切换、预检与发送同通道、缺失空框证据零发送、HTTP失败不重试、旧unknown只读，以及全部本机消费者导入；再运行原共享与消费者回归。受管摘要由本次代码化维护入口按精确变更清单、原字节备份和测试回执更新；原验收事实保留，变更后不伪造新非空验收。

本阶段只新增本方案和接管证据，不改业务执行代码、企微路由或历史发送事实。启动由原安装脚本生成机器本地 LaunchAgent。核验以真实 launchctl/PID/心跳为准；业务完成仍以当日原回执为准。Windows health 为 ready 仅证明进程与登录就绪，不证明空框、载荷和送达证据充分。

## 风险与回退

如果发现新机仍在执行同一生产工作，停止旧机新增生产并核对唯一所有权，不抢锁。主任启动失败如实记录，不修改账本冒充恢复。Windows 切换尚未实施时保留企微现行路由，不能隐式降级。停机回退使用原 LaunchAgent bootout，浏览器和历史记录保留。
