# 昨日差评分析代码强制执行器方案

## 目标

把“金鲨昨日差评查询 → 下载与页面逐条对账 → 生成固定格式 Excel → 微信唯一群发送 → 完成复盘”从自动任务提示和临时脚本升级为单一确定性执行器。只有执行器状态达到 `complete` 且生成代码化 `completionReview` 才能报告完成。

## 已验证事实与当前缺口

- 2026-09-18 的真实发送收据证明：目标群发送链路、文件哈希、防重账本、单次发送和发送后双帧验证有效。
- 公共微信执行器已经强制完整群标题、群类型、文件身份、单次发送和未知结果不重发。
- 当前差评数据采集、昨日日期、金鲨页面唯一定位、外卖/淘宝入口状态、下载与页面三平台对账、报表结构及最终复盘仍有部分依赖自动任务提示或日期固定的临时脚本。
- 当前公共微信搜索使用完整群标题；用户要求搜索时只使用核心文字“上海臻肆外卖运营-盯个盯-饭敢当”，忽略头像、图标和后续装饰符号，并且只在唯一结果时发送。这条要求尚未形成代码门禁。

## 固定执行边界

1. 唯一入口为 `daily-negative-reviews/scripts/workflow_executor.mjs`；调用方不能传日期、端口、群名、通道、输出目录或发送器。
2. 业务日期由执行器按 `Asia/Shanghai` 自动计算为昨日；运行目录按业务日期唯一，重复调用复用状态与收据。
3. 浏览器固定为 `127.0.0.1:9232`，域名固定为 `data.guoshuyufen.com`。只绑定唯一已认证金鲨业务页；登录、验证码、滑块和账号风险页阻断，授权失败仅作为业务覆盖告警。
4. 页面必须处于外卖业务，淘宝入口状态必须可验证；差评路由固定为 `#/negativeAnalyse`。日期必须由代码设置并逐字段回读。
5. 平台固定为美团外卖、淘宝闪购、京东外卖；每个平台切换后回读选中值、分页大小、总数和页面卡片数。下载只允许一次；恢复只复用同一运行目录中已绑定哈希的下载收据。
6. Excel 固定为单表“差评分析数据”和七列既定顺序。下载与页面按店铺、评分、日期、平台、正文做多重集逐条对账；页面免责或拦截提示只在下载正文为空时补齐。
7. 微信固定走 `wechat-messaging` 的 `negative-reviews` 注册入口。搜索词只用于拉起搜索；群结果分区中唯一的群行即直接点击，不比较其展示前缀、后缀、省略号、图标或与输入文字的长度/内容，也不再以标题或人数否决该唯一结果。输入框为空、文件名、目录、大小、哈希、业务日期、防重账本和双帧校验仍全部通过才算发送成功。
8. 任何已经形成 `attempted` 或结果未知的发送只允许持续只读对账，不得再次发送。登录有效时，阶段失败只能形成可恢复记录，不能成为永久停止门禁；后续执行必须保留历史并继续未完成阶段。

## 状态机与复盘

状态固定为：

`created → browser_validated → downloaded → reconciled → report_built → sent → complete`

每个阶段由执行器记录开始、结束、尝试次数、耗时、状态和踩坑代码。成功或失败都写 `workflow-summary.json`；成功 CLI 直接输出：

- `codeEnforced: true`
- `totalElapsedMs`
- `reviewItems[]`：阶段名称、尝试次数、耗时、状态、踩坑数组
- `pitfalls[]`：本轮全局踩坑
- 数据行数、平台分布、业务告警、输出文件哈希与微信验证等级

调用方只能展示执行器生成的复盘对象，不得由模型补写节点或耗时。缺少 `completionReview` 时不得报告流程完成。

## 代码结构

- `scripts/workflow_policy.mjs`：固定参数、业务日期、运行目录、状态转换、配置与依赖摘要门禁。
- `scripts/browser_collect.mjs`：唯一页面定位、入口状态、日期、平台、下载和页面快照。
- `scripts/reconcile.py`：原始 Excel 与页面快照逐条对账、空正文补齐和数据画像。
- `scripts/build_report.mjs`：固定单表七列报表生成及结构化验收。
- `scripts/workflow_executor.mjs`：状态机、恢复、重试、微信桥接、收据校验和代码化复盘。
- `tests/` 或同级测试脚本：覆盖日期、配置、状态转换、错误页面、重复结果、错误文件、错群、未知发送和复盘结构。

### 心跳内受控恢复顺序（2026-09-19）

- “运行失败立即失败关闭”不构成本轮结束条件；总执行器首次返回失败后，心跳必须保留失败收据并进入受控恢复。
- 发送代码失败或依赖摘要失败时，当前心跳按固定顺序执行：受控维护授权、依赖维护回归、差评执行器自检及相关离线回归；维护只允许更新登记依赖和摘要，不得执行业务发送。
- 维护与回归通过后，当前心跳继续调用唯一生产入口 `workflow_executor.mjs --execute`；若总执行器复跑失败，不能结束本轮，必须继续受控维护、回归和复跑，直到任务流程完整完成。业务浏览器、下载、报表和微信动作仍全部由总执行器完成。
- 总执行器复跑失败不构成本轮停止条件；只有登录页、验证码、滑块或账号风险页才请求用户处理。发送已进入 `attempted` 或 `unknown` 时只读对账，禁止借恢复流程重发。
- 自动化提示必须明确上述顺序，不能只写“失败后通知”，也不能让模型临场拼接业务动作或绕过总执行器。
