# UI岗位去除人为卡停

## 用户原则
只保留防重复，慢发优于不发，不允许岗位无声卡停。群名、文件和正文核对属于交付内容，继续保留。纯UI通道不变。

## 已定位的层级
1. 外层skill_runner按固定总秒数终止整个进程组。
2. 各流程内部子进程另有短timeout；UI请求deadline从采集前开始计算。
3. UI队列把deadline当作静态失效时间，实际窗口操作尚在推进也会中断。
4. UI适配器session最多等待90秒，排队即失败。
5. 独立预检和发送岗位再次查群消耗同一预算。
6. blocked0未被原恢复判据接受，形成永久只读空转。
7. 过期后未自动清理文件选择框。

## 实施约束
逐层实现，不把改大数字冒充已删除计时限制，不延长旧发送任务或重发unknown。新任务按已授权当日工作范围执行；保留唯一任务/意图/账本、互斥、正确群及内容、实际送达回读。已终止旧任务通过原零发送证据恢复，新任务仍由原control提交。先修复当前活动选店及文件交付卡点；全局排队与执行等待改为状态驱动，存活或真实进展不应因总时长被杀。真正停滞由监理主动恢复，不允许无声放置。

## 验证
离线验证正常慢任务不因固定时长终止，重复意图仍拒绝，unknown不重发，队列只消费原注册任务；随当日原班次验证交付，禁止重复发已完成内容测试。每层实施状态必须明确，未完成不能宣称全面修复。

## 第一层实施

夜间补查：runtime/run_now_watcher.py仍以900秒终止整个--once补跑进程，与owner-process机制冲突。本次将ONCE_TIMEOUT_SECONDS设为None，等待真实退出，启动失败/互斥失败仍沿原force_run降级；不新增补跑请求。wecom_ui_queue原无载荷目标预检仍要求deadline剩余15到300秒，改为只校验有限正时间戳的接口形状，实际原生任务继续由双进程身份管理；非owner任务仍用自身旧deadline等待逻辑。群和请求字段范围不变，发送入口仍不接受无载荷预检。离线验证过期字段不再阻断owner预检，非数字/NaN/无限/非正值仍拒绝。
