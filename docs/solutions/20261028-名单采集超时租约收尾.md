# 名单采集超时租约收尾

## 问题与边界

品牌名单维护入口使用 subprocess.run(timeout)，到期强杀原 Node 子进程。子进程 finally 未必执行，自己的物理租约可能保留；原获取接口会拒绝尚未过期的异 runId，令后续维护等待。当前三个流仍停用，本次不启动名单采集或生产，也不修改岗位租约协议和已登记岗位文件。

## 最小方案

- 修改 `skills/workflows/daily-store-metrics-rotation-to-wechat/scripts/refresh_shop_pool.py`：父进程生成唯一 monthly-roster UUID，显式传入原采集器；使用 Popen，超时 kill 后 communicate 回收子进程，再做收尾。正常退出同样复核收尾；失败不验证/发布快照。
- 修改同目录 `collect_shop_pool_brand.mjs`：允许父进程传入合法本次 lease-run-id；未传仍维持原随机 UUID，原遍历和 finally 不变。
- 新增同目录 `release_roster_lease.mjs`：只读取原物理租约 PID/runId，必须与本次唯一身份一致，且进程确已不存在，才调用原 releasePostLease。缺锁幂等成功；活进程、外来租约、畸形租约均不释放。不得只根据 TTL 或前缀判断所有权。
- 新增隔离测试，使用临时目录与测试进程，不连接 Chrome，不触碰现役锁、原账本、游标、生产队列或原名单。

## 验收与风险

验证正常退出、真实超时并回收、异常退出均触发退出后收尾；缺锁、死进程本次锁、活进程、不同 PID/runId、畸形锁、释放前被换锁均覆盖。原释放接口重新核对 runId，唯一随机身份不复用。收尾失败明确报错，不把失败快照当完整来源。源文件语法、原月登记回归及修改范围复核后提交推送。

采集使用现有业务页、不新建页。本次不增加强杀后的页面操作；如留下切店弹层，后续原流程仍需自身页面前置验证。父进程本身被强杀/宿主崩溃不在本次退出回调的保证范围。更广泛的旧租约 TTL/原子获取机制另行评估，不能用该窄修复宣称全部互斥机制已修复。
