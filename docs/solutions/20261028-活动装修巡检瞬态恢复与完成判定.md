# 活动装修巡检瞬态恢复与完成判定

## 规则与问题

读取两流现行Skill、daily/单店workflow/选店及收尾代码和原测试。用户允许明确“未搜索到店铺”经原提示送达后成功结束，固定记录“店铺在主账号查不到未能检查”；不允许将搜索超时、岗位忙、登录失败当查无店铺或成功。当前daily却把全部collection-skipped前缀列为已完成的skipped，包含post-lease-busy/shop-search-timeout；收尾还可能在岗位忙时尝试复位。

## 最小实施

- 修改 `skills/workflows/daily-new-stores-activity-audit-to-wechat/scripts/activity_daily.py` 和 `skills/workflows/daily-new-stores-decoration-audit-to-wechat/scripts/decoration_daily.py`。
- 仅exact collection-skipped:shop-search-timeout在调用发送函数之前，使用原collector重试一次。首轮错误与重试预算留本run证据；第二次使用search-retry-1子目录，不覆盖首轮日志/结果。正常采集和业务消息路径不变。
- 持续搜索超时标retry-required，零发送且本流不算complete；继续本批尚未尝试的独立店。原主任后续按原control接续，原已发/unknown账本仍阻止重发。岗位忙标skipped-busy，不重试、不抢锁、不做复位，也不标完成。
- 普通skipped成功仅接受原collector明确的非营业状态（暂停营业/已下线）；明确查无店铺保持既有独立提示及真实verified门。未知其他前缀不再冒充成功。
- 登录/验证码/风险等外部条件不重试、不额外复位；实际发送unknown仍原停批，不能触发采集重试。未完成项在顶层reason及recoveryRequired中显式给原主任/监理定位。
- 不改Node原岗位/租约文件、共享消息模块、班表、旧记录和制动；装修watchlist仍只消费真实targetStatus，没有检查结果的待恢复项不据此康复。
