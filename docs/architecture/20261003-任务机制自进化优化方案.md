## 0. 一句话结论

**车间的「稳定」已经做得相当扎实（现场维护、互斥组锁、只认当天、反虚高 SUCCESS、孤儿收割、测试隔离三层防线），但「聪明」还几乎是零——系统每天产生 500+ 条告警、14GB 级运行日志，却没有一条被转化成下次能用的知识。**

根本症结不是缺功能，而是**缺一条把「运行结果」回流成「下次更好的行为」的闭环**。本文给出三条可独立落地的进化回路（诊断进化 / 参数进化 / 知识进化），并严格遵守既有铁律。

## 2. 诊断：为什么「不会越跑越聪明」

### 2.1 症结一（最严重）：失败分类器是**死名单**，结构化证据被当场丢弃

**实测代码**（`runtime/skill_runner.py:125-138`）：

```
classify(text, exit_code, timed_out)
  exit=0 且未超时        → SUCCESS
  timed_out              → RECOVERABLE
  命中 NEEDS_LOGIN_PATTERNS（约 6 个关键词：扫码/未登录/login expired/...）→ NEEDS_LOGIN
  命中 RECOVERABLE_PATTERNS（约 9 个关键词：timeout/econnreset/device offline/...）→ RECOVERABLE
  否则                    → UNKNOWN，detail = "exit=1 未命中已知分类"
```

**但真实失败日志是这样的**（`run_history/2026-10-03/daily-taobao-download-to-jinsha--20261003-145650--a1--s1.log`）：

```json
{"ok":false, "stage":"wechat-send-failed",
 "workflowReceipt":{"ok":true, ..., "phase":"completed",
   "phaseHistory":["initialized","profiles_ready","taobao_open","taobao_downloaded",
                   "taobao_closed","jinsha_open","jinsha_processed","completed"],
   "stageMs":{"taobao_download_sequence":16263, "jinsha_sequence":3752, ...}}}
```

**诊断**：skill **自己已经明确报告了** `stage:"wechat-send-failed"`，且业务流程（`taobao_downloaded`→`jinsha_processed`）**全部成功**，只有最后一步微信发送失败。但调度层只看文本里有没有那 15 个英文关键词，一眼没命中就丢进 `UNKNOWN`，detail 里连一个字的有用信息都没有。

**后果链**（可验证）：
1. 数百条告警（83% 为 UNKNOWN）→ 看护代理读到的全是「exit=1 未命中已知分类」→ 无法分诊，只能人肉 `cat` 日志
2. `daily-taobao-download-to-jinsha` 连败 5 次，**每次都全量重跑**（重新下载淘宝报表 + 重新上传金鲨），而实际只是末段发送失败
3. 重试预算（max_retries=2, cooldown=300s）被浪费在注定失败的完整流水线上

> **这就是「不聪明」的定义：同一个错犯了 5 次、系统记录了 5 次、但第 5 次的行为和第 1 次完全一样。**

> ⚠️ **监理补注（P0-1 的字段陷阱）**：上面那条收据是**嵌套**的——**外层** `ok:false` / `stage:"wechat-send-failed"`，**内层** `workflowReceipt.ok:true`（业务流程本身是成功的）。若解析器朴素地读 `"ok"`，会命中内层的 `true`，把「仅末段发送失败」**误判为 SUCCESS**，恰好与事实相反。P0-1 实现时**必须钉死字段优先级**：以**外层 `stage` / 外层 `ok`** 为准；`workflowReceipt.ok` 只用于判断「业务链是否走完」，**不得用于成败分类**。详见 §4 P0-1「字段优先级」（含负例自测）。

### 2.2 症结二：经验只增不减，无索引、无老化、无回滚

| 累积物 | 现状 | 问题 |
|---|---|---|
| `alerts.jsonl` | 508 行，只 append | 无聚合、无去重（仅 auth_watch 有 24h 去重）、无老化 |
| `run_history/` | 每日子目录 | prune 只留 14 天，过期即**物理删除**，历史经验随之蒸发 |
| 验收快照 `.runtime/` | 30+ 时间戳目录 | 无索引，靠人肉翻目录 |
| `KNOWN_ANNOUNCEMENTS` | 硬编码数组（`collector.mjs:221`） | 新弹窗＝改代码＝触发封印漂移 |
| `REGISTRY`（落群表） | 硬编码 dict（`workflow_bridge.py:53`） | 改落群＝改代码＝重封印 |

**没有任何一处是「可检索的知识」**，全是「碰巧还在磁盘上的证据」。

### 2.3 症结三：fork 而非引用，修一处漏多处

`docs/architecture/流程执行器依赖与共享库清单.md` 已记录，本次实测复核：

- `workflow_executor.py` **4 份**，md5 全异（`daily-agent` / `daily-top10` / `video-publish` / `maintenance/candidate`）
- `executor_integrity.py` **2 份**
- `runtime_contract.py` 与 `runtime_guard.py` **同名不同责的平行实现**

→ 任何一次「修复」都有 3/4 的概率只修好其中一份。这是**稳定性**的直接威胁。

### 2.4 症结四：封印会自锁，恢复通道依赖人肉

`docs/solutions/20261003-⑪封印死锁恢复方案-待授权.md` 记录当前死锁：验收回执写在 `/private/tmp/`（重启即失）→ refresh 断链 → `prepare` 要求 SEALED 态、当前 UNSEALED → 重封需真实非空发送、发送被门禁拦死 → **四向死锁，只等人肉授权**。

封印本身是对的（防漂移），但**缺少「证据丢失后的合法自愈通道」**。

### 2.5 症结五：重跑＝全量重跑，没有阶段级断点续跑

如 §2.1 所示，收据里已有 `phaseHistory` 和 `stageMs`，具备一切断点续跑所需信息，但调度层完全没用。

### 2.6 症结六：告警无聚合，噪音淹没信号

508 条里真正的信号（如 `AUTH_EXPIRED`、桌面通道不可用）被大量重复 `UNKNOWN` 淹没。看护代理每小时读到的都是同一片噪音。

## 3. 优化总纲：三条可独立落地的进化回路

```
        ┌──────────────────────────────────────────┐
        │        运行结果（日志/收据/告警）          │
        └───────┬────────┬────────┬────────────────┘
                │        │        │
      ┌─────────▼──┐ ┌───▼──────┐ ┌▼─────────────┐
      │ A 诊断进化  │ │B 参数进化 │ │ C 知识进化   │
      │ 认得更多错  │ │自己调参   │ │ 经验可检索   │
      └─────────┬──┘ └───┬──────┘ └┬─────────────┘
                │        │        │
                └────────▼────────┘
                  下次运行行为更好
```

| 回路 | 目标 | 借鉴来源 | 落地节奏 |
|---|---|---|---|
| **A 诊断进化** | 让系统认得越来越多的错，并自动沉淀新分类规则 | openJiuwen「演进补丁架构」+ Hermes「Curator 空闲自维护」+ skill-up 技能沉淀 | **P0，最先做** |
| **B 参数进化** | 让 timeout / cadence / retry 由历史数据驱动，而非拍脑袋 | DSPy「程序即优化对象」+ EvoAgentX 优化器 | P1 |
| **C 知识进化** | 把累积证据变成可检索、可老化、可回滚的知识 | Letta 分层记忆 + memflywheel 记忆飞轮 + openJiuwen `evolutions.json` | P1–P2 |

**三条回路的共同纪律**（照抄 openJiuwen 的经验，也是本车间最需要的）：

> **经验层与代码层分离。** 新增的认知写在独立的数据文件里（可版本化、可回滚、可评分），**绝不覆盖源文件**。源文件只在走完封印流程后才动。
>
> **经验层必须有「消费者」。** 数据文件本身不产生行为——openJiuwen 的经验层之所以生效，是因为有一个 Agent **在运行时读取它并据此调整行为**。本车间的 daemon 是**确定性 Python，不会自动读 `evolutions.json`**。因此**任何「外置经验层」项在立项前，必须先回答：谁读它、怎么读、读出的东西如何在不变成「代码」的前提下影响行为**（详见 §4 P0-2「消费者设计（前置·硬约束）」）。**答不出＝不许立项。**

这一条是本方案的灵魂——它直接解决了「改一点就要重封印」的死结。

## 4. 具体优化方案（P0 / P1 / P2）

### ── P0（治最痛的，1 个波次内可完成）──

#### P0-1　结构化收据驱动的失败分类（治 UNKNOWN 噪音）

| 项 | 内容 |
|---|---|
| **现状** | `classify()` 靠 ~15 个硬编码关键词匹配纯文本，未命中即 `UNKNOWN`，detail 无信息 |
| **改法** | ① 每个 step 结束后，先尝试把日志里的**顶层收据**解析出来，读 **外层** `ok` / `stage` / **`reason`** / `phaseHistory` 末项（**字段优先级见下方专块**；**`reason` 是 `stage` 的关键同义字段**，全量实测显示它是最大来源）；② 若拿到结构化收据，**以收据为准**判定分类与失败阶段；③ 文本正则降级为**兜底**（含 `Error: <code>` 提取）；④ 分类结果里带上 `stage` / `reason` 与 `phaseHistory` 末项，写进告警 |
| **借鉴** | Hermes 的「软触发」思路：不是硬编码规则，而是让系统自己注意到信号；skill-up 的「经验沉淀」 |
| **验收判据** | ① 重放告警：对 434 条 UNKNOWN，`detail` **不再出现纯「未命中已知分类」**（实测可达 **99.8%**，仅 2 条边缘残留：1 条空日志 + 1 条 argparse 用法错误）；② `UNKNOWN` 占比 **83% → <5%**（预期 ~0.5%，`<30%` 为宽松下限）；③ 每条告警 `detail` 必须含可读失败码（`stage` 或 `reason`）；④ `--selftest` 新增 **4 正例**（顶层 `stage` / 顶层 `reason` / 嵌套 `reason` / 文本 `Error: <code>`）**+ 2 负例**（嵌套收据反转：外层 `ok:false`+内层 `workflowReceipt.ok:true` 必须判 **FAILED**；超长单行 JSON 必须完整解析、不得被尾部截断） |
| **风险** | 低。**只读不改**：不碰 classify 的既有返回值语义，只在前面插一层解析；解析失败自动回退原逻辑 |

> 收益（**经全量实测**）：这一项**单独**就能把 434 条 UNKNOWN 中的 **433 条（99.8%）**变成可读故障码（详见下方「收据发射清单 v2」与 `docs/solutions/P0-1-实施细则.md`）。读出来的不是噪音而是分类信号：`executor_integrity` 71 / `appeal-status-not-stable` 47 / `desktop-preflight-retry-limit-exceeded` 40 / **封印漂移类合计 58（13.4%）** / `wechat-send-failed` 11 …… 看护代理第一次能一眼归堆，并可直连 P1-1（断点续跑）与既有的封印维护流程。

> 1. **P0-1（调度层 · 不改封印 · 唯一必做项）**：实现「顶层收据优先」解析，**字段优先级 = 顶层 `stage` → 顶层 `ok` → 顶层 `reason` → 嵌套 `reason`/`stage+failed` → 文本 `Error: <code>`**。一步即覆盖 **433/434**。此步纯调度层，零封印风险。

> **更正记录（监理复审 2026-10-03 21:55 · 第三次）**：本节两度被写窄。**第一次**（他人版）误称「jinsha 是真发射者、new-merchants 未必吐」；**第二次**（监理 21:20）仍只认顶层 `stage`、且用了尾部 8000B 截断，得出「仅 22%、须新增 P0-1b」——**同样错**。**第三次**（本版，用整行顶层 JSON + `stage`/`reason` 双字段）定论 **99.8%**。教训已写入 `docs/solutions/P0-1-实施细则.md` §1「顶层收据的精确定义」与 §10 版本记录。

**字段优先级（监理补 · 必做）**：解析器按下列次序取值，命中即停——

| 优先 | 字段 | 含义 | 用途 |
|---|---|---|---|
| 1 | 外层 `stage` | 技能自报的失败阶段（如 `wechat-send-failed`） | 分类 + 写进 `detail` |
| 2 | 外层 `ok` | 技能整体成败（本段发送失败则为 `false`） | 判定 FAILED |
| 3 | **外层 `reason`** | **失败原因码**（如 `dependency-drift` / `daily-record-key-duplicate`）——**实测最大来源（241/434）** | 分类 + 写进 `detail` |
| 4 | 外层 `phaseHistory` 末项 | 已完成到的阶段 | 供 P1-1 断点续跑参考 |
| 5 | 嵌套 `reason` / 嵌套 `stage`+`status:failed` | 如 `send.reason`、`review[].stage` | 分类（标注「嵌套」） |
| 6 | 文本兜底 `Error: <code>` | Node 崩溃栈（如 `channel-context-readback-mismatch`）；取**最后一个**匹配 | 分类 |
| — | 内层 `workflowReceipt.ok` | **仅供判断「业务链是否走完」，不得用于成败分类** | 上下文 |

> **关键 1**：外层 `ok` 与内层 `workflowReceipt.ok` **可以相反**（业务成功、发送失败）。只读内层 = 把失败误判成成功。负例已进验收判据。
>
> **关键 2**：**`reason` 与 `stage` 同等重要**——`stage` 回答「卡在哪一步」，`reason` 回答「为什么」。全量实测中 **241/434 条只有 `reason`、没有 `stage`**，若解析器漏掉 `reason`，覆盖面会从 99.8% 塌到 25%。（这正是本方案 P0-1 两度被写窄的根因。）

## 6. 铁律边界：本方案**绝不能碰**的东西

任何一项优化实施前，先对照此表自检：

| 铁律 | 含义 |
|---|---|
| **安全门零改动** | `EXTERNAL_EFFECT` fail-closed / 防重账本 / 逐字授权 / ActionResult 收据 / policy sha256 / UNSEALED_ACCEPTANCE —— 一律不动 |
| **看护进程绝不代劳重封** | 重封只在「本轮真实非空发送通过」时由 skill 内部原子完成 |
| **失败绝不停排** | 现场维护取代熔断，连败只增告警强度，不产生阻断 |
| **只认当天成功** | 昨日的成功不算本日完成；凌晨成功不顶当日档 |
| **监理不下场替代任务流** | 缺环节**上报车间主任**，禁止代跑代补；未收口不发台账 |
| **发送验证内容不只验送达** | `verified:true` 只证明送达；「0 条记录」是红灯必须上报 |
| **台账每个 ✅ 必须有 run 证据** | 禁止未核实复述 |
| **验证用测试群，生产逻辑必须发线上群** | 严禁把生产逻辑重定向到测试群 |
| **封印改动需受控再封印 + 大同授权** | 修改被封印脚本走 `dependency_maintenance.py prepare()` 全流程 |

## 7. 与车间岗位体系的关系：**能力增强，不新增岗位**（监理评审补）

> 问题（大同提出）：这套方案落地后，车间的「**监理 — 车间主任 — 岗位**」体系会不会多出新岗位？

**结论：不新增任何「生产岗位」，全部落在既有三角色的能力增强上。** 现有 6 个岗位（`runtime/posts.json`：金鲨 `9232` / 淘宝品牌商 `9230` / 淘宝服务商 `9231` / 美团 `9233` / 视频 `9222` / 发微信岗）的**内聚主题与工位契约一个字都不改**——自进化是「让系统更会看病、更会记事」，不是「多招一个工人」。

| 方案要素 | 落在谁身上 | 新岗位？ | 说明 |
|---|---|---|---|
| P0-1 结构化收据分类 | **车间主任**（daemon / `skill_runner.py`） | ❌ 否 | 派班者的「眼睛」变亮，仍**只派班不干活** |

1. **改现有 daemon 的代码**（W1 / W3 / W5）；
2. **新增它周期内调用的模块或数据文件**（P0-3 聚合、P1-2 索引、P0-2 外置表）；

**⚠️ 必须做、但别误当成「新增服务」的一件事：重启现有 daemon。**

才生效。这是**重启**既有服务，不是新增。
