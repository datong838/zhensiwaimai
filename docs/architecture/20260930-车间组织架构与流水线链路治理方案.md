## 1. 对大同组织模型的评价：方向正确，一处关键修正

大同的模型：

| 工人 = 专职岗位 | **修正点**：现实中工人不是常驻进程，而是**岗位资源池**——流水线每班到岗时临时借用，下班归还                                                                | ⚠️ 概念对，形态不同          |

**修正说明**：今天没有一个叫「金鲨工人」的常驻程序。真实形态是：

- **采集岗 = 专用浏览器身份**（隔离 Chrome 实例 + 登录态），谁当班谁连；
- **发送岗 = `wechat-messaging` 共享库的三条适配器**（封印状态），所有流水线发送都走它；
- daemon 是唯一能「派班」的角色，skill 脚本（流水线上的工序）被执行器按班拉起，跑完即退。

这个形态本身是对的（无常驻进程 = 无内存泄漏/僵尸态，符合「禁止常驻」的一贯原则），**不需要推翻重构**；缺的是把「岗位」显式登记、把共用岗位的冲突管住。详见 §4。

**已落地的范式条款**：异常即停线（`unknown-page-overlay` 熔断）、防错（`verified` 幂等防重发）、工人无状态短命（skill 跑完即退）、主任只派班不干活。

**范式预言且已被现实验证的缺口**：G1 = TPS「混线生产必出乱」（9232 五线共用）；G4 = OTP「supervisor 必须有升级策略、重试必须带熔断上限」（jinsha 全天重跑 14 轮）。

**两问评审制（新流水线立项 / 既有流水线改造时必答）**：

1. **TPS 问**：它占哪个工位？互斥组是谁？（答不出 → 不许上线）
2. **OTP 问**：它失败时的升级路径是什么？重试几次后 NEEDS_HUMAN？（答不出 → 不许上线）
