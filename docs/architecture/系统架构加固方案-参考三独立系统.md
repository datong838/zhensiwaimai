## 0. 基本原则（本方案铁律）

1. **三个参考系统都是独立的，与 zhensi_waimai 零依赖**。本方案**不**把 MediaCrawler / Easel / n8n 引入为 zhensi 的依赖，也**不**合并仓库。
2. zhensi_waimai **只"参考学习 + 抄（设计范式 / 代码骨架）"**，长出**自己的**系统架构加固模块，落在 `zhensi_waimai/` 目录内（建议新增 `runtime/` 子目录）。
3. 抄的对象分两类：
   - **抄设计**：n8n 的 retry/queue/error-workflow/schedule/wait 思路；Easel 的常驻守护 + 配置热加载；MediaCrawler 的分层模块化 + 缓存抽象 + 浏览器生命周期隔离。

4. **当前阶段只写方案，不碰任何现有代码**；所有落地动作排期到 §7 的 Phase 1–5。

## 2. zhensi_waimai 现状痛点回顾（映射根因）

来自 `docs/architecture/20260928-任务流稳定性诊断与加固分析.md`，六类根因：
1. **会话冷启动**：hourly cron 派生全新进程，每次重建 ADB/微信/Chrome 会话，中途一断就废。
2. **抖动当失败→无限续跑**：AX/AppleScript 无超时 `subprocess.run`，瞬态抖动复跑，runs 堆积。
3. **资源争用**：桌面微信 + 浏览器 CUA + OCR 挤一台 Mac，全技能抢 `wechat-ui-interaction.lock`。
4. **睡眠/掉线级联**：Mac 睡眠掐断会话，无超时调用挂起后级联。
5. **授权过期单点**：`runtime-policy.json.expiresAt` + `executor-lock.json.UNSEALED_ACCEPTANCE` 任一过期→整链 fail-closed，需人工续章。
6. **恢复覆盖面窄**：`heartbeat_recovery.py` 只认代码类失败，环境故障不真修复，只甩人工。

> 那批 `plan-2026-09-*` / `*-维护方案.md` 是**逐症状打补丁的病历**，根架构从未变。本方案的目的就是**一次替掉根架构**，不再写补丁文档。

## 3. 目标架构（zhensi 自有）—— 四层 + 安全门

```
┌─────────────────────────────────────────────────────────┐
│  L2 编排调度层（抄 n8n 设计）                              │
│  scheduler / retry预算 / 失败分类 / 断点续跑 / 观测看板     │
│  实现：runtime/scheduler.py（或直连已落地的 n8n-obs /data:ro）│
├─────────────────────────────────────────────────────────┤
│  L1 浏览器/重负载 worker 层（抄 MediaCrawler launcher + Easel 常驻）│
│  专用 Chrome 常驻服务 + 中央任务队列（替代每 run 派生）      │
│  实现：runtime/browser_worker.py                           │
├─────────────────────────────────────────────────────────┤
│  L0 常驻会话守护层（抄 Easel gateway.sh 双fork + ollama 防睡）│
│  持有 ADB / 微信 AX / Chrome 会话；暴露 /healthz；launchd KeepAlive │
│  实现：runtime/session_daemon.py                           │
├─────────────────────────────────────────────────────────┤
│  L3 状态/缓存层（抄 MediaCrawler cache + db store base）    │
│  session态 / 登录过期 / run历史 prune；可插拔 local→redis   │
│  实现：runtime/state_store.py + runtime/cache_layer.py      │
└─────────────────────────────────────────────────────────┘
        ▼ 下方安全门（绝不动，全在 executor 层）
  ┌──────────────────────────────────────────┐
  │ 防重账本 / EXTERNAL_EFFECT fail-closed /  │
  │ 逐字授权 / ActionResult 收据              │
  └──────────────────────────────────────────┘
```

**核心转变**：触发方式从"每小时外部 heartbeat 派生新进程"→"L2 向 L0 常驻守护**发一个执行请求**，守护在已有会话上续跑"。L0 常驻即消掉根因 1、4；L1 常驻 + 队列消掉根因 3；L2 重试预算 + 失败分类消掉根因 2、6；L2 授权续期告警消掉根因 5；L3 prune 治 runs 堆积。

## 5. 失败分类与重试预算（抄 n8n `retryOnFail`）

executor `fail()` 时 POST 标准 payload：
```json
{ "workflow_id": "...", "business_date": "...", "phase": "...",
  "reason": "...", "needs_login": false, "category": "recoverable|needs_login|unknown" }
```
- **recoverable（瞬态/环境）**：窗口尺寸抖动、OCR 噪声前缀、导航超时、锁等待 → L2 自动重试（抄 `maxTries=3` + `waitBetweenTries`），**连错 3 次 / 5 分钟内不再派生新 run**，冷却后升级。
- **needs_login**：登录态过期 → `@人` 告警，等人工重登，**不自动重试**（避免越重试越锁）。
- **unknown**：未知 → 升级人工，不静默 fail-closed。
- **铁律**：`attempted` / `unknown` 状态**绝不重试**（幂等门在 executor，L2 碰不到），与 n8n 约束一致。

## 6. 授权续期与配置热加载（抄 Easel 热加载 + ollama 防睡）

- `runtime-policy.json` 改**热加载**（抄 openclaw.json：改文件即生效，无需重启守护），避免改授权要停整链。
- **过期前告警**：L2 每日扫 `expiresAt`，到期前 N 天企业微信机器人告警（抄 n8n Error Workflow 告警），**不静默 fail-closed**（治根因 5）。
- 守护进程绑 `launchd KeepAlive` + 启动时 `caffeinate -is`（抄 ollama 防睡），治根因 4。

## 8. 安全门不可动清单 + 验收标准

**不可动（全部留在 executor 层，加固层绝不触碰）**：
- 防重账本（幂等，避免重复发消息/下单）
- `EXTERNAL_EFFECT` fail-closed（外部副作用默认拒绝）
- 逐字授权（发送前明确确认）
- `ActionResult` 收据（执行结果留痕）

**验收标准（每个 Phase 末）**：
1. L0：守护进程 `launchd` 常驻、`/healthz` 200、模拟 Mac 睡眠 10min 后会话仍在。
2. L1：同一时刻仅一个浏览器 worker 消费任务，无 `wechat-ui-interaction.lock` 等待 > 1min。
3. L2：注入 1 次瞬态故障 → 自动重试 ≤3 次后恢复；注入 1 次登录过期 → 仅告警不重试。
4. L3：run 历史自动 prune（保留 ≤30 天），不再产生新 `plan-*` 补丁文档。
5. 全程：executor 安全门单测回归全绿，防重账本无重复发送。

## §10 调研修订（2026-09-28 读真实代码 + 摸排 14 流程后）

### 10.1 推翻的两个假设
- **假设 A（14 skill 共用 candidate 模板）**：实际**异构**。执行器 py/mjs 混用；原以为"scripts 为空"的 6 个 skill 实际都有入口（`workflow.py` / `entrypoint.mjs` / `deliver_batch.mjs` / `appeal_executor.mjs` 等），只是不叫 `workflow_executor.py`。**无单一模板可改**，原"改 candidate 模板覆盖全部"不成立。
- **假设 B（缺超时/锁/幂等）**：实际**安全基建已存在**。`fcntl.flock` 互斥锁、`WeChatExecutionGuard`（持锁+等竞争进程离场）、`wechat-messaging/executor.py` 的 **SIGALRM `deadline()` 超时** + `ledger.atomic_json` **防重账本**、`runtime_guard` 的 **policy sha256 fail-closed**、`executor_integrity` 的 `UNSEALED_ACCEPTANCE` 门均在。原方案"补超时/锁"部分冗余。

### 10.2 真实架构（关键）
- **无中央 dispatcher**：全仓无 registry/dispatch.py；触发器＝`~/Library/LaunchAgents/Feibing Neo.plist` → 第三方 Rust app `neo-rust-app`，**每小时硬编码**调各 skill 入口命令。Rust 派发逻辑不可读。
- **wechat-messaging 是统一收发底座**，被 8+ 业务 skill 委托；`negative-review-appeal-reporting` 是 taobao-flash 的共享采集库（非独立派发）；`meituan-intelligent-customer-service` 无 CLI，由 agent/harness 驱动。
- 运行记录散落：`runs/`(148) / `outputs/` / `records/` / `state/` / `work/` + 各 skill `.runtime/`。

### 10.4 L2 落地方式修正（关键决策）
因 Feibing Neo 是硬编码第三方触发器、不可改，L2 包裹层不能"接管 Rust 派发"，只能**在 skill 入口处注入薄 shim**：
- 原入口 `scripts/XXX.py|.mjs` 改名 `XXX_core.py|.mjs`；新 `XXX.py|.mjs` 仅 3–5 行：调用 `runtime/skill_runner.py`（zhensi 自有、落 `runtime/`），由它按 **manifest** 查真实命令、加 **超时 + 重试预算(连错 3 次/5min 冷却) + 失败分类(recoverable→重试 / needs_login→@人 / unknown→升级) + run 历史 prune**。
- 好处：Feibing Neo 调用路径不变、零改原 executor 逻辑（安全门不动）、14 流程一把覆盖。
- 例外：`meituan-intelligent-customer-service`（无 CLI、harness 驱动）与 `negative-review-appeal-reporting`（共享库）不进 shim，单独处理或排除。

### 10.5 Phase 重排
- **Phase 1（最先）**＝ L2 入口 shim + `runtime/skill_runner.py` + 失败分类器 + run prune + 调用契约 manifest（覆盖 14 流程，零改原 executor）。
- **Phase 2**＝ L0 会话常驻守护（改 executor 内会话创建，更侵入，且 WeChatExecutionGuard/锁已缓解争用）。
- **Phase 3**＝ L1 浏览器 worker 常驻。

### 10.6 当前触发方式定论（用户澄清 + 方向佐证）
- 用户确认：14 个 skill **当前由 codex 从外部驱动**（手动跑或 codex 自带定时），**不是 Feibing Neo，也不是 WorkBuddy 自动化**。
- 佐证：仓库内无任何 central scheduler / registry / dispatch；`Feibing Neo.plist` 仅做 app 开机自启（无参数、无定时、无 skill 映射）。
- **推论**：统一调度器是**新建替代** codex 触发的，无旧调度兼容负担。

### 10.7 统一调度器形态：一键启动 + 代理看护（用户定调）
用户明确要求："统一调度器 我希望你 仅仅是 一键启动，然后后续每个流程你看着执行完，你适合看护着。"
- **形态 ≠ 自治 cron**：不是 set-and-forget 定时循环，而是**单入口 launcher（`runtime/run_all.py`）+ 代理（WorkBuddy）逐流程看护**。
- **机制**：launcher 按 manifest 顺序（或依赖序）对每个 skill 调 `skill_runner.py`（超时 + 重试预算 + 失败分类 + run prune）；**每个流程结果回传代理**，由代理判断：
  - `recoverable`（瞬态）→ 预算内自动重试（连错 3 次 / 5min 冷却）
  - `needs_login`（登录态失效）→ @人告警，等人工恢复
  - `unknown`（真故障）→ 升级，附日志
- **为何优于自治重试**：把"抖动当失败无限续跑（thrashing）"交给有判断力的代理而非呆板循环，正好治根因②；且天然零改 skill 内部逻辑。

### 10.8 执行器/共享库维护授权（用户授权 + 测试前提）
用户授权："你也可以 维护 依赖的执行器或共享库。前提是你要测试好。"
- 详见 `docs/architecture/流程执行器依赖与共享库清单.md` §五（2026-10-18 改名；条目已重导 23 条）：改造项 A–E（合并 fork 模块 / 修 `.codex` 硬编码路径 / 解 sha256 自锁 / 补 subprocess timeout / 删漂移副本）。
- **铁律**：每项改造须有独立测试（单元 + 一次真实跑通）后才并入主线；**安全门（EXTERNAL_EFFECT fail-closed / 防重账本 / 逐字授权 / 收据）一行不动**；`mobile_runtime/`、`skills/.daily-jinsha-reports-core/`（封板）不动。

### 10.9 Phase 重排（终版）
- **Phase 1（最先、零碰 skill）**＝ 建 `runtime/`：`skill_runner.py`（超时+重试预算+失败分类+run prune）+ `skills_manifest.json`（14 条目，逐 skill 指定 解释器/cwd/命令/参数）+ `run_all.py`（一键启动入口，由代理驱动看护）。
- **Phase 2（带测试改造）**＝ 按 `流程执行器依赖与共享库清单.md §五` 的 A–E 逐项维护执行器/共享库，每项独立测试。
- **Phase 3**＝ L0 会话常驻守护（抄 Easel `gateway.sh` 双 fork+setsid+healthz 骨架）。
- **Phase 4**＝ L1 浏览器 worker 常驻（抄 MediaCrawler `browser_launcher.py`）。
- **Phase 5**＝ 授权到期前告警 + 静默看板。

> 本方案恪守 §0 铁律：三系统独立、只抄设计/骨架、**安全门零改动**。Phase 1 建 `runtime/` 为全新文件，不碰任何现有 skill 代码；执行器/共享库维护（Phase 2）须逐项测试后并入。配套依赖基线见 `docs/architecture/流程执行器依赖与共享库清单.md`（2026-10-18 改名，原 `14流程执行器依赖与共享库清单.md`）。
