## 3. ⚠️ 重启后「不会自动恢复」的唯一种口：微信中继 relay

**为什么**：relay（localhost_relay.py，127.0.0.1:8732 → Windows 网关 192.168.110.184:8731）负责给 launchd daemon 提供最后一跳（daemon 连局域网被 macOS TCC「本地网络」授权拦，Errno 65）。launchd 标签 com.zhensi.windows-relay 结构性不可用（launchd 进程无 TCC 授权，启动探测必败，占着 8732 端口还不干活）。

**★2026-10-18 20:22 重启实测新坑（SOP 漏洞已补）**：仅 `launchctl bootout` **不够**——plist 文件只要还在 `~/Library/LaunchAgents/` 且后缀是 `.plist`，**重启后 launchd 登录时自动重新加载**（RunAtLoad=true），且 KeepAlive=true + ThrottleInterval=10 会让它每 10 秒循环空转刷 relay.err.log（143KB 全是 `no candidate passed driver identity check`），端口被占着不干活，curl 经 8732 一律 HTTP 000。**正解：bootout 后必须把 plist 改名禁用**（`.plist.disabled-日期`），本次已改名为 `com.zhensi.windows-relay.plist.disabled-20261018-reboot-proof`。判活口诀：端口 LISTEN ≠ 干活，必须经 8732 POST list_sessions（带 Bearer 头）回真实会话。

**恢复方式（二选一）**：

- **方式 A（推荐，大同零操作）**：重启后开 WorkBuddy，跟我说一声，我用后台任务方式重拉 relay 并端到端验证。
- **方式 B（大同自己）**：打开**终端（Terminal.app）**跑：
  ```bash
  bash ../wechat-windows-driver/relay-up.sh
  ```
  看到 `已启动 127.0.0.1:8732 -> candidates=192.168.110.184,...` 且后面跟着一行 `{"ok": true, ...}` 即成功。
  （必须是有本地网络授权的 GUI 会话——终端或 WorkBuddy 都行；**不要**用 launchd 起。）

**为什么 daemon 也依赖它**：careloop 是 launchd 拉的 ⇒ 它里面的微信 client 直连 Windows 网关会被 TCC 拦（Errno 65）⇒ 回落走 8732 relay。relay 不在，daemon 的发送类任务会 fail-closed 失败（**不会误发**，安全），恢复 relay 后按需补跑。

## 5. 重启注意事项（大同）

1. **必须正常关机重启**（苹果菜单）。强制断电可能丢 Chrome 未 flush 的登录态写入。
2. **重启总时长越短越好**：饿了么/美团/金鲨的**服务端会话 TTL 固定不滑动**（2026-10-15 实证：定期访问不能延长，9231 一夜就掉过）。本地登录态（Cookie/localStorage）重启不丢，但服务端可能已过期——**重启后 2 小时内验收**，掉了按 §6 处理，只是要人工重登一次。
3. 9232（金鲨）重启后是**有头窗口**（设计如此，大同能看到页面），窗口别最小化关掉。
4. 重启后各岗页面从初始 URL 起（9232 会停在「负面评价」页不是「数据上传」页）——**这是正常的**，daemon 跑流时会经左侧菜单导航；大同手工要用哪个页面也从左侧菜单点，**别新开标签页/别手打 URL**（2026-10-18 教训：新开标签必撞无文案教程浮层）。

**两条新铁律（本次实锤）**：
1. **bootout ≠ 禁用**：LaunchAgent plist 只要后缀是 `.plist` 还在目录里，重启后 launchd 自动重新加载（RunAtLoad）。持久禁用 = 改名/移走，不是 bootout。
2. **`launchctl disable` 是持久状态、跨重启存活**：服务「plist 在但不自动起」时，先 `launchctl list` 确认服务域无此 label，再 `launchctl enable gui/501/<label>` + `launchctl bootstrap gui/501 <plist>` 两连修。
