# 每日20点台账后收口与新对话交接制度

用户2026-10-28明确授权。北京时间每天20:00在当前监理聊天唤醒，以下步骤按顺序执行。目标是连续接班且避免单一聊天长期累积上下文；不是复制全部历史对话。

## 1. 前置：当日工作台账已经发出

先读仓内监理Skill、企业微信UI岗位约定、最新用户约束及当日交接。核实当日原台账真实送达凭据。仅生成、发送意图、其他文件、旧日记录或unknown不算台账已经发出。若尚未发送，记录本日待前置，不自行放行台账；台账送达后在同一持续Goal顺延接续，不等次日20点、不创建重复定时任务。

今天2026-10-28仍24流，用户已确认业务完成并明确放行发送；2026-10-29起27流，后续数量按最新用户指定和班表核对。业务确认单独留痕，不改技术unknown/原发送记录。商家经营指标、优惠券、巡店三流由另一台电脑负责，本机不接管、不采集其数据、不修改其代码、状态或排班。

用户长期授权：原图片已合规实际单次提交，且当日群、载荷、绑定、数量及空框证据完整时，客户业务按完成展示，不再每日等待人工确认，不设月底或跨年截止；技术回执缺失只记内部遗留，原unknown保持且不重发。仅有意图、零提交、真实失败或错群错图不算完成。此图片业务判定不替代最终Excel台账自身的原文件发送节点与防重门检。

## 2. 梳理当日全部遗留

用“问题、原证据、根因或未知点、影响、优先级、已修/待修/待真实验收、下一步、恢复边界”记录，区分客户业务完成与内部技术遗留。保留全部原事实和范围，不用技术待核否定用户明确的业务验收，也不伪造自动验证。清单写入docs/operations，详细凭据写runtime/state，后续以新证据更新。

## 3. 完善与修复

先方案和具体文件目录，做最小修改、自测、一致性和风险核对及原门禁验证；代码、资料、状态及时commit/push并核验远端。真实生产仍只沿原主任/control/适配器/队列/账本；attempted/unknown不重发、不换事件、不改游标。仅登录/扫码/验证码/账号风险等真实外部阻碍报告本聊天，其他授权内可恢复问题继续处理。不能为了封板发送测试图或借终态任务复制历史图。

## 4. 明日全流程预检

以Asia/Shanghai明日日期及最新班表为准，逐流核对排班、依赖、数据日期/范围、全量来源与分页/字段/模板、解释器/共享库与release policy、新日事件及旧unknown隔离、原主任/真实锁/四岗业务域/登录/原企业微信队列、目录和有界恢复。优先08至10点链路。明日尚未产生的数据标明到点新鲜度复核，不用旧数据冒充通过，不提前执行明日生产。

全局口径从24变27时，三条另一机器负责的流只记执行归属与已提供的交接摘要，不在本机检查或执行其细项。预检逐流清单及证据存runtime/state/next-day-preflight/目标日期/，同目标日期只补变化和未完成项。必须修掉已知可恢复卡点；待自然真实验收、未来数据或真实外部条件明确列入交接，不能无限等它们而漏掉每日交接。

## 5. 保存完整交接包

按[监理新对话交接模板](监理新对话交接模板.md)填写，保留完整原Goal objective、真实status、最新用户覆盖约束、全部待办及已完成凭据，不缩小目标。收录代码/测试/部署/回滚、数据目录/日期/名单/原账本和防重、真实运行进程与锁（只作当时快照）、每项定时任务、下一步行动及停止规则。更新latest交接并推送远端。交接包引用可靠原文件，不能只写“看旧聊天”。

参考前例：runtime/state/night-goal-handoff/20261028-0606-cutoff-handoff.json、automation-transfer-20261027.json、transfer-goal-clear-20261027.json。例子内旧threadId仅是历史，绝不能照抄到新迁移。新对话读取交接包和必要证据，不灌入全部历史聊天。

## 6. 最后一步：新建干净聊天并交出所有权

这是用户明确授权的每日最后阶段。用create_thread新建当前项目的干净聊天，不fork历史。先list_projects核对当前仓库，传入完整交接入口、完整原objective及最新覆盖约束。新聊天先只读核收、确认资料和待办齐全，未收到正式接班信号前不创建Goal、不执行生产。等待其明确接收结果，不能只凭新聊天存在就宣称接班完成。

若原Goal active且未完成：保存原目标和状态、停止本聊天继续施工；按官方app-server JSON-RPC initialize（experimentalApi=true）、initialized、thread/goal/clear（实际旧threadId，origin=user）、thread/goal/get，核验源Goal严格null。不得update_goal伪complete，不修改私有数据库/锁。然后向新聊天发送接班信号，由新聊天以完整原objective创建Goal，不设token_budget；创建结果未知先回读，不重复创建。核验新Goal真实active且旧Goal仍null，才算Goal迁移成功。既有明确暂停目标不得借迁移恢复；原Goal null/complete时不重建已完成的旧目标，保存真实状态，按未完成任务和原08点规则接续。官方操作失败如实报告并保留交接，不能声称迁移成功或并行运行两个Goal。

在新聊天确认接续后，逐一用官方automation_update把本监理拥有的全部定时任务挂到新threadId，包括20点任务自身。每次从当前任务列表发现全部归属项，不只依赖固定白名单；当前已知02、06、08、20、22点共5项。保留名称、时间、启停、通知和其他设置，更新targetThreadId及prompt中嵌入的旧threadId（尤其06点Goal清理目标）。回读每项核验新归属，保存前后映射及完整清单；不搬动无关项目和另一台电脑任务，不激活历史暂停任务、不新建重复排班。

新聊天随后带着全部未完成任务继续工作，不等用户再次说开始；旧聊天仅完成迁移核验和交接通知，不再与新聊天并行施工。原主任和浏览器不停止。22维护/06硬截止/08启动的职责与时刻保持；给06点收口留足时间，不跨06继续前夜施工。存在未完成项仍须完整交接，不能伪complete，也不能因未修完而省略每日新聊天接班。
